# NDIP-3 代码级设计

Status: Draft

## A0：当前调用者清单

`DelayShard.readyProjections` 是单消息 mutation 的投影汇合点，涵盖 Schedule、Cancel、
Reschedule、Claim/revoke、retry、Admission、Outcome、终态与受控恢复。prior/next 跨 Lane
必须共同计算；当前 command API 不扩为 batch API。

`findLaneCandidate` 的直接调用者：`readyProjections`、source-ordered Lane 控制（kind 9）、
Lane activation/control helpers、Lane retire 前的非空检查、`rebuildReadyIndexes`。
`findLaneNativeCandidate` 的直接调用者：`readyProjections`、`projectLane` 的便捷重载、
`rebuildReadyIndexes`。`projectLane` 从 mutation、控制、激活和 rebuild 进入。
精确方法名/计量与逐个完整审计义务在 A0/A3 源码核对后补齐。

DUE 使用现有 eligibleAt，ORDERED 使用 deliverAt，NATIVE 使用 candidateAt；同时间使用
完整 key 的 unsigned 字节顺序。A 不改变 Lane ID、消息 schema、prepared bytes 或发送身份。

## A1/A2：计划和提交

小型 head helper 使用 exact removed/overwritten keys 与 inserted entries。每前缀的
首个非排除持久项严格验证后与局部新增最小项合并。健康单消息最多读两个候选。
FOUND / EMPTY_CONFIRMED / INCOMPLETE 必须可区分；插入项不能掩盖未完成的持久读取。
预算贯穿全部前缀、Message/binding 依赖以及 READY tail/wrap。任何必要分支未完成时
不写 Message、head、quota、结果或 applied source position；不创建 Producer authority。

同一 plan 在 Shard 串行 turn 内绑定 Owner/Store/source/mutation view；成功 WriteBatch 后
才发布内存状态，未知写结果使用现有 Store fencing。全前缀审计移到显式恢复/审计路径。

## 后续契约

B1–B6 将完整设计中的 Target identity、最终 key layout、共同 policy 签名域、K 个真实
执行域、局部 quota revision、增量 aggregate、恢复公平性、ordering contract、观测模式、
资源预算与迁移 replay 冻结成精确字段/状态/向量；未冻结内容仍属 PLANNED。
C–F 必须逐项替换为真实实现路径和结果，不能仅把旧 Lane 类型改名。

- Outcome/recovery：`applyUnknownPublishOutcome`、`applyPublishedPublishOutcome`、

  `normalizeDefinitiveRetryAfterNotPublishedEvidence`、`terminalizeNotPublishedEvidence`、
  `settleVerifiedPublishedUncertainGeneration`、`applyPossibleDeliveryTerminalization`。
- terminal/expiry：`applyReplayDeadLetterMutation`、`applyExpireGenerationMutation`。
- 控制与激活：`applyShardControlMutation`、`updateLaneGate`、`updateLaneReadiness`、
  `activateLaneReadiness`；非空保护：`retireLaneWithTerminalGuard`。
- 完整审计义务：`rebuildReadyIndexes` 目前通过三个全扫前缀验证尾部；A1 后必须显式保留。
  控制/激活的求头与首次恢复完整审计分开，不将一次局部求头当作队尾完整性证明。

测试-only 全扫 oracle：`committedHeadsMatchFullScanReferenceAcrossMutationsAndClaimRollback`
覆盖混合 DUE/ORDERED、时间 tie、Cancel、Reschedule 两个方向、Claim/revoke 后的 head。
Native 现有基线：`explicitNativeScheduleKeepsOrdinaryDueAndMaintainsSeparateStaticCandidate`。
KeyCodec 基线：`timelineAndTerminalKeysPreserveUnsignedGenerationBits`、
`remainingRegisteredKeyNamespacesUseExactLayouts`；A3 扩充预算/写失败/损坏/重开矩阵。

固定基数探针：`DelayShard.headReadStatistics()` 区分候选 key 与依赖 Message 点查；
`ShardStore.operationStatistics()` 区分 READY 返回读取、quota/fairness 组装 put 字节、
native write 调用和成功返回。prepared 字节含未提交 batch，不能充当 committed WAL bytes。
全部为进程内计量，不产生逐消息 durable SLO。

## A1 已实现的取头与审计分离

`HeadIndexUpdater.firstStored` 在短生命周期 iterator 内逐项访问，遇到首个非 exact removed
key 即停；未受 A2 预算限制的本切片仍沿用无耗尽的读取配置，因此它不将部分读取解释为空。
DUE/ORDERED 使用 prior SCHEDULED 的完整 `timelineKey`；NATIVE 使用 prior 的完整
`nativeCandidateKey`。CLAIMED 本身不伪装为仍存在的 timeline key。跨 Lane 的 prior/next
仍由一次 readyProjections 和原有业务 WriteBatch 处理。

调用方严格解码选中 key/value/Message，再按原 comparator 与 included candidate 取最小。
明确删除的 key 不需要为找 successor 再解码 Message。`auditLaneCandidateIndexes` 在
`rebuildReadyIndexes` 和正式 `activateLaneReadiness` 中保留全前缀完整性/容量检查；
正常 mutation 不再附带队尾审计。A3 仍需完成有界审计/写失败和恢复专项。

测试增加 `exactOverlayReadsAtMostDeletedKeysPlusOneAtEveryBacklogSize`、
`emptyAndDeletedOnlyPrefixesDoNotReadTheAdjacentNamespace`、
`unrelatedMutationDoesNotAuditTailButRebuildAndSelectedCorruptionFailClosed`。
随机 mutation/Claim 回归继续使用独立全扫 oracle。

## A2 进行中：读取基础与待接通边界

已加入 `ShardStore.visitResult` 的 RANGE_END / RECORD_LIMIT / VISITOR_STOPPED / INCOMPLETE
结果，以及 `HeadReadResult` 的 FOUND / EMPTY_CONFIRMED / INCOMPLETE。
seek、entry、next 和依赖点查之前检查共同 record/byte/elapsed budget；使用 native iterator
upper bound，已返回但超出剩余额度的 key/value 仍计入 actualBytes/actualRecords。

`readWithBudget` 在 Store monitor 内绑定多次 iterator 与点查；调用顺序为 Shard 单写者锁→
Store monitor，reader 不得写入业务 batch 或嵌套新预算。ReadView 绑定 Store 实例、native
sequence、已完成写次数和 Owner runtime metadata；提交方通过 Batch.requireReadView
验证；ReadIncompleteException 传播前再次核对视图，不能用普通预算让出掩盖写入变化。
这些都是进程控制类型，不注册客户端 stable code 或赋予 Producer 权限。

## A2 READY discovery 已接通（切片仍未完成）

`PersistentLaneScheduler` 逐项调用 `visitResult`，在同一 `BoundedReadBudget` 内完成
READY、两次 Lane 验证、Message、timeline 及可选 native Message/timeline/binding 读取。
`SchedulerBudget.maxMessages` 仍表示逻辑 head 数；物理记录上限由当前最大依赖路径
`8 × maxMessages` 派生并限制到 Integer.MAX_VALUE，全部实际 key/value 字节共用原 byte cap。
普通投影读取 5 条，含 native 验证时 7 条，加 binding 时最多 8 条。此为应用读取计数，
不是 RocksDB 块 I/O、解码复制内存或外部 policy RPC 的物理资源认证。

尾部使用 `lastScannedReadyKey + 0x00` 作为 exact cursor 的独占后继，避免为跳过 cursor
先多读一条。只有 tail 的 RANGE_END 已被证明后才尝试 wrap；两个区间没有重置额度。
只有完整校验的投影进入临时列表。依赖耗尽时丢弃当前未完成投影，保留此前完整投影；
尚无完整投影时不发布队列、不写 scheduler META，也不推进 cursor。完整 tail 后的未完成
wrap 不增加 wrap generation；完整但尚未到期的 wrapped native 投影也不推进到期 cursor。
两个区间均已证明结束后，可点查原 cursor，保留 singleton/live policy refresh 语义。

Store 读取计划绑定的 ReadView 在 `withReadView` 内再次校验，并持锁发布进程状态；
fairness batch 也要求同一 ReadView。native policy callback 在 Store monitor 之外执行，
避免外部 authority/source-position callback 与 Shard→Store 顺序形成倒置；每次发起前
仍检查同一 elapsed deadline。回调期间若 Store view 改变，整个发布步骤失败并恢复本地状态。
预算只能阻止下一次动作发起，不能中断已经进入的 native read 或外部调用。

`discoveryReadStatistics` 暴露最近一次实际 records/bytes、成功计费字节、拒绝的 Store read
次数及首个耗尽原因。READY 点查也计入 Store 的 READY probe。visitor 内的依赖 get 耗尽
转换为显式 INCOMPLETE 后仍检查 iterator.status；原生 I/O error 不被预算让出掩盖。

此批不声称 Source Apply/head mutation 的预算链已完成，也不将旧 4 KiB fixture 视为
最大合法资源认证。Claim handoff 回归按实际 READY + 两次 Lane + Message + timeline
字节构造完整读取预算并核对计量；最大合法 mutation envelope 和正式激活配置仍待闭合。
