# NDIP-3 代码级设计

Status: Draft

## A0：当前调用者清单

`DelayShard.readyProjections` 是单消息 mutation 的投影汇合点，涵盖 Schedule、Cancel、
Reschedule、Claim/revoke、retry、Admission、Outcome、终态与受控恢复。prior/next 跨 Lane
必须共同计算；当前 command API 不扩为 batch API。

`findLaneCandidate` 的直接调用者：`readyProjections`、source-ordered Lane 控制（kind 9）、
Lane activation/control helpers、Lane retire 前的非空检查、`rebuildReadyIndexes`。
`findLaneNativeCandidate` 的直接调用者：`readyProjections`、`projectLane` 的便捷重载、
`rebuildReadyIndexes`。`projectLane` 从 mutation、控制、激活和 rebuild 进入。
精确方法名/计量与逐个完整审计义务在 A0/A3 源码核对后补齐。

DUE 使用现有 eligibleAt，ORDERED 使用 deliverAt，NATIVE 使用 candidateAt；同时间使用
完整 key 的 unsigned 字节顺序。A 不改变 Lane ID、消息 schema、prepared bytes 或发送身份。

## A1/A2：计划和提交

小型 head helper 使用 exact removed/overwritten keys 与 inserted entries。每前缀的
首个非排除持久项严格验证后与局部新增最小项合并。健康单消息最多读两个候选。
FOUND / EMPTY_CONFIRMED / INCOMPLETE 必须可区分；插入项不能掩盖未完成的持久读取。
预算贯穿全部前缀、Message/binding 依赖以及 READY tail/wrap。任何必要分支未完成时
不写 Message、head、quota、结果或 applied source position；不创建 Producer authority。

同一 plan 在 Shard 串行 turn 内绑定 Owner/Store/source/mutation view；成功 WriteBatch 后
才发布内存状态，未知写结果使用现有 Store fencing。全前缀审计移到显式恢复/审计路径。

## 后续契约

B1–B6 将完整设计中的 Target identity、最终 key layout、共同 policy 签名域、K 个真实
执行域、局部 quota revision、增量 aggregate、恢复公平性、ordering contract、观测模式、
资源预算与迁移 replay 冻结成精确字段/状态/向量；未冻结内容仍属 PLANNED。
C–F 必须逐项替换为真实实现路径和结果，不能仅把旧 Lane 类型改名。

## A1 已实现的取头与审计分离

`HeadIndexUpdater.firstStored` 在短生命周期 iterator 内逐项访问，遇到首个非 exact removed
key 即停；未受 A2 预算限制的本切片仍沿用无耗尽的读取配置，因此它不将部分读取解释为空。
DUE/ORDERED 使用 prior SCHEDULED 的完整 `timelineKey`；NATIVE 使用 prior 的完整
`nativeCandidateKey`。CLAIMED 本身不伪装为仍存在的 timeline key。跨 Lane 的 prior/next
仍由一次 readyProjections 和原有业务 WriteBatch 处理。

调用方严格解码选中 key/value/Message，再按原 comparator 与 included candidate 取最小。
明确删除的 key 不需要为找 successor 再解码 Message。`auditLaneCandidateIndexes` 在
`rebuildReadyIndexes` 和正式 `activateLaneReadiness` 中保留全前缀完整性/容量检查；
正常 mutation 不再附带队尾审计。A3 仍需完成有界审计/写失败和恢复专项。

测试增加 `exactOverlayReadsAtMostDeletedKeysPlusOneAtEveryBacklogSize`、
`emptyAndDeletedOnlyPrefixesDoNotReadTheAdjacentNamespace`、
`unrelatedMutationDoesNotAuditTailButRebuildAndSelectedCorruptionFailClosed`。
随机 mutation/Claim 回归继续使用独立全扫 oracle。

## A2 READY discovery 已接通（切片仍未完成）

`PersistentLaneScheduler` 逐项调用 `visitResult`，在同一 `BoundedReadBudget` 内完成
READY、两次 Lane 验证、Message、timeline 及可选 native Message/timeline/binding 读取。
`SchedulerBudget.maxMessages` 仍表示逻辑 head 数；物理记录上限由当前最大依赖路径
`8 × maxMessages` 派生并限制到 Integer.MAX_VALUE，全部实际 key/value 字节共用原 byte cap。
普通投影读取 5 条，含 native 验证时 7 条，加 binding 时最多 8 条。此为应用读取计数，
不是 RocksDB 块 I/O、解码复制内存或外部 policy RPC 的物理资源认证。

尾部使用 `lastScannedReadyKey + 0x00` 作为 exact cursor 的独占后继，避免为跳过 cursor
先多读一条。只有 tail 的 RANGE_END 已被证明后才尝试 wrap；两个区间没有重置额度。
只有完整校验的投影进入临时列表。依赖耗尽时丢弃当前未完成投影，保留此前完整投影；
尚无完整投影时不发布队列、不写 scheduler META，也不推进 cursor。完整 tail 后的未完成
wrap 不增加 wrap generation；完整但尚未到期的 wrapped native 投影也不推进到期 cursor。
两个区间均已证明结束后，可点查原 cursor，保留 singleton/live policy refresh 语义。

Store 读取计划绑定的 ReadView 在 `withReadView` 内再次校验，并持锁发布进程状态；
fairness batch 也要求同一 ReadView。native policy callback 在 Store monitor 之外执行，
避免外部 authority/source-position callback 与 Shard→Store 顺序形成倒置；每次发起前
仍检查同一 elapsed deadline。回调期间若 Store view 改变，整个发布步骤失败并恢复本地状态。
预算只能阻止下一次动作发起，不能中断已经进入的 native read 或外部调用。

`discoveryReadStatistics` 暴露最近一次实际 records/bytes、成功计费字节、拒绝的 Store read
次数及首个耗尽原因。READY 点查也计入 Store 的 READY probe。visitor 内的依赖 get 耗尽
转换为显式 INCOMPLETE 后仍检查 iterator.status；原生 I/O error 不被预算让出掩盖。

本 discovery 批次自身不证明 Source Apply/head mutation 的预算链，也不将旧 4 KiB fixture 视为
最大合法资源认证。Claim handoff 回归按实际 READY + 两次 Lane + Message + timeline
字节构造完整读取预算并核对计量；最大合法 mutation envelope 和正式激活配置仍待闭合。


## A2 HeadPlan 和 source/Claim/recovery 接通

`DelayShard.readHeadPlan` 持有 Shard→Store 顺序，使用一个 `HeadReadPolicy` 派生的
BoundedReadBudget 计算整个消息 delta 的所有 Lane 与 DUE/ORDERED/NATIVE 分支。
所选候选的 Message、legacy binding/Claim/Admission 依赖通过同一个 Store 读取 scope
计费。旧 `firstStored` 仅保留为组件兼容 helper；writer 调用三态 `HeadIndexUpdater.read`，
INCOMPLETE 不与 inserted candidate 合并，也不写任何业务投影。

每个完成 plan 带有 Store/Owner ReadView、mutationSequence 与 applied source position。
`LaneProjection` 必须携带该 binding；`writeReadyProjections` 在同一 Store monitor 内
验证全部投影后才开始构造业务 WriteBatch，`putReadyProjection` 在 batch 中再核对。
未绑定或陈旧投影不能开始业务 batch。单 Lane 控制、readiness/activation helper、retire no-work 证明和逐 Lane
fenced rebuild 也使用这个读取入口。恢复仍保留单独的全尾部审计，未把局部 head 求值
当作完整 audit；rebuild 的多 Lane 投影必须在同一未变化的 Store 上一起提交。

`runReadRetryableMutation` 在整个 command/system mutation 或严格 Claim 前捕获 Store view，
发生预算耗尽时验证从入口起没有 Store 写入、mutation/source 变化，才创建专用的
`HeadReadIncompleteException`。外层 mutation 已有写入时，即使内层提供局部只读证明也
不能改称整个外层可重试。未知 native write 仍走既有 Store/Owner fencing。

SourceApplyCoordinator 的 READ_INCOMPLETE 保留 exact entry，清除已完成的 submission，
不 ACK、不推进 source cursor、不写客户端拒绝结果；下一 turn 重新提交并核对当前 Owner。
OwnerRecoveryCoordinator 保留 pending entry 和 CATCHING_UP，返回独立 readIncompleteReason，
再调度时重建 submission；只有该条记录的结果和 cursor advance 完成后才考虑激活。
其他 work-class 的失败不能被同一轮的 head read yield 掩盖成普通 retry。

严格 Claim 在 proven read yield 后释放 permit、重新排入 exact polled head，并返回本地
READ_INCOMPLETE；没有 Claim/source 业务提交或 Producer authority。失败回排目前仍沿用
原 fairness META 持久化，C3 将完成进程内公平性收敛。permit release/回排自身失败仍 fence。
非单消息的 owner-open/requeue activation 路径保留原失败关闭，不能借内部局部证明豁免
此前已经发生的元数据或多项恢复写入；A3 继续审计这些恢复边界。

HeadPlanReadStatistics 提供真实返回记录/字节、成功计费字节、拒绝读取和连续 elapsed 次数。
连续 elapsed 耗尽在第 3 次及后续 2 的幂次记录 warning，成功或其他耗尽原因重置该计数。
legacy Profile 依赖调用前也检查共享 deadline；已经开始的 native/external 调用不能被预算中断。

**尚未闭合的资源配置条件：** 新 full constructor 可以显式提供有限 HeadReadPolicy；
旧构造器为兼容性保留 `HeadReadPolicy.compatibility()`，不是已认证的生产默认容量。
仅检查正数不构成“最大合法单消息 plan 可装入”的证明。必须继续冻结并验证 Route/Profile/
Message/legacy inflight 的最大依赖 bytes/records 与正式激活配置，接入统一 Worker envelope，
再清退生产入口的兼容无耗尽配置。B1–B5 的设计可按实施计划在 A 期间推进，作为该证明
所需的前置契约。此条件未完成前 A2 仍为 IN_PROGRESS，不授予 P0 或整方案完成状态。


## B1 物理身份与 key codec

`CanonicalTargetPartition` 通过闭合 BrokerResourceIdentity + uint32 partition 定义
canonical bytes；从旧 Lane 提取前验证全部 tuple。TargetPartitionId 使用独立 nominal
type/hash 域。最大 UTF-8 输入和完整 canonical bytes 都有显式上限；该局部上限不能
替代 A2 所需的完整 Message/Lane/legacy 读取成本证明。

`TargetKeyCodec` 预留普通 DUE、按 deliverAt 的 Native、独立 Expiry 和 Target state key；
slot/generation 位于时间之前，单域到多域沿用一个格式。候选 decoder 关闭未知 tag、
format、token kind/length、零 domain generation、负时间以及损坏 Message ID。
精确布局、format 2 的旧 reader 拒绝要求和固定向量见 [B1 契约](05-Target身份与索引契约.md)。
生产 writer 尚未使用这些 key；queue/domain/head/work/locator 与 ORDER_STATE 的编码见
后续小节，B2–B4 ref、C1 mutation 及 C1/B6/F1 激活/转换仍由对应切片闭合。


### B1 TargetQueueState、域/head 与独立物理 identity

`TargetHeadRef` 校验选择 key、时间、Message/generation 和 digest；ordinary 可以引用
DUE 或 ORDER_HEAD，native 只能引用 NATIVE。`TargetDomainState` 固定 refs 的 presence
及角色，VACANT 保留 generation。`TargetQueueState` 固定控制字段、计费 incarnation、
lead cap、连续 slot 历史和整体 digest，提供 source/key/identity/已激活域数的完整读取
边界，以及不跳版本、不回绕、不重写 bound scope 的结构后继检查。

不可变物理 tuple 单独存 TARGET_IDENTITY，普通 head 变更只重写小型 state。按具体
编码公式，head/domain/state 的保守字节上限为 214/587/37883；64-slot 最大宽度向量
实测 canonical=37626。reader 不把该局部 proof 当作完整 Message/head budget。

`TargetKeyCodec` 加入 ORDERED/ORDER_HEAD/ORDER_STATE 和独立 identity key；ORDERED
按 deliverAt，ORDER_HEAD 按本域可服务 head 的 eligibility。NV type 12/13 仍只是格式 2
预留，活动 Lane reader 继续拒绝。B1 的身份/存储验收与后续 reference/activation 分工见字段契约 §19，
状态转换的结构检查不替代 source Owner 和旧义务排空证明。


### B1 Message 定位与完整 Target work

`TargetMessageLocator` 嵌入新 Message/current work，固定 Message/generation、Target、
slot/generation、accounting incarnation、可选 ordering domain 和 Schedule binding digest。
它不创建额外 locator key，完整 binding/ref 对象和授权检查继续由 B2/C1 闭合。

`TargetTimelineWorkRef` 保留 initial/definitive/uncertain work、attempt、runtime revision
以及 UNKNOWN 控制依据，普通/Native 两路 value 共享同一 work bytes。DUE 使用
max(deliverAt,retryEligibility)，Native 永久按 deliverAt；FIFO 的 ORDERED 保留
业务时间，只有允许服务的 ORDER_HEAD 才按 eligibility 暴露。semantic digest 排除
runtime revision，instance digest 包含它；新槽位、计费、binding 或授权会改变 semantic。

跨记录校验覆盖 Message、queue/domain、真实物理 Target、source Shard/order，以及
Control retry 的完整同资源且晚于 Schedule 的 source。Native 要求初次 best-effort、
Pulsar 资源和域 policy scope；实时 Owner/policy、完整 binding 和 obligation gate 仍需
C1 接通，不能用这些 codec 提供首次发送权。

`TargetSourcePosition` 保留完整已注册 bytes，加入 Kafka cluster=256 UTF-8 bytes 与
Pulsar topic=1MiB 的新格式边界；source canonical 上限分别为 318/1048670。locator
和 work 保守上限为 222/1049113，独立最大 work 向量实际 1049075 bytes。超限旧 source
在受控转换时必须列为冲突，不改变活动旧 reader 或缩短资源身份使其通过。NV type 14
仅预留；Message/runtime 与 Expiry 编码见下节，ORDER_STATE 见后续小节，格式激活仍待 C1/B6/F1。


### B1 完整 Message/runtime 与稳定 Expiry

`TargetGenerationRuntimeIndex` 保留 current work oneof、累计 Admission、duplicate 标记及
原 AttemptObligationRef。新格式最多 1024 个 refs，严格唯一排序并核对 generation、key
内 ID/长度；不会把终态等同于清空义务。非终态只能有一个与 current publisher 对应的
PUBLISHING ref，任何 UNCERTAIN ref 均使非终态聚合保持 UNCERTAIN。

`TargetMessageRecord` 以该 runtime 为单一聚合状态来源，携带 locator、状态 revision、
业务/重试/过期时间、Native permission、完整 Schedule source 和 payload oneof。
inline 最多 16MiB；对象引用保留 committed PayloadReference 原 bytes 和 proof 身份，
四个变长身份字段各最多 1MiB。`PayloadReference.maximumIdentityComponentBytes` 不复制
字段即可检查边界，旧 reader/encoding 行为未改变。

`TargetExpiryRef` 只绑定 locator 与 expireAt，Claim/retry 不导致重复刷新；终态移除
可过期索引仍不清除 attempt。新增 id tag 05 TARGET_MESSAGE 和 NV type 15/16 均为
format 2 预留，活动 reader/writer 不切换。完整 Message/runtime/Expiry 的保守上限
为 19040258/1214052/272 bytes；独立最大 Message 向量实际 19040181 bytes。

跨记录 helper 验证 exact key、source Shard、generation、全部 timeline work 和当前
非终态 Expiry。实际 source/Owner/binding/Target/Claim/Admission 及义务增删 gate
仍待 C1，1024-ref 容量须在不可逆 Admission 之前兑现，超限旧数据需 B6/F1 冲突处理。

### B1 ORDER_STATE 与轻量 barrier

`TargetOrderState` 固定单个 strict domain 的 source Shard、slot/generation、accounting
incarnation、排序契约、revision/control/gate、水位与互斥的 serviceableHead/barrier。
`TargetOrderBarrier` 只引用精确 locator、完整 ORDERED key 与 runtime revision/digest，
不重复保存 attempt ledger。CLAIMED/PUBLISHING、UNCERTAIN 与终态未决 refs 继续阻止
后继。Store helper 拒绝错 Shard、不同计费 incarnation、VACANT/重用槽位；跨记录 helper
拒绝 stale runtime 和伪造可服务 head。OPEN 是结构条件，不能替代实时 Target/域控制。

ORDER_HEAD 仍使用 NV 14 的完整 work；业务时间排序与 retry eligibility 分离，Barrier
存在时不暴露任何 head。NV 17 保留 ORDER_STATE；777/447-byte 保守上限及 774-byte
最大 state 向量由独立 Python 生成器与 Java 检验。新 `checkTargetIdentityVectors` 纳入
常规 `check`，只验证向量，不重写它们，也不激活格式。

排序 revision 1 保留旧 strict 语义；revision 2 的 Admission watermark 只能显式绑定，
普通 successor 不允许切约、丢水位或无符号后退。真正 Admission/释放由 C1/E5 同 batch
接入，迟到拒绝和 replay 由 B5 定义、B6/F1 处理旧数据切点。B1 验收不等待其后续切片
先实现，但 B7 与最终完整交付仍须覆盖这些义务。


### B2 执行/控制引用与有界注册规划

`TargetDispatchCompatibility` 将 destination/capability Profile 归一化为目标、授权范围、
encoding、完整能力与 Broker 生命周期要求，排除 Profile identity/version 等无关参数。
完整内容的 equals/digest 与 offered.canServe(required) 分开：固定通道可以承载较弱
retention/timing 要求，但不切换 outcome、evidence/recovery 身份或提升权限。

`TargetControlScope` 保存 source Shard/Target 下全部额外 control/permit group，均有
32 个条目上限与严格排序。独立 Pause/credential availability/发送 permit 使 scope
不同；DTO 本身不能证明没有被省略的 gate。两对象 reserved NV 18/19 和 meta 0c/0d
引用的字段/长度/完整性要求见 [B2 契约](06-执行与控制兼容契约.md)。

## Message mutation 与实际队头维护

TargetMessageStore 的 Input 包含有界 Message before/after、严格 OrderTransition 和
额外业务 records。Message ID 必须一致、stateVersion 精确 +1、generation 不跳号/
回绕；物理删除至少须终态且无未决 attempts，真正 Floor/retention/引用删除权威仍
由 CommitAuthority 持有。初始/迁移/业务 source 语义不由投影结构规则替代。

组件读取并比较完整原 Message/Expiry/ordinary/native/ORDERED bytes，自动生成新
投影；非终态有稳定 Expiry，终态删除 Expiry；当前 work 两个 sibling 一起变更。每条变更中的 timeline work 都验证实际
Target identity/queue/domain/accounting routing，不只核对最终选中的 head。
extra 不得覆盖它管理的 Message/TIMELINE/ORDER_STATE。严格 Message 变化必须带
对应 ordering domain transition；order before 精确匹配，旧 serviceable head 必须
是原 ORDERED 最小项。新 head 按 gate/barrier 和 overlay 重算，并核对完整 Message
runtime/attempt 及真实 ORDERED work；barrier 绑定的 Message 必须精确匹配。

Reader.first 在一个 bounded Store plan 内合并固定范围与 exact overlay。最多读取
范围内 touched keys 数 + 1 条持久 entry，选第一个未被替换/删除的项，再与 overlay
最小 put 比较。INCOMPLETE 传播为 ReadIncompleteException，不解释为无队头。

TargetQueueHeadUpdater 对受影响 domain 先验证原 due/native/strict 最小项与原
queue heads，再用 overlay 更新。新 domain 若已有孤立候选即拒绝；slot generation、
physical identity、Message、普通/native sibling、strict state 都在同视图核对。
每个受影响 Target 只产生一次 headRevision +1 和一次 queue write；不改进程公平性。
普通 due 与 strict serviceable 先按 eligible time 比较，同 time 按完整 key 决胜；
Native 保留独立最小项。此跨类选择不改变各 strict orderingDomain 内的 FIFO 顺序。

最终完整生成写集交给 AccountingPlanner，随后交给 TargetStoreBackend.prepare/
commit。计费 planner 必须从原 owner 与完整 records 推导费用；CommitAuthority 必须
保持实际 source/Owner/Store/Route/grant/业务语义到 native commit。当前未装配真实

## 实际记录计费与 source/local 装配

独立计算。共享 immutable metadata 保留首次 allocation，channel/native records
按其 incarnation 解析。结果检查完整首次引用；Claim projection/attempt budget
使用原 execution/commitment/allocated 与原 artifact。mirror 只复制资源，不复制
Target/domain/incarnation cardinality；未知类型直接失败，无零费用 fallback。

SourceAccounting 从完整业务 Edit 双视图分别重建 removed/added，计算每个实际
counter 的 prior - removed + added，交已有 Delta/Total planner。它点读当前 root

重复计费。没有 inventory 变化时 root 原 bytes 保持不变；零 counter/total 继续保留。

重复或伪造 before、同 key 改冻结 owner、重写不可变结果均拒绝。

TargetMessageStore 增加 AccountingAssembler：它收到自动生成的完整 Message/
index/order/queue 写集后可以追加 bookkeeping，返回同一批次的完整 Mutation。

accounting，不能配置空 updates 或 no-op authority 作为生产实现。Assembler 返回的
写集必须逐字节保留所有生成投影，只允许额外追加精确 root bookkeeping key；不能
删除、更改生成的 Message/index/head 或夹带新的未投影业务写。

和 bookkeeping，恰好创建或删除一个不可变 Claim charge，不分配任何新 counter。
它只接受 Message/work/Expiry/queue/order/Claim-charge 家族，最多原有四个 counter，
由已有 prepareLocalClaim 校验维度/cardinality/正负 execution 变化；本地 ordinal

revoke/admission 边界仍须 LocalClaimAuthority 和 CommitGuard 贯穿实际提交。

这些计费器计算实际数额，不提供签名或业务决策权威，也不代替物理资源准入、完整
账本恢复/retention/grant 激活审计。source 控制、持久业务 Claim/outbox、完整运行
factory 仍须继续实现。Local 计费本轮仅编译，所有场景移交集中验证。

ClaimId[32] 可由 runtime.claimId 直接点查，避免依赖已退出 Owner epoch 扫描。quota

证明。Prepared 绑定 wrapper/backend/ReadView，一次提交；返回检查对象不是发送许可。

## System physical replay 与 grant source 分流

TargetSystemReplayStore 在有界 Store view 内点查原 SYSTEM 和本 physical POSITION，

batch；不修改 activation/descriptor 或重复运行 grant prior/CAS/capacity verifier。

### 2026-09-23 NV40 OPEN 空 Target 的本地 reopen 续跑

四组场景另在原 Store 创建第三 Target：实际 grant writer、source-accounted 物理身份与 OPEN queue、签名 Close writer 留下 NV39 与 OPEN NV40。关闭原 RocksDB 后，新 backend/ClosureStore 的受保护范围扫描读到两个 COMPLETE 和一个 OPEN；新 GC executor 从起点跳过完成项，并对 OPEN 空索引执行 field7 本地完成，同批写 NV40、两 counter、total、aggregate 共 5 条 native 记录。Source sequence/position 均不变。该证据只覆盖同一 root/lineage 的本地空 Target 续跑，尚未验证真实 Owner lease 接管、活跃 reservation 恢复、native UNKNOWN 或 Broker 恢复。

### 2026-09-23 持久 root anchor 的受保护重开

`TargetStoreBootstrap.reopen` 在首次读之前获取 ReadAuthority，使用同一 `BoundedReadBudget` 和 Store ReadView 点读固定 Shard NV31 bookkeeping anchor、其指向的 NV33 incarnation、当前 aggregate 与 source META3/5。必须满足 Shard/tenant、root identity/accounting、aggregate incarnation/最新 source frontier 和 root/bookkeeping mutation 先后关系；交付重建结果前再次检查 ReadView 与权限。`TargetSourceApplyRuntime` 可用此结果构造实际 source store，而不是要求调用者保存首次 bootstrap 对象。它仅建立当前本地 root/backend，既不完成全账本 fold，也不替代 Owner epoch/lease、checkpoint、历史注册或受控迁移验证。

### 2026-09-23 Close GC 的 Owner/Store guard

`TargetSourceApplyRuntime.newCloseGcExecutor` 只接受自身 source loop 已绑定的 WorkClass registry，固定此实例的 backend、Shard scope、lineage、domain bound 与 source ReadAuthority。任务接纳和执行时的本地 eligibility 读取当前 lease；读写 guard 在外部权限检查前后重验同一 Owner 身份、有效时间、Store 打开 epoch 与精确 Store/scope，失权会 fence 原 source runtime。写 authority 只接受 reservation Close、expiry 或 Close cursor 的本地 mutation；配额仍由各独立 authority 校验。此 factory 只装配同一 Owner 的 GC 单步权限，不自行提供周期触发或声称恢复/外部权限认证。

### 2026-09-23 Close/expiry 有界维护 turn

`TargetSourceApplyRuntime.newExpiryGcExecutor` 以同一 Owner/Store guard 装配普通 expiry 扫描，并只接受 reservationExpiry 本地 mutation。`newReservationGcRuntime` 对每个 source runtime 只绑定一次，组合 Close/expiry 两个 executor。`runTurn` 在共享 WorkClass 图中每次最多新排一个任务，以 Owner epoch 与递增 uint64 序号组成 16 字节请求 ID；只有所选任务产生结果后才切换 Close/expiry，预算未选中时保留原 submission 与身份。新 Owner 重新创建 runtime，从 NV40 与 expiry 索引起点恢复扫描。调用方必须提供持续 tick 与足够任务字节预算；当前无生产 timer、跨 Shard 公平性界限或完整恢复认证。

`TargetWorkerShardRuntime` 将一个已激活 Target source runtime、它的精确 Store、共享资源、source consumer 和 Close/expiry 权限装配为单 Shard Worker 调用入口。先核对 Store/资源实例，再绑定同一 WorkClass registry 的 source loop 与一次性 GC；两个 turn 先查资源 admission gate，随后各走已有 source ACK 或 GC Owner/Store 权限检查。它不持有 Owner drain/周期调度权，关闭 source 时仍须先由 host 处理 pending ACK 和 Owner 生命周期。

`TargetWorkerShardFleetRuntime` 只接纳同一 Worker registry/资源 envelope 的唯一 ShardId 集合，并用独立 source/GC 游标选下一 Shard。游标在执行前移动，维护异常保留 cause 并附上本轮 Shard 身份，下一次调用仍轮到后续 Shard；每个 Shard 的待执行 GC submission 仍由其自己的 `TargetReservationGcRuntime` 保存。宿主必须启动维护循环并处理失权 Shard 的 Owner drain，fleet 不隐含 timer 或接管授权。

Target fleet 的维护异常现封装为携带 `selectedShardId` 的 `MaintenanceDispatchFailure`；该身份只表示本轮选择，不证明共享 WorkClass dispatcher 中哪一项 action 失败。`TargetWorkerMaintenanceLoop` 用正数固定间隔和有限 `SchedulerBudget` 单线程调用 fleet，每轮在独立锁内执行，普通失败及失败回调异常均被记录且不抑制下一 tick；fatal Error 报告后仍向调度器传播。`close` 取消后续任务且在不打断当前 Store action 的前提下等待在途 turn 锁释放；宿主须在 Owner drain 前关闭循环，当前尚无统一启动宿主。
