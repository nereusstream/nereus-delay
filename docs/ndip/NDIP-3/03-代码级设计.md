# NDIP-3 代码级设计

Status: Draft

## A0：当前调用者清单

`DelayShard.readyProjections` 是单消息 mutation 的投影汇合点，涵盖 Schedule、Cancel、
Reschedule、Claim/revoke、retry、Admission、Outcome、终态与受控恢复。prior/next 跨 Lane
必须共同计算；当前 command API 不扩为 batch API。

`findLaneCandidate` 的直接调用者：`readyProjections`、source-ordered Lane 控制（kind 9）、
Lane activation/control helpers、Lane retire 前的非空检查、`rebuildReadyIndexes`。
`findLaneNativeCandidate` 的直接调用者：`readyProjections`、`projectLane` 的便捷重载、
`rebuildReadyIndexes`。`projectLane` 从 mutation、控制、激活和 rebuild 进入。
精确方法名/计量与逐个完整审计义务在 A0/A3 源码核对后补齐。

DUE 使用现有 eligibleAt，ORDERED 使用 deliverAt，NATIVE 使用 candidateAt；同时间使用
完整 key 的 unsigned 字节顺序。A 不改变 Lane ID、消息 schema、prepared bytes 或发送身份。

## A1/A2：计划和提交

小型 head helper 使用 exact removed/overwritten keys 与 inserted entries。每前缀的
首个非排除持久项严格验证后与局部新增最小项合并。健康单消息最多读两个候选。
FOUND / EMPTY_CONFIRMED / INCOMPLETE 必须可区分；插入项不能掩盖未完成的持久读取。
预算贯穿全部前缀、Message/binding 依赖以及 READY tail/wrap。任何必要分支未完成时
不写 Message、head、quota、结果或 applied source position；不创建 Producer authority。

同一 plan 在 Shard 串行 turn 内绑定 Owner/Store/source/mutation view；成功 WriteBatch 后
才发布内存状态，未知写结果使用现有 Store fencing。全前缀审计移到显式恢复/审计路径。

## 后续契约

B1–B6 将完整设计中的 Target identity、最终 key layout、共同 policy 签名域、K 个真实
执行域、局部 quota revision、增量 aggregate、恢复公平性、ordering contract、观测模式、
资源预算与迁移 replay 冻结成精确字段/状态/向量；未冻结内容仍属 PLANNED。
C–F 必须逐项替换为真实实现路径和结果，不能仅把旧 Lane 类型改名。

## A1 已实现的取头与审计分离

`HeadIndexUpdater.firstStored` 在短生命周期 iterator 内逐项访问，遇到首个非 exact removed
key 即停；未受 A2 预算限制的本切片仍沿用无耗尽的读取配置，因此它不将部分读取解释为空。
DUE/ORDERED 使用 prior SCHEDULED 的完整 `timelineKey`；NATIVE 使用 prior 的完整
`nativeCandidateKey`。CLAIMED 本身不伪装为仍存在的 timeline key。跨 Lane 的 prior/next
仍由一次 readyProjections 和原有业务 WriteBatch 处理。

调用方严格解码选中 key/value/Message，再按原 comparator 与 included candidate 取最小。
明确删除的 key 不需要为找 successor 再解码 Message。`auditLaneCandidateIndexes` 在
`rebuildReadyIndexes` 和正式 `activateLaneReadiness` 中保留全前缀完整性/容量检查；
正常 mutation 不再附带队尾审计。A3 仍需完成有界审计/写失败和恢复专项。

测试增加 `exactOverlayReadsAtMostDeletedKeysPlusOneAtEveryBacklogSize`、
`emptyAndDeletedOnlyPrefixesDoNotReadTheAdjacentNamespace`、
`unrelatedMutationDoesNotAuditTailButRebuildAndSelectedCorruptionFailClosed`。
随机 mutation/Claim 回归继续使用独立全扫 oracle。

## A2 READY discovery 已接通（切片仍未完成）

`PersistentLaneScheduler` 逐项调用 `visitResult`，在同一 `BoundedReadBudget` 内完成
READY、两次 Lane 验证、Message、timeline 及可选 native Message/timeline/binding 读取。
`SchedulerBudget.maxMessages` 仍表示逻辑 head 数；物理记录上限由当前最大依赖路径
`8 × maxMessages` 派生并限制到 Integer.MAX_VALUE，全部实际 key/value 字节共用原 byte cap。
普通投影读取 5 条，含 native 验证时 7 条，加 binding 时最多 8 条。此为应用读取计数，
不是 RocksDB 块 I/O、解码复制内存或外部 policy RPC 的物理资源认证。

尾部使用 `lastScannedReadyKey + 0x00` 作为 exact cursor 的独占后继，避免为跳过 cursor
先多读一条。只有 tail 的 RANGE_END 已被证明后才尝试 wrap；两个区间没有重置额度。
只有完整校验的投影进入临时列表。依赖耗尽时丢弃当前未完成投影，保留此前完整投影；
尚无完整投影时不发布队列、不写 scheduler META，也不推进 cursor。完整 tail 后的未完成
wrap 不增加 wrap generation；完整但尚未到期的 wrapped native 投影也不推进到期 cursor。
两个区间均已证明结束后，可点查原 cursor，保留 singleton/live policy refresh 语义。

Store 读取计划绑定的 ReadView 在 `withReadView` 内再次校验，并持锁发布进程状态；
fairness batch 也要求同一 ReadView。native policy callback 在 Store monitor 之外执行，
避免外部 authority/source-position callback 与 Shard→Store 顺序形成倒置；每次发起前
仍检查同一 elapsed deadline。回调期间若 Store view 改变，整个发布步骤失败并恢复本地状态。
预算只能阻止下一次动作发起，不能中断已经进入的 native read 或外部调用。

`discoveryReadStatistics` 暴露最近一次实际 records/bytes、成功计费字节、拒绝的 Store read
次数及首个耗尽原因。READY 点查也计入 Store 的 READY probe。visitor 内的依赖 get 耗尽
转换为显式 INCOMPLETE 后仍检查 iterator.status；原生 I/O error 不被预算让出掩盖。

本 discovery 批次自身不证明 Source Apply/head mutation 的预算链，也不将旧 4 KiB fixture 视为
最大合法资源认证。Claim handoff 回归按实际 READY + 两次 Lane + Message + timeline
字节构造完整读取预算并核对计量；最大合法 mutation envelope 和正式激活配置仍待闭合。


## A2 HeadPlan 和 source/Claim/recovery 接通

`DelayShard.readHeadPlan` 持有 Shard→Store 顺序，使用一个 `HeadReadPolicy` 派生的
BoundedReadBudget 计算整个消息 delta 的所有 Lane 与 DUE/ORDERED/NATIVE 分支。
所选候选的 Message、legacy binding/Claim/Admission 依赖通过同一个 Store 读取 scope
计费。旧 `firstStored` 仅保留为组件兼容 helper；writer 调用三态 `HeadIndexUpdater.read`，
INCOMPLETE 不与 inserted candidate 合并，也不写任何业务投影。

每个完成 plan 带有 Store/Owner ReadView、mutationSequence 与 applied source position。
`LaneProjection` 必须携带该 binding；`writeReadyProjections` 在同一 Store monitor 内
验证全部投影后才开始构造业务 WriteBatch，`putReadyProjection` 在 batch 中再核对。
未绑定或陈旧投影不能开始业务 batch。单 Lane 控制、readiness/activation helper、retire no-work 证明和逐 Lane
fenced rebuild 也使用这个读取入口。恢复仍保留单独的全尾部审计，未把局部 head 求值
当作完整 audit；rebuild 的多 Lane 投影必须在同一未变化的 Store 上一起提交。

`runReadRetryableMutation` 在整个 command/system mutation 或严格 Claim 前捕获 Store view，
发生预算耗尽时验证从入口起没有 Store 写入、mutation/source 变化，才创建专用的
`HeadReadIncompleteException`。外层 mutation 已有写入时，即使内层提供局部只读证明也
不能改称整个外层可重试。未知 native write 仍走既有 Store/Owner fencing。

SourceApplyCoordinator 的 READ_INCOMPLETE 保留 exact entry，清除已完成的 submission，
不 ACK、不推进 source cursor、不写客户端拒绝结果；下一 turn 重新提交并核对当前 Owner。
OwnerRecoveryCoordinator 保留 pending entry 和 CATCHING_UP，返回独立 readIncompleteReason，
再调度时重建 submission；只有该条记录的结果和 cursor advance 完成后才考虑激活。
其他 work-class 的失败不能被同一轮的 head read yield 掩盖成普通 retry。

严格 Claim 在 proven read yield 后释放 permit、重新排入 exact polled head，并返回本地
READ_INCOMPLETE；没有 Claim/source 业务提交或 Producer authority。该回排只核对 READY
键仍存在并恢复进程内队列/fairness 状态，不写公平性 META；Claim/source 业务写仍只在
严格 Claim 成功路径提交。permit release/回排自身失败仍 fence。
非单消息的 owner-open/requeue activation 路径保留原失败关闭，不能借内部局部证明豁免
此前已经发生的元数据或多项恢复写入；A3 继续审计这些恢复边界。

HeadPlanReadStatistics 提供真实返回记录/字节、成功计费字节、拒绝读取和连续 elapsed 次数。
连续 elapsed 耗尽在第 3 次及后续 2 的幂次记录 warning，成功或其他耗尽原因重置该计数。
legacy Profile 依赖调用前也检查共享 deadline；已经开始的 native/external 调用不能被预算中断。

**尚未闭合的资源配置条件：** 新 full constructor 可以显式提供有限 HeadReadPolicy；
旧构造器为兼容性保留 `HeadReadPolicy.compatibility()`，不是已认证的生产默认容量。
仅检查正数不构成“最大合法单消息 plan 可装入”的证明。必须继续冻结并验证 Route/Profile/
Message/legacy inflight 的最大依赖 bytes/records 与正式激活配置，接入统一 Worker envelope。
兼容 `actionAtFromOpenAdmission` 会扫描并完整解码 open `PublishAttemptLedger`，其 admission、
outcome、evidence 和 source-position bytes 也必须纳入该 envelope；有界的 ledger 数量不代表
单条或总 value bytes 有界。之后再清退生产入口的兼容无耗尽配置，
B1–B5 的设计可按实施计划在 A 期间推进，作为该证明所需的前置契约。此条件未完成前 A2 仍为 IN_PROGRESS，不授予 P0 或整方案完成状态。

### A2 有限字节预算的 iterator key 长度预检（2026-10-06）

有限 byte budget 下，`ShardStore.visitResult` 现在先用固定两字节复用缓冲区调用
RocksJava `RocksIterator.key(byte[])`，取得完整逻辑 key 长度并保留 READY probe 所需的前缀；
与单字节 value 长度预检一起记入共享预算。只有 key/value 长度都装入剩余额度，才申请完整
Java key/value 数组。累计额度不足的下一行不会完整物化。RocksDB 回归覆盖已读取一条 2-byte
key/30-byte value 后，32-byte key/1-byte value 在 50-byte 总预算下被拒绝；首行保持可见，
拒绝项计入 actualBytes 而不计入 chargedBytes。

该边界只减少超预算条目的 Java 数组分配，不限制 RocksDB 原生 key 访问、索引/块读取或
visitor/projection 后续分配；单 mutation 最大 envelope、legacy 字段边界和生产有限 policy
仍未闭合，A2 继续 IN_PROGRESS。


## B1 物理身份与 key codec

`CanonicalTargetPartition` 通过闭合 BrokerResourceIdentity + uint32 partition 定义
canonical bytes；从旧 Lane 提取前验证全部 tuple。TargetPartitionId 使用独立 nominal
type/hash 域。最大 UTF-8 输入和完整 canonical bytes 都有显式上限；该局部上限不能
替代 A2 所需的完整 Message/Lane/legacy 读取成本证明。

`TargetKeyCodec` 预留普通 DUE、按 deliverAt 的 Native、独立 Expiry 和 Target state key；
slot/generation 位于时间之前，单域到多域沿用一个格式。候选 decoder 关闭未知 tag、
format、token kind/length、零 domain generation、负时间以及损坏 Message ID。
精确布局、format 2 的旧 reader 拒绝要求和固定向量见 [B1 契约](05-Target身份与索引契约.md)。
生产 writer 尚未使用这些 key；queue/domain/head/work/locator 与 ORDER_STATE 的编码见
后续小节，B2–B4 ref、C1 mutation 及 C1/B6/F1 激活/转换仍由对应切片闭合。


### B1 TargetQueueState、域/head 与独立物理 identity

`TargetHeadRef` 校验选择 key、时间、Message/generation 和 digest；ordinary 可以引用
DUE 或 ORDER_HEAD，native 只能引用 NATIVE。`TargetDomainState` 固定 refs 的 presence
及角色，VACANT 保留 generation。`TargetQueueState` 固定控制字段、计费 incarnation、
lead cap、连续 slot 历史和整体 digest，提供 source/key/identity/已激活域数的完整读取
边界，以及不跳版本、不回绕、不重写 bound scope 的结构后继检查。

不可变物理 tuple 单独存 TARGET_IDENTITY，普通 head 变更只重写小型 state。按具体
编码公式，head/domain/state 的保守字节上限为 214/587/37883；64-slot 最大宽度向量
实测 canonical=37626。reader 不把该局部 proof 当作完整 Message/head budget。

`TargetKeyCodec` 加入 ORDERED/ORDER_HEAD/ORDER_STATE 和独立 identity key；ORDERED
按 deliverAt，ORDER_HEAD 按本域可服务 head 的 eligibility。NV type 12/13 仍只是格式 2
预留，活动 Lane reader 继续拒绝。B1 的身份/存储验收与后续 reference/activation 分工见字段契约 §19，
状态转换的结构检查不替代 source Owner 和旧义务排空证明。


### B1 Message 定位与完整 Target work

`TargetMessageLocator` 嵌入新 Message/current work，固定 Message/generation、Target、
slot/generation、accounting incarnation、可选 ordering domain 和 Schedule binding digest。
它不创建额外 locator key，完整 binding/ref 对象和授权检查继续由 B2/C1 闭合。

`TargetTimelineWorkRef` 保留 initial/definitive/uncertain work、attempt、runtime revision
以及 UNKNOWN 控制依据，普通/Native 两路 value 共享同一 work bytes。DUE 使用
max(deliverAt,retryEligibility)，Native 永久按 deliverAt；FIFO 的 ORDERED 保留
业务时间，只有允许服务的 ORDER_HEAD 才按 eligibility 暴露。semantic digest 排除
runtime revision，instance digest 包含它；新槽位、计费、binding 或授权会改变 semantic。

跨记录校验覆盖 Message、queue/domain、真实物理 Target、source Shard/order，以及
Control retry 的完整同资源且晚于 Schedule 的 source。Native 要求初次 best-effort、
Pulsar 资源和域 policy scope；实时 Owner/policy、完整 binding 和 obligation gate 仍需
C1 接通，不能用这些 codec 提供首次发送权。

`TargetSourcePosition` 保留完整已注册 bytes，加入 Kafka cluster=256 UTF-8 bytes 与
Pulsar topic=1MiB 的新格式边界；source canonical 上限分别为 318/1048670。locator
和 work 保守上限为 222/1049113，独立最大 work 向量实际 1049075 bytes。超限旧 source
在受控转换时必须列为冲突，不改变活动旧 reader 或缩短资源身份使其通过。NV type 14
仅预留；Message/runtime 与 Expiry 编码见下节，ORDER_STATE 见后续小节，格式激活仍待 C1/B6/F1。


### B1 完整 Message/runtime 与稳定 Expiry

`TargetGenerationRuntimeIndex` 保留 current work oneof、累计 Admission、duplicate 标记及
原 AttemptObligationRef。新格式最多 1024 个 refs，严格唯一排序并核对 generation、key
内 ID/长度；不会把终态等同于清空义务。非终态只能有一个与 current publisher 对应的
PUBLISHING ref，任何 UNCERTAIN ref 均使非终态聚合保持 UNCERTAIN。

`TargetMessageRecord` 以该 runtime 为单一聚合状态来源，携带 locator、状态 revision、
业务/重试/过期时间、Native permission、完整 Schedule source 和 payload oneof。
inline 最多 16MiB；对象引用保留 committed PayloadReference 原 bytes 和 proof 身份，
四个变长身份字段各最多 1MiB。`PayloadReference.maximumIdentityComponentBytes` 不复制
字段即可检查边界，旧 reader/encoding 行为未改变。

`TargetExpiryRef` 只绑定 locator 与 expireAt，Claim/retry 不导致重复刷新；终态移除
可过期索引仍不清除 attempt。新增 id tag 05 TARGET_MESSAGE 和 NV type 15/16 均为
format 2 预留，活动 reader/writer 不切换。完整 Message/runtime/Expiry 的保守上限
为 19040258/1214052/272 bytes；独立最大 Message 向量实际 19040181 bytes。

跨记录 helper 验证 exact key、source Shard、generation、全部 timeline work 和当前
非终态 Expiry。实际 source/Owner/binding/Target/Claim/Admission 及义务增删 gate
仍待 C1，1024-ref 容量须在不可逆 Admission 之前兑现，超限旧数据需 B6/F1 冲突处理。

### B1 ORDER_STATE 与轻量 barrier

`TargetOrderState` 固定单个 strict domain 的 source Shard、slot/generation、accounting
incarnation、排序契约、revision/control/gate、水位与互斥的 serviceableHead/barrier。
`TargetOrderBarrier` 只引用精确 locator、完整 ORDERED key 与 runtime revision/digest，
不重复保存 attempt ledger。CLAIMED/PUBLISHING、UNCERTAIN 与终态未决 refs 继续阻止
后继。Store helper 拒绝错 Shard、不同计费 incarnation、VACANT/重用槽位；跨记录 helper
拒绝 stale runtime 和伪造可服务 head。OPEN 是结构条件，不能替代实时 Target/域控制。

ORDER_HEAD 仍使用 NV 14 的完整 work；业务时间排序与 retry eligibility 分离，Barrier
存在时不暴露任何 head。NV 17 保留 ORDER_STATE；777/447-byte 保守上限及 774-byte
最大 state 向量由独立 Python 生成器与 Java 检验。新 `checkTargetIdentityVectors` 纳入
常规 `check`，只验证向量，不重写它们，也不激活格式。

## Message mutation 与实际队头维护

TargetMessageStore 的 Input 包含有界 Message before/after、严格 OrderTransition 和
额外业务 records。Message ID 必须一致、stateVersion 精确 +1、generation 不跳号/
回绕；物理删除至少须终态且无未决 attempts，真正 Floor/retention/引用删除权威仍
由 CommitAuthority 持有。初始/迁移/业务 source 语义不由投影结构规则替代。

组件读取并比较完整原 Message/Expiry/ordinary/native/ORDERED bytes，自动生成新
投影；非终态有稳定 Expiry，终态删除 Expiry；当前 work 两个 sibling 一起变更。每条变更中的 timeline work 都验证实际
Target identity/queue/domain/accounting routing，不只核对最终选中的 head。
extra 不得覆盖它管理的 Message/TIMELINE/ORDER_STATE。严格 Message 变化必须带
对应 ordering domain transition；order before 精确匹配，旧 serviceable head 必须
是原 ORDERED 最小项。新 head 按 gate/barrier 和 overlay 重算，并核对完整 Message
runtime/attempt 及真实 ORDERED work；barrier 绑定的 Message 必须精确匹配。

Reader.first 在一个 bounded Store plan 内合并固定范围与 exact overlay。最多读取
范围内 touched keys 数 + 1 条持久 entry，选第一个未被替换/删除的项，再与 overlay
最小 put 比较。INCOMPLETE 传播为 ReadIncompleteException，不解释为无队头。

TargetQueueHeadUpdater 对受影响 domain 先验证原 due/native/strict 最小项与原
queue heads，再用 overlay 更新。新 domain 若已有孤立候选即拒绝；slot generation、
physical identity、Message、普通/native sibling、strict state 都在同视图核对。
每个受影响 Target 只产生一次 headRevision +1 和一次 queue write；不改进程公平性。
普通 due 与 strict serviceable 先按 eligible time 比较，同 time 按完整 key 决胜；
Native 保留独立最小项。此跨类选择不改变各 strict orderingDomain 内的 FIFO 顺序。

最终完整生成写集交给 AccountingPlanner，随后交给 TargetStoreBackend.prepare/
commit。计费 planner 必须从原 owner 与完整 records 推导费用；CommitAuthority 必须
保持实际 source/Owner/Store/Route/grant/业务语义到 native commit。当前未装配真实
生产实现，开发 smoke 使用显式 doubles；不会因生成了完整投影就声称 source 或
Claim/Admission/Producer 全路径完成。集中测试清单保留所有相应缺口。


## 实际记录计费与 source/local 装配

TargetRecordAccounting 对指定 before 或 after Store overlay 解码实际 NV record，
每条记录以冻结 META descriptor、payload owner、first allocation/grant、physical
identity 和必要 Message/OrderState 为依赖。依赖同样由实际 Store/overlay 点读并
检查完整 bytes。Message/索引/binding 继承原 payload owner；payload owner 自身
只加一次 record fee + 当前 payload phase；queue/order 的 primary cardinality
独立计算。共享 immutable metadata 保留首次 allocation，channel/native records
按其 incarnation 解析。结果检查完整首次引用；Claim projection/attempt budget
使用原 execution/commitment/allocated 与原 artifact。mirror 只复制资源，不复制
Target/domain/incarnation cardinality；未知类型直接失败，无零费用 fallback。

独立 checkpoint ledger audit 还会把实际 Message 与 Terminal 中的 open attempt refs
关联到 META 中的 `TargetQuotaAttemptBudget`：相同 locator/attempt ID 下，ADMITTED
必须对应 PUBLISHING，UNKNOWN 必须对应 UNCERTAIN；预算缺失、孤儿 open 预算、状态
冲突或已解决预算仍被引用都会拒绝恢复候选。同一 generation 同时有 Terminal 与当前
Message 时，两份 runtime 必须一致；相同 ref 只按一个逻辑 obligation 核对。

SourceAccounting 从完整业务 Edit 双视图分别重建 removed/added，计算每个实际
counter 的 prior - removed + added，交已有 Delta/Total planner。它点读当前 root
bookkeeping 与对应 descriptor，计算实际新增 counter/total 和 grant create/delete
数量；自动追加 bookkeeping 后态并把固定预留费用计入 root primary/mirror。
COUNTER/TOTAL/GRANT_ACTIVATION 固定槽位与 aggregate/root 自身不再按 actual bytes
重复计费。没有 inventory 变化时 root 原 bytes 保持不变；零 counter/total 继续保留。
已有 root counter 缺失/欠费、已有 Target counter 缺 total、非空 source 无 root、
重复或伪造 before、同 key 改冻结 owner、重写不可变结果均拒绝。

TargetMessageStore 增加 AccountingAssembler：它收到自动生成的完整 Message/
index/order/queue 写集后可以追加 bookkeeping，返回同一批次的完整 Mutation。
旧 AccountingPlanner 入口仍可用于组件开发，但生产组合应使用实际 assembled
accounting，不能配置空 updates 或 no-op authority 作为生产实现。Assembler 返回的
写集必须逐字节保留所有生成投影，只允许额外追加精确 root bookkeeping key；不能
删除、更改生成的 Message/index/head 或夹带新的未投影业务写。

TargetLocalClaimAccounting 从同样的记录差集建立局部费用，但必须有已应用 source
和 bookkeeping，恰好创建或删除一个不可变 Claim charge，不分配任何新 counter。
它只接受 Message/work/Expiry/queue/order/Claim-charge 家族，最多原有四个 counter，
由已有 prepareLocalClaim 校验维度/cardinality/正负 execution 变化；本地 ordinal
增加且 source/sequence 不变。完整 actual Claim、原费用、Owner/Store/source 与
revoke/admission 边界仍须 LocalClaimAuthority 和 CommitGuard 贯穿实际提交。

这些计费器计算实际数额，不提供签名或业务决策权威，也不代替物理资源准入、完整
账本恢复/retention/grant 激活审计。source 控制、持久业务 Claim/outbox、完整运行
factory 仍须继续实现。Local 计费本轮仅编译，所有场景移交集中验证。


## 持久 Claim、精确撤销与直接引用

TargetClaimStore.prepareClaim 从实际当前 Message、完整 ScheduleBinding、Target queue
及选中 head 读取。binding 必须匹配 locator/source/queue；slot ACTIVE、queue OPEN，
selected 与对应 ordinary/native head 相同。ordinary 检查到期；native 必须早于 due
且不早于固定 maximum lead；当前有效 native policy、lease/时钟、完整 compatibility、
资源与物化条件由真正 CommitGuard 保持到 native commit，固定 cap 不代替有效 policy。

TargetClaimRecord 保留原 GenerationRuntimeIndex（含原 work/义务/counters）、Message
version/digest、selected head、Owner/Store、sequence/deadline/execution bytes、control
version 和 local creation。Claim ID 由完整上述字段域哈希产生；INFLIGHT 04/01 +
ClaimId[32] 可由 runtime.claimId 直接点查，避免依赖已退出 Owner epoch 扫描。quota
charge 仍使用原 META 1b + Shard/epoch/ClaimId，业务 Claim 的完整 SHA-256 与 charge
互相核对。record 为 NV 36/schema 1；旧 reader 不接受它。

Claim sequence 取当前 aggregate revision 的 checked successor，复用所有 Store
mutation 已持久递增的序号，不写新 fixed counter；不是 source sequence。Claim/revoke
继续在当前 source frontier 增加 local ordinal，不消耗 Admission 或不确定重试次数。
新 Message runtime revision +1/currentWork CLAIMED；严格域同批建立 exact barrier，
不推进 lastAdmittedOrder。计费从实际业务 Claim STATE bytes 与原 execution charge
分别计入，保持镜像、Target total 与 aggregate 同批，禁止只写/删其中一条 Claim。

撤销要求原 Claim 全 bytes、原 Owner/Store、当前 Message 的完整反投影与冻结费用一致。
只恢复原语义 work，runtime revision 再 +1，生成新 instance digest；原 ordinary/native
索引由 MessageStore 恢复，严格 barrier 核对后同批释放，head 重新计算。source 已改变
Message/义务、不同 Owner 或 Store 的情况拒绝本地撤销，必须走另外的 source/recovery
证明。Prepared 绑定 wrapper/backend/ReadView，一次提交；返回检查对象不是发送许可。

当前记录描述可逆 ownership，还不包含物化后 Admission prepared descriptor。真正
Owner/Native/compatibility/物理 permit guard、完整 materialization/Admission/Outcome、
source 消费/Owner takeover 恢复和 Worker 接线仍待实现。未以通用 guard 回调宣称这些
生产边界完成；集中阶段须验证真实 Store 混合写集和全链路。


## 实际 Store grant gate

TargetQuotaStoreGate.wrap 在真实 record assembler 生成完整 Mutation 后读取实际
META17 Shard/Target grant activation。检查操作 scope、业务记录/Target 数上限、
source/local kind、真实 counter/aggregate/total prior、root descriptor/lineage、
activation source/local stamp 以及首次 allocation 的当前完整 descriptor；历史 OPEN
origin 可对应同来源的 DRAINING descriptor，不能换成不同 origin 或恢复 lineage。
已有 Target total 不允许缺 first allocation。普通业务批次禁止修改授权自身的 grant。

纯 TargetQuotaGrantGate 现在用上述实际 activation 和 all-incarnation primary totals
运行。FIRST_SCHEDULE/PREPARE/DLQ_REPLAY 必须提供已接受的实际计量 artifact，两个
grant 都需匹配；任一维增长超过 Shard/Target limit 抛出带准确 scope 的 Rejected。
已有工作使用原 existing-work drain 规则，额度下调不阻止其释放/推进；它仍须原
reserve/Claim/业务 source/物理 permit 的真正授权。所有实际 gate 读取属于 Prepared
的同一 Store ReadView，任何后续 grant 写使旧计划失效，native commit 前再次检查。

TargetMessageStore.prepareGranted/applyGranted 显式组合真实 accounting 与此 gate。
TargetClaimStore 的 CLAIM/REVOKE 入口自动组合 local assembler + gate，调用者不能
在这个 wrapper 上跳过实际 grants。低层 accounted/backend 仍供受控 bootstrap/grant
control 与开发使用；正式运行组合必须选择正确入口，不能配置空 gate/guard。

本组件不从任意操作枚举推断业务权限。源日志去重、签名/Route/operation 分类、
新 ingress 的完整冻结 artifact/可用 incarnation、reject first-result/POSITION 与
source 同批持久化、已接受 activation 的真实认证来源和 physical guard 仍须由完整
source/Worker 组合提供。Rejected 只代表逻辑额度拒绝；缺 activation/descriptor、
损坏/错 scope/source、有限读取耗尽不能降级成业务拒绝，也不能提前推进 source。

## System physical replay 与 grant source 分流

TargetSystemReplayStore 在有界 Store view 内点查原 SYSTEM 和本 physical POSITION，
校验 key/type/full bytes、owner descriptor/tenant/lineage、原 source/aggregate stamps，
并精确匹配 System ID/hash/type/retryUntil/author。source 不能回退；与 frontier 同序
必须包括 metadata 在内完全相等。不存在首记录且位置确实未处理时只返回 first 分支，
真正首次 applier 随后在自己的 view 再验证全部 absence，不把前一次 probe 当提交证明。

同一 physical source 必须存在 POSITION_SYSTEM，sequence 等于当前 source sequence，
完整 envelope SHA-256 等于既有 position mutation digest，并精确引用首次 SYSTEM。
ReadPlan 捕获实际 Store ReadView，completeRead 在明确 ReadAuthority/CommitGuard
内复核该 view，只完成一次、零 batch 写；陈旧/跨 backend/重复完成均拒绝。准备对象
的 inspection 不是 source ACK，grant Dispatch 不在 commit 前暴露业务结果。

后续 physical duplicate 重新读取全部事实，沿用首次 logical result bytes、source、
owner 和 artifact，只为新 POSITION 及其 Shard evidence 费用生成 SourceAccounting
batch；不修改 activation/descriptor 或重复运行 grant prior/CAS/capacity verifier。
probe 与 writer 共用同一个累积 records/bytes/elapsed 预算。两阶段之间分支变化则
失败并要求按最新 view 重新准备，不能把竞争误当首次执行或跳过 source。

过期 duplicate 按收到的位置 timestamp 与原 retryUntil 返回物理级 RETRY_WINDOW
EXPIRED 结果，首次逻辑结果保持原 bytes；POSITION 仍引用原首记录，同位置再放也
不重复收费。对相同位置更换 signature/key-version 导致的 envelope digest 变化拒绝。
原结果的完整 identity/author/hash 已持久固定，重复路径不重新选择业务归属。

TargetQuotaGrantStore.prepare/commit(Dispatch) 已选择 first/replay/later duplicate；
原 prepareFirst 仍是显式首次入口。真实 source-protected writer/Route/Owner/Store
权限及 read/write guard 必须保持到完成；该 Store 分流没有完成 Broker consumer、
root bootstrap、全类型 System/Command appliers、Worker 或跨账本恢复。通用 readonly
planner 仅返回不可变对象，Reader 离开 scope 后不可使用。


## 空 Target Store 的首条 grant 初始化

TargetStoreBootstrap.prepare 接受明确 Shard/tenant、lineage、实际 SourcePosition、
PreparedControlOperation/SystemMutation、原 grant verifier Authority，以及独立
StartAuthority。只接受 prior=null 的 SHARD grant。Root incarnation 由该签名 envelope
SHA-256、source sequence=1、scope、accounting 与 lineage 经原 allocate 规则推导，
不接受外部指定随机 root ID，也不把构造本身作为授权。

Backend.Reader.requireUninitialized 在同一预算和 Store ReadView 下证明整个 Store
为空：default CF 无数据；七个业务 CF 遍历到 RANGE_END，META 仅含 openTarget 写入
的六项精确初始值（format、Store identity、空 evidence cursors、Owner epoch=0、
clean=false、当前 Store 的 OPEN install marker 且无 checkpoint）。任何未知键、
source/counter/grant、Owner/恢复历史、预算耗尽或扫描错误都拒绝；有限最多七项 META
访问即足以终止，不以局部前缀为空代表全库为空。返回后的写入使旧计划失效。

同视图运行现有签名/精确注册/RBAC/scope/route/parent grant verifier，创建 root
NV33、SHARD activation NV30、SYSTEM/POSITION NV35；真实 SourceAccounting 创建
root inventory NV31、两个 primary/mirror counters、aggregate 与 source metadata。
完整 aggregate 的 resources/cardinalities 必须全部落在初始 SHARD grant 内，不能
只付 descriptor 而漏掉 result、root projection 或 activation 槽位。SHARD activation
仍不携带 Target allocation，SYSTEM 也不增加 allocation attachment。

StartAuthority 接收实际 StoreMetadata、root 和完整 Mutation，必须证明新 route 或
经过认证的空 source cut、没有被略过的历史记录/义务及旧 Store/recovery 保护，并覆盖
整个批次的 tenant placement/物理资源。实际 CommitAuthority 必须持有并复核这些
外部快照和 Owner/Control 权威直到 native write 完成。当前该接口没有默认放行 provider，
签名校验、空目录、ACTIVE 指针或本地 root 数据均不能替代这些证明。

Prepared 不暴露 backend/result；commit 成功才产生不可自行构造的 Initialized。
已初始化 Store 不可再次 bootstrap；同源记录改走 TargetQuotaGrantStore 的物理重放。
无效/过期/欠费的首记录或外部权威失败直接使启动失败，零业务写/零 source ACK，不能
先造 root 再持久拒绝、更不能跳过首条记录。UNKNOWN 必须重开并由独立恢复流程核对。
本路径只覆盖受控空态初始化；非空迁移、恢复复用、root rotation/handover、完整 Worker
factory/config 与生产 Start/Commit providers 仍需后续实现，集中验证条件保持原范围。


## Target source WorkClass/Owner/ACK 装配

SourceApplyTarget 是 ownership 包内抽象适配器，旧 OwnedDelayShard 的完整 active 与
recovery 边界经内部 adapter 保留。SourceApplyCoordinator/SourceApplyWorkClassExecutor
继续唯一地管理 WorkClass 任务、单条 native look-ahead、结果缓存、ACK UNKNOWN 和
close 保护。公开构造不接受任意 executor；Target runtime 的 apply/submission 方法
保持包内，WorkerSourceApplyLoop 新增明确 TargetSourceApplyRuntime 入口。

Target runtime 使用 bootstrap 成功产生的 Initialized，Backend.requireStore 验证
同一个 ShardStore 实例。构造还要求 context-bound ACTIVE_FOR_COMMANDS lease、完整
SourceAssignment ID/epoch、已持久 Owner epoch、实际已达到的 activation barrier；
它不执行或代替恢复/激活。WorkClass registry 绑定该 Store 的真实共享资源图。

`TargetWorkerOwnerActivation.activate` 为这一 Owner 边界提供本地有序入口：它只接受
`TargetStoreBootstrap.Initialized` 或 `Reopened` 对应的精确 format-2 Store/root，检查
Owner lease 的 assignment ID/epoch、当前身份/状态/期限以及 Store 已达到 activation
barrier；随后先持久化单调 Owner epoch，再把同一 lease CAS 到 `ACTIVE_FOR_COMMANDS`。
CAS 空响应会读取并接受同身份的 ACTIVE lease；若调用在 CAS 提交后异常，原调用仍失败，
同一 ACQUIRING lease 的后续调用只在 Store epoch 与当前 ACTIVE lease 精确相同时恢复。
Owner clock 必须是 epoch 毫秒且非回退；本次 Store marker 写入到 lease CAS 之间检测到回退
会拒绝激活，调用方应向 Target source runtime 继续提供同一非回退时钟。
该方法不接受或认证外部 assignment、Start/Commit 权威，也不创建 source/Worker/Host；
失败后的 Store 与 lease 清理由调用方负责。
真实 Oxia/RocksDB 回归覆盖首启和 takeover：首个 root 在精确 ACQUIRING lease guard 下提交，
随后调用此入口写 Owner epoch 并激活；第二 Owner 也先以 ACQUIRING lease 受 guard 地
`reopen` 旧 epoch Store，再写入新 epoch 并激活，用原 lease 精确重试会读回同一 ACTIVE
identity。该验证覆盖真实 Oxia lease CAS 与 Store 重开，不覆盖 Kafka/Pulsar source fencing
或生产 assignment/Start/Commit providers；首启 StartAuthority 仍是测试 fixture。

TargetWorkerShardRuntime 的外部构造现经 TargetWorkerShardFactory.create：先精确核对
source runtime 与 accepted SourceAssignment，再绑定 Store、RocksDB resource graph、
WorkClass registry 和 maintenance providers；assignment 不符时 source adapter 所有权
仍归调用方，接管后的组装失败则关闭 adapter。Kafka/Pulsar Target source factories
分别检查类型化 activation barrier 和当前 guarded client identity，Kafka 从 exclusive
offset seek，Pulsar 核对 connection generation 与 guard attestation。它们只接收已经
bootstrap/reopen 且完成 Owner activation 的 Target runtime，不负责创建 root 或授权
source 起点；应用级 bootstrap/Owner/host 生命周期和配置装配仍待接入。

每次执行先实际读取 OxiaOwnerLeaseStore.current，检查 lease token/owner/epoch/
assignment/session/state/非回退 expiry，并在读取返回后检查时间。每个提交 guard 再
校验精确 Store/scope、源记录/guard、实际 Store frontier 与 adapter successor，执行
外部资源/Control guard，最后再次读 lease 和时间。写入 stamp 必须 source-only，
source full bytes 与完整 signed envelope digest 精确匹配；未知或退化的 proof 不放行。
Pulsar 必须匹配 activation barrier 的 connection generation 和 guard attestation，
Kafka 拒绝携带 Pulsar proof。Owner loss、时间回退、错误/UNKNOWN 提交或外部 guard
失败使本 runtime 不可逆 fence，不能靠下一次 poll 恢复权限。

首次业务当前已装配 APPLY_SHARD_CONTROL 内的 TargetQuotaGrantControlBody；
下文后续批次补充了保留 Command 首结果的重放入口。
先在共用 read budget 下探测实际 SYSTEM/POSITION；重复直接用 replay store 和明确
duplicate write/read authorities。真正首次才解析 Prepared/Grant authority，再执行
TargetQuotaGrantStore.prepareFirst/commit，完整 Control/capacity 快照由相应外部
CommitGuard 持有。未实现的 Command/System 分支保持 source pending，禁止跳过或
借旧格式 applier 写 Target Store；这些业务仍须继续实现，不能据此称完整 Source。

仅 backend prepare 抛出的 ReadIncomplete 可包装为内部 ReadYield，由协调器保留
原记录并重新提交。外部 grant resolver 的同型异常不享有这个证明；commit/guard/
close 中的异常也不能伪装成零写重试。一个共同 records/bytes/elapsed 预算覆盖 duplicate
probe 和真正首次 prepare。远端服务调用仍必须由各生产 provider 的超时/队列约束。

只有 Store commit/read completion 后返回 SourceReplayOutcome；返回结果重锚到当前

`META/[0x1d,0x01]/Target[32]` 保存 NV40/schema1。字段 1 version=1、2 Target、3 首 NV39 marker 的 SHA-256、4 recovery lineage[16]、5 非零 revision、可选 6 after MessageId[32]、7 OPEN=1/COMPLETE=2、8 完整 TargetQuotaMutation、9 域分离摘要。初始 revision=1、无 after、OPEN，stamp 与首次 marker 相同，和 CLOSED queue/marker/首结果/source 同批写入。后续只能以严格递增的本地 field5/6/7 stamp 更新，绑定原 marker 与 lineage。

终态 point writer 在相同 ReadView 读取首活跃索引和游标：当前候选是首项才在删除该索引及双 ID/expiry/owner 的批次中前移；若再无第二项，写 COMPLETE。非首项可以终态化但不可跳过首项。空索引且仍 OPEN 时，`completeEmpty` 以 field7 mutation 更新游标及原 Target/tenant mirror、total、aggregate；source META3/5 不变。预算、ReadAuthority、quota authority 与 CommitAuthority 均须覆盖受保护视图和同批写。可恢复 GC scheduler 和旧 format2 回填仍缺。

### 2026-09-23 Close GC WorkClass 单步

`TargetReservationClosureWorkClassExecutor.Request` 冻结 Shard、Target、非零 requestId 与有限 record/byte/elapsed 预算。排队只验证本地身份/资格并收取最大读取字节，不读 Store；执行时共享同一 `BoundedReadBudget`，ReadAuthority 在首读前获取、在视图交付前复核。`ClosureStore.discover` 只返回该 Target 最早活跃候选；`QueryStore` 判定 ABANDONED/EXPIRED 后调用相应点 writer，点 writer 再次核对终态/游标/权限并原子提交。空索引经 `completeEmpty` 的独立 field7 writer；已完成、无 marker 和并发变化分别返回，不冒充全 Target 关闭完成。Executor 无进程内 cursor，重新提交从 NV40 恢复，但持久任务触发与跨 Target 选择仍是后续装配。

### 2026-09-23 空索引完成的局部 Store 证据

第二 Target 的真实 grant 和签名首 Close 之后没有活跃 reservation；GC action 在同一有限预算下调用 `completeEmpty`，field7 更新 NV40 与原 Target/tenant mirror、total、aggregate，保留 source META3/5。测试先让 CommitAuthority 失败，确认零写，再重提交成功并以新请求读出 ALREADY_COMPLETE。队列初始化在测试中通过 source-accounted fixture；生产注册、真实 Owner 接管与跨 Target 长期调度仍待独立验证。本地 reopen 续跑见后续小节。

### 2026-09-23 NV40 范围发现与轮转

`ClosureStore.discoverNextTarget` 在 ReadAuthority 下对 `META/[0x1d,0x01]..[0x1d,0x02]` 做一次有界 seek，并读取首 NV39 marker、CLOSED queue、NV40 与 aggregate stamp；键必须恰为 prefix+Target[32]。返回的 ScanCursor 只属于原 store facade，记录当前 key 作为下一次的排他下界。无候选返回范围结束，由 GC action 将进程扫位归零。每个 action 最多跳过一个 COMPLETE 或处理一个 OPEN Target；处理失败、预算耗尽或需重新发现时不推进扫位。重建 executor 从起点重新扫描持久 NV40；每 Target 的 terminal 进度仍由 NV40 保证。持续触发、公平上界、旧 format2 数据回填与真实 Owner 接管尚缺。

### 2026-09-23 NV40 已完成态的本地 reopen 证据

四组实际 Worker 场景在关闭原 RocksDB/ShardStore 后，以保存的真实 root accounting incarnation 与 recovery lineage 构造新 backend；新 ClosureStore 从 `META/0x1d` 读取两个 COMPLETE Target，新 GC executor 从空进程扫位跳过二者并回卷，没有 native 写。该测试只证明已完成游标的持久读取和进程扫位重建，不覆盖未完成 Target 的继续物化、真实 Owner lease 接管、native UNKNOWN 或完整恢复审计。

### 2026-09-23 NV40 OPEN 空 Target 的本地 reopen 续跑

四组场景另在原 Store 创建第三 Target：实际 grant writer、source-accounted 物理身份与 OPEN queue、签名 Close writer 留下 NV39 与 OPEN NV40。关闭原 RocksDB 后，新 backend/ClosureStore 的受保护范围扫描读到两个 COMPLETE 和一个 OPEN；新 GC executor 从起点跳过完成项，并对 OPEN 空索引执行 field7 本地完成，同批写 NV40、两 counter、total、aggregate 共 5 条 native 记录。Source sequence/position 均不变。该证据只覆盖同一 root/lineage 的本地空 Target 续跑，尚未验证真实 Owner lease 接管、活跃 reservation 恢复、native UNKNOWN 或 Broker 恢复。

### 2026-09-23 持久 root anchor 的受保护重开

`TargetStoreBootstrap.reopen` 在首次读之前获取 ReadAuthority，使用同一 `BoundedReadBudget` 和 Store ReadView 点读固定 Shard NV31 bookkeeping anchor、其指向的 NV33 incarnation、当前 aggregate 与 source META3/5。必须满足 Shard/tenant、root identity/accounting、aggregate incarnation/最新 source frontier 和 root/bookkeeping mutation 先后关系。root/frontier 通过后，`reopen` 在同一个 `readWithBudget` 计划内调用 `TargetCheckpointRootVerifier.auditLiveStoreLedger`；live Store 与 checkpoint 镜像共用 `TargetCheckpointLedgerAudit`，扫描实际 CF、校验恢复/固定 metadata，解析 Message、OrderState、DEDUP 和 grant-result 依赖，从业务记录重建 quota usage，并核对 counters、totals、primary/mirror、grant inventory 与 aggregate。有限 `LedgerAuditLimits` 可由调用方收紧，所有 iterator 条目和依赖点读同时计入同一个 `BoundedReadBudget`。预算耗尽、依赖缺失或账本/投影不匹配时不创建 `Reopened`、不写入修复值；Store open 已核验 default CF 为空。交付重建结果前还要验证 ReadView 与 ReadAuthority。`TargetSourceApplyRuntime` 可用此结果构造实际 source store，而不是要求调用者保存首次 bootstrap 对象。此路径证明的是当前本地投影与账本一致，不认证 Owner/Oxia/Broker 接管、历史权限、checkpoint 发布或 restore/install。

### 2026-09-23 Close GC 的 Owner/Store guard

`TargetSourceApplyRuntime.newCloseGcExecutor` 只接受自身 source loop 已绑定的 WorkClass registry，固定此实例的 backend、Shard scope、lineage、domain bound 与 source ReadAuthority。任务接纳和执行时的本地 eligibility 读取当前 lease；读写 guard 在外部权限检查前后重验同一 Owner 身份、有效时间、Store 打开 epoch 与精确 Store/scope，失权会 fence 原 source runtime。写 authority 只接受 reservation Close、expiry 或 Close cursor 的本地 mutation；配额仍由各独立 authority 校验。此 factory 只装配同一 Owner 的 GC 单步权限，不自行提供周期触发或声称恢复/外部权限认证。

### 2026-09-23 Close/expiry 有界维护 turn

`TargetSourceApplyRuntime.newExpiryGcExecutor` 以同一 Owner/Store guard 装配普通 expiry 扫描，并只接受 reservationExpiry 本地 mutation。`newReservationGcRuntime` 对每个 source runtime 只绑定一次，组合 Close/expiry 两个 executor。`runTurn` 在共享 WorkClass 图中每次最多新排一个任务，以 Owner epoch 与递增 uint64 序号组成 16 字节请求 ID；只有所选任务产生结果后才切换 Close/expiry，预算未选中时保留原 submission 与身份。新 Owner 重新创建 runtime，从 NV40 与 expiry 索引起点恢复扫描。调用方必须提供持续 tick 与足够任务字节预算；当前无生产 timer、跨 Shard 公平性界限或完整恢复认证。

`TargetWorkerShardRuntime` 将一个已激活 Target source runtime、它的精确 Store、共享资源、source consumer 和 Close/expiry 权限装配为单 Shard Worker 调用入口。先核对 Store/资源实例，再绑定同一 WorkClass registry 的 source loop、一次性 GC 和本地 drain coordinator；两个 turn 先查资源 admission gate，随后各走已有 source ACK 或 GC Owner/Store 权限检查。周期调度由显式维护循环负责；host 仍须先关闭循环并消解 pending source ACK。

`TargetWorkerShardFleetRuntime` 只接纳同一 Worker registry/资源 envelope 的唯一 ShardId 集合，并用独立 source/GC 游标选下一 Shard。游标在执行前移动，维护异常保留 cause 并附上本轮 Shard 身份，下一次调用仍轮到后续 Shard；每个 Shard 的待执行 GC submission 仍由其自己的 `TargetReservationGcRuntime` 保存。宿主必须启动维护循环并处理失权 Shard 的 Owner drain，fleet 不隐含 timer 或接管授权。

Target fleet 的维护异常现封装为携带 `selectedShardId` 的 `MaintenanceDispatchFailure`；该身份只表示本轮选择，不证明共享 WorkClass dispatcher 中哪一项 action 失败。`TargetWorkerMaintenanceLoop` 用正数固定间隔和有限 `SchedulerBudget` 单线程调用 fleet，每轮在独立锁内执行，普通失败及失败回调异常均被记录且不抑制下一 tick；fatal Error 报告后仍向调度器传播。`close` 取消后续任务且在不打断当前 Store action 的前提下等待在途 turn 锁释放；本地 host 已在 Owner drain 前关闭循环，生产进程仍未接线。

`TargetWorkerShardRuntime.pauseNewTurns` 拒绝后续 source poll 与新 GC 提交；`settlePendingMaintenance` 仅进入 `TargetReservationGcRuntime.settlePendingTurn`，没有 pending 时返回空，有限预算未执行时保留原 submission/task，已经由共享 dispatcher 完成但因其它 action 异常未回报的结果可直接消费而不再运行队列。它仍要求 Worker 资源 admission，不能代替 Owner DRAINING CAS 或受损 Store 的紧急 teardown；宿主必须先证明 pending source ACK 已解决，再开始普通 drain。

`TargetWorkerShardRuntime.drain` 拒绝未确认的 source entry 并暂停新 turn，随后由 `TargetOwnerDrainCoordinator` 获取 Worker drain slot、结算旧 GC task、读取同一 Owner 身份与有效租期、CAS 至 DRAINING、fence 本地 source、flush/close Store、按精确身份 release lease、最后关闭 native source。小预算只返回 `PENDING_GC`，不更改 Owner；lease 变化返回 `OWNER_LOST_CLOSED`，保留新 Owner；写结果不确定则先 fence/close Store 再尝试精确 lease release，返回 `UNCERTAIN_RELEASED`。后两者都不宣称正常 flush。Store 关闭或 lease release 失败保持同一 coordinator 可重试。该入口没有 checkpoint、pending ACK 解决器、真实 Broker/Oxia 接入或生产宿主关闭编排。

`WorkerSourceApplyLoop.settlePendingEntry` 在同一锁内检查是否存在留存 entry，再调用 source 协调器的原 turn；空时不执行 `poll`。`TargetWorkerShardRuntime.settlePendingSourceTurn` 暂停前暴露此入口：尚未 apply 的 entry 仍受 Worker 资源 admission；已有 `appliedOutcome` 的 ACK 重试只走当前 Owner/Store 和 native ACK 校验。结果不为 `APPLIED_AND_ACKED` 时仍留存 entry，不能开始 drain。这个 API 不负责判定失权后的 Broker 重投或清除 ACK UNKNOWN。

若该 entry 的 WorkClass submission 已有结果但协调器尚未消费，settlement 直接读取结果，不再运行共享 dispatcher；这样不会在关闭前顺带执行另一项已排队工作。结果尚未出现时仍按原有限预算运行共享 turn。

`TargetOwnerDrainCoordinator` 的 DRAINING CAS 通过 `OxiaOwnerLeaseStore.transitionOrRead` 接受精确同身份 successor；返回空且未确认时先 fence 本地 source，再由调用方重试。lease release 记录已发尝试：若抛错前 CAS 实际成功，下次权威读为空才接受释放完成；Store 不会因此重开。真实 Oxia 后端/会话仍须验证。`CheckpointManifest` 现允许 `storeFormatVersion == 2` 并规范输出相应 JSON，解码经原 canonicality 校验；它尚无 Target 控制快照语义。`ShardStore` restore probe/manifest 校验及物理控制快照校验仍固定 format 1，scheduled/drain 执行器、旧 `createCheckpoint`、上传、Catalog/Oxia、下载/安装继续在副作用前拒绝 format 2。独立本地候选已进入 CHECKPOINT work class；完整 Target 控制快照与 catalog 候选契约、物理发布/恢复安装及最终 drain 仍须接线。

`TargetWorkerHostRuntime.start` 用同一组 Shard 构建 fleet 与固定间隔维护 loop；`runNextSourceTurn` 和 `drainAll` 在宿主锁下互斥。`drainAll` 先置 stopping，关闭 loop 并等待 `turnLock` 退出，再等待单 Shard 在途 drain 结束，逐 Shard 尝试 entry-only source settlement 和本地 drain；普通 RuntimeException 只记录在该 Shard 结果内，之后仍处理其它 Shard。重复调用只重试未达终态的 Shard，已完成实例的结果保留，不重新关闭其 Store。2026-09-30 的 Host 回归注入一次 ACK UNKNOWN，确认 pending entry 留存时返回 `PENDING_SOURCE` 且不进入 Owner drain；重试结清后才调用 drain。该测试使用 Host Shard seam，不替代真实 Broker ACK/重投验证。

Host 启动先创建尚未调度的维护 loop，再逐个绑定该 Host 的精确信号；只有 Host 完整构造后才启动 tick。任一 Worker 绑定失败会按逆序清除本次已尝试的同一信号，身份不匹配的既有 Host 信号不会被解绑；构造或调度失败还会关闭新建 loop。真实多 Store 回归覆盖部分绑定失败后的原 Host 接纳，以及配置 Worker 与既有 Host 冲突时不遗留维护线程。该证据仅覆盖本地启动失败生命周期。

`drainShard` 要求传入精确运行实例，在宿主锁内核对当前成员并调用 fleet 的 `withdraw`：fleet 的 source 与 GC dispatch 持同一锁，撤出返回时该 Shard 的已选 turn 已退出，两个游标按删除位置校正；然后释放宿主锁，仅对该 Shard 串行执行 entry settlement 和 drain。同一实例同时只准一次 drain；其它 Shard 的 source 与维护 tick 不等待此 drain。`admitShard` 在宿主与 fleet 锁内验证同一 WorkClass/资源图，新 ID 直接加入；同 ID 只替换已撤出且完成 drain 的实例，并拒绝旧实例的迟到撤出。最后一个 Shard 撤出后维护 tick 返回空，后续加入可继续运行。仍须接入真实 assignment 成员变更、Broker/Oxia 连接生命周期和 checkpoint 发布。

`TargetCheckpointRootVerifier.validate` 对不可变 format 2 RocksDB 镜像执行有限文件 inventory 后只读打开全部关闭 CF 集。它从固定 META1/2/3/5 读取格式、Store 身份、Source Position 与 mutation sequence，从 Shard 固定 NV31 anchor 定位 NV33 root，再定位 NV27 aggregate；核对 Shard/tenant/accounting 身份及 root/bookkeeping mutation 不晚于 aggregate、aggregate stamp 等于固定 source/sequence。`validateManifestImageIdentity` 再比较完整文件名/长度/checksum、DB/Store 身份、root recovery lineage、META7 checkpoint ID、META8 Owner epoch、source/sequence 与 META6 evidence cursors。返回的 `RootProof` 只是这些本地持久事实的读取结果，不认证 Manifest 的 controlStateDigest 或 referencedSemanticVersionsDigest。完整 Target 投影盘点、Catalog 与 restore/install 尚未接入。

`auditQuotaProjections` 在同一只读打开和物理文件预算内，对 META 的 counter/total/grant activation tag 施加独立记录数及总 key/value 字节预算。逐条验证 NV envelope、规范 value/key/Shard/tenant，核对 NV31 inventory、所有 primary counter 的精确 NV27 aggregate 和按 Target 求和的 total、每个 primary 的 tenant mirror 资源向量，以及记录 mutation 不晚于 aggregate。这一层只建立配额投影之间的一致性。

`auditIndependentLedger` 再用独立有限扫描/点读预算遍历全部关闭 CF，拒绝未知业务 key，让只读 `TargetRecordAccounting.View` 逐条从 Message、Reservation、payload owner、队列、result 等真实记录及其依赖重算冻结费用；NV31 库存费用和固定 ingress fence 另计一次。`TargetQuotaDelta.audit` 对每个实际 counter 的 identity/用量及 aggregate/镜像关系逐一核对。`auditManifestImageLedger` 在一次镜像打开中合并 Manifest 身份、配额投影和这一账本重算。受保护零用量退休 counter 的独立身份权威及固定控制/语义摘要、全部 Target 跨记录关系仍须补齐；本地扫描不构成恢复或发布权限。

完整 DEDUPE CF 遍历在扫描预算内收集 06–09/NV35，并用同一镜像的有限 META 点读交给 `TargetResultLedgerAudit.auditRows`；它校验结果规范键、source 序列的 stamp/事件唯一性、首结果引用及精确 owner。结果 primary/tenant 小计必须与 `TargetRecordAccounting` 在本次扫描内对同一记录逐条重算的费用一致。`auditRows` 不要求外部 CompletenessAuthority，也不单独宣称输入完整：完整性仅来自调用方本次完整 CF 迭代和物理镜像约束；Owner/控制认证与 checkpoint 发布仍须独立证明。

`ShardStore.createTargetCheckpointCandidate` 是 format 2 专用的本地物理镜像入口，必须传入显式非零 checkpoint ID 与有限物理/配额/账本预算。它复用旧格式的 checkpoint 容量槽、META7 身份写入、私有临时目录、原子目录移动和失败时恢复前一 META7 的机制；在镜像落位前，对临时镜像运行 `TargetCheckpointRootVerifier.auditLocalCandidate`，同时比对传入 lineage、Store/source/native write 切点、META7 checkpoint ID、META8 Owner epoch 与 META6 evidence cursors。预算无界时在写入前拒绝；审核失败删除临时镜像、回滚身份，回滚不确定则沿用 Store 的 write-uncertain fencing。直接调用此包内入口只产出本地候选物理字节，不构成 Manifest、外部 Owner/CHECKPOINT、控制快照、Catalog、上传或 restore/install 权威。

`reuseTargetCheckpointCandidate` 仅在活动 Store 仍保有同一 META7 ID 时读取既有真实目录；同一次 `auditLocalCandidate` 检查完整文件/CF、配额与业务账本，另将镜像根与当前 Store 的 DB/Incarnation、lineage、source position/sequence、RocksDB latest native sequence、Owner epoch 和 evidence cursors 精确比较，成功不执行 native 写。创建前同样要求 opened Owner epoch 和非空 source cut；这只是本地身份/重试屏障，外部 Owner lease、Source Assignment 与 Catalog 权威仍须在 Worker 执行器中取得。

`TargetCheckpointCandidateWorkClassExecutor` 现把本地候选创建/复用放入同一 Worker 的 `CHECKPOINT` 队列。提交前和排队后执行前，它从 Owner Lease 与 pending upload intent 权威读取当前值，核对完整 lease fencing/context、ACTIVE session、有效期、intent 精确值/上传期限、Store Incarnation、Shard、checkpoint ID/lineage 与 opened Owner epoch；物理操作后再次核对两项外部权威。队列拒绝不修改 Store；后验失权只留下未发布的本地目录。这个局部入口尚未装入生产 Worker 的 checkpoint 调度/源切点流程，Owner 的 deployment/worker-run 身份与认证 lease 的最终装配关系、控制/语义快照、Manifest、上传、Catalog 和 restore/install 仍须另行实现并验证。
