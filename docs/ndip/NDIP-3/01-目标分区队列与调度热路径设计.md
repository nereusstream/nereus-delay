## 1. 结论与本次改造范围

本次应做的不是“把所有 Lane 的 ID 改成 topic 名称”，而是两类不同的改造。

**第一类是必须优先修复的热路径问题。** 当前选择 Lane 最早候选的代码没有充分利用 RocksDB 已有排序：每次更新相关投影，会扫描该 Lane 的 DUE、ORDERED、NATIVE 候选前缀，逐条读取 Message 再选最小值。调度器还会为普通 poll 持久化整套公平性投影。先修复这些问题，再扩大单队列规模。[S02][S03][S04][S05][S06]

**第二类是架构收敛。** 默认无序投递不应因为 Profile 版本、unordered bucket 或 ordering key 而为同一个目标物理分区复制完整的 Lane 生命周期、READY、公平性、限流、Producer 和恢复登记。发送调度应以目标物理分区为核心，消息策略、可选严格顺序、通道身份分别处理。[S01]

最终建议：

```text
一个目标物理分区，一个逻辑 TargetPartitionId
    每个源 Shard 内：一份该目标的持久调度队列投影
    每个 Worker 内：一个该目标的发送调度入口
    Producer：按真正的兼容性和吞吐需要使用有界通道，不按 Lane 数创建
```

必须保留两个边界：

- 同一个目标可能同时存在于多个源 Shard 的 RocksDB 中。这是持久化与恢复边界，不应为消灭这个事实再引入一个全局集中式 Dispatcher。
- 一个逻辑目标队列不等于全集群只能存在一个 Producer。不同进程、不同认证身份、不同事务或 sequence 恢复域可能必须使用不同通道，但不应因此复制独立发送权重和整套 Lane 状态机。

## 2. 当前实现到底在做什么

### 2.1 Lane 并不只是目标 topic/partition

`CanonicalLaneTuple` 解析的字段包含 tenant routing scope、Adapter、认证 cluster、Broker resource incarnation、物理 topic/partition、Destination Profile ID/version/hash、Capability Profile ID/version/hash，以及 ordering-domain hash 或 unordered bucket。`DestinationLaneId.derive` 对整份 tuple 求 hash。[S01]

因此，下列变化都可能使同一目标物理分区产生不同 Lane：

```text
同一目标分区 + Profile version 1
同一目标分区 + Profile version 2
同一目标分区 + 不同 Capability Profile
同一目标分区 + unordered bucket 0 / 1 / ...
同一目标分区 + ordering domain A / B / ...
同一目标分区 + 不同 tenant routing scope
```

这些维度里，有些需要隔离，有些只是消息策略，有些只是为了并发分桶。把它们全都提升为“持久 Lane 身份”，才是问题所在。

这里不能直接得出“所有 Lane 都是多余的”：严格顺序需要自己的未决 head；认证身份不兼容时不能共用凭据；强去重与事务需要稳定通道身份。但这些需求不必全部通过一种重量级 Lane 表达。

### 2.2 每秒的 discovery 不是对未来 60 秒所有消息做完整范围扫描

生产组合 `WorkerSchedulingRuntime.runDueTurn` 经 `DueSchedulerWorkClassExecutor` 进入 `PersistentLaneScheduler`。[S07]

`PersistentLaneScheduler.discoverReady` 扫描 READY namespace；`scanReadyEntries` 使用 `lastScannedReadyKey`，扫后半段、必要时 wrap，并用 `discoveredHeads` / 已排队项目判断是否已经发现或正在等待 Claim。[S02][S03]

其特点是：

```text
扫描对象：Lane READY head，而非窗口内全部消息正文
扫描范围：有记录数限制的旋转 slice
重复控制：已经发现/已经 poll、尚未完成 Claim 的 head 不再次 offer
单一 head：为重新判断实时 Handoff policy，可能被有意重访
```

NDIP-1 还让同一份 READY 投影容纳 ordinary 与 native head。选择任一分支成功 Claim 后，另一个进程内 sibling 不能残留为新的发送工作。[S03][S04]

所以，“两个时间窗口重叠 59 秒”并不能单独证明“59 秒内所有消息每秒重复扫描或重复发送”。已 Claim、已 Admission、已发送的记录是否仍在可调度索引，才决定扫描行为。

### 2.3 真正的全量重读发生在维护最早 head 时

源码调用链：

```text
DelayShard.persistMutation(...)
    -> readyProjections(...)
        -> findLaneCandidate(...)
        -> findLaneNativeCandidate(...)
    -> store.write(...)
```

`persistMutation` 是 Command 状态落盘的共同路径。当前 `findLaneCandidate` 对 DUE 和 ORDERED 两个 Lane 前缀分别执行：

```java
candidateLimit = boundedLimitPlusOne(config.maxPendingMessages());
entries = store.scan(TIMELINE, prefix, prefixUpperBound(prefix), candidateLimit);
for (entry : entries) {
    candidate = decodeTimelineCandidate(entry, tag, laneId);
    // 校验、读取对应 Message，再挑选最小 candidate。
}
```

`findLaneNativeCandidate` 对 tag 7 的 native 前缀做同样的扫描。`decodeTimelineCandidate`、`decodeNativeTimelineCandidate` 中还会读取对应 Message 并校验其状态、generation、Lane 与索引一致性。[S05][S06]

**这里既没有 60 秒的上界，也不是“读到第一个合法最小值就停止”。** 只要 Lane 中还有更远期的候选，相关前缀也可能被读到。

因此当前应优先修复的不是“窗口右移时有没有减掉 59 秒”，而是：

> 为了知道队列最前面是谁，反复读了队列中很多甚至全部候选。

### 2.4 复杂度影响

设一个 Lane 当前有 N 条候选。一次 head 重算的应用层候选读取量可能是 O(N)，而不是 O(1) 个候选。

若连续向同一 Lane 插入 N 条未来消息，每次插入都走上述路径，仅普通候选读取次数就可能接近：

```text
0 + 1 + 2 + ... + (N - 1) = N × (N - 1) / 2
```

N=100,000 时，这个公式等于 4,999,950,000 次候选访问；如果这些消息同时都有 native 索引，还会有相应的 native 前缀访问。它不是等量的磁盘随机 I/O，缓存可能命中，也不是性能测试结果；但 Java 解码、Message 点查、对象分配和迭代本身已经有明显放大。

**在修复前合并 Lane，可能让原来分散的 N 变大，反而先变慢。**

### 2.5 还有两处具体写放大

`PersistentLaneScheduler.poll` 在返回结果前无条件调用 `persist()`，包括没有选中工作时。`persist()` 重新生成 active ring、deficit map、last-served map、round、discovery cursor，并写五个 scheduler projection。[S03][S04]

`DelayShard.persistQuota` 在 per-Lane usage 变化时，会写入完整 `LaneQuotaUsageProjection.canonicalBytes()`；aggregate projection 也一起写。单 Lane 的计费变更因此可能导致整个 Lane map 重新编码和写入。[S08]

进一步的源码检查表明，`LaneQuotaUsageProjection.replace` 还会复制集合、把所有 entry 的 revision 统一到本次 revision、重新排序；`aggregateQuotaUsage` 则遍历所有 Lane 求和。因此 quota 优化必须覆盖计算过程，不能仅把最终存储拆成独立 key。[S16]

这两项不是“有 DRR 就一定很慢”，而是把可恢复的调度细节、聚合 map 放进了高频同步写路径。

## 3. 哪些属于过度设计，哪些不能随意删

### 3.1 建议收敛的部分

| 当前做法 | 问题 | 目标做法 |
|---|---|---|
| Profile version、unordered bucket、ordering domain 全部进入 Lane ID | 同一目标有多套登记和生命周期 | Target ID 只标识物理目的地；策略与顺序单独处理 |
| 默认通过增加 Lane 获得并发 | 调度权重、连接数、证据对象随 Lane 数增长 | 单目标有界并发/通道槽位，不增加目标公平份额 |
| 每次找 head 扫完整候选前缀 | 已排序数据又被全量求最小值 | seek 最小项，结合本次变更 overlay |
| discovery 每次重新验证未变 head 的整条对象关系 | 对稳定队头反复解码/点查 | head revision + bounded cache；首次发现和 Claim 前严格验证 |
| 每次 poll 持久化全部 DRR 状态 | 调度行为变成额外同步写事务 | 公平性状态在内存，重启重建；语义事实继续 durable |
| quota 按全 Lane map 保存 | 单项变更写整个集合 | 单 target/tenant counter key 与 shard aggregate 原子更新 |
| 每种本地动作都有重复 authority wrapper、兼容 overload | 装配链长，审查很难判断真正入口 | 少量正式入口，共享 guard；legacy 收到有限升级层 |
| 逐消息 SLO outbox 与业务 batch 绑定 | 观测系统可能阻塞业务持久化 | 默认运行时指标异步导出；认证/审计用明确可选模式 |
| 将历史修补、认证执行记录不断追加到当前设计 | 当前行为有多个来源 | 当前规范只写当前行为；历史材料归档 |

### 3.2 保留的正确性边界

本次不删除 Command 排队与 applied 的区别；不删除 Source Position 顺序；不删除消息 ID/generation、命令幂等与稳定的重试字节；不删除 Producer 调用前的 durable Admission；不把超时当作未发送；不删除 owner/store/resource incarnation fencing；不删除 outcome 回写、checkpoint/Floor/GC 保护与物理 in-flight/zombie 计费。[S09][S10]

这些机制可能还有实现优化空间，但不能以“看起来有很多状态”为理由直接移除。

尤其禁止两种捷径：

```text
先把消息发出去，再补 PUBLISHING                  // crash 后无法恢复发送义务
把 Outcome 改成只写本地 DB、不进可重放日志         // checkpoint+replay 可能改变历史业务结果
```

### 3.3 严格顺序作为可选复杂度，不再污染默认无序路径

默认 `BEST_EFFORT` 使用普通目标队列，不创建 ordering-domain 生命周期对象。

已有 `DELIVERY_TIME_FIFO` 仍必须保护未决 head。不能为了统一 target 而把它降级成“Producer 本身有序”。严格模式的队头、迟到插入规则、未知结果 barrier 只在启用该能力时出现，不给每个 key 配置独立 Producer、熔断器、证书或一套 DRR。

本次不承诺跨 Route、跨源 Shard 的全局 FIFO，也不把 Pulsar native delivery 扩展成严格顺序能力。

## 4. 目标架构与概念数量控制

### 4.1 最终流程

```text
SDK / Gateway
    -> Command Topic / Shard Log
    -> Shard 单写者 apply
    -> Message + 时间索引 + TargetQueue 摘要
    -> Worker Target 调度器
    -> Claim
    -> source-ordered Publish Admission
    -> 适配器有界通道
    -> Kafka / Pulsar 目标物理分区
    -> source-ordered Outcome
```

不新增 Dispatcher 服务，不新增时间轮服务，不增加第二条业务状态日志，不为了 Handoff 再建 Scanner，不改变源 Shard 作为独立 RocksDB/ownership/recovery 单元。

### 4.2 四个概念足够覆盖默认发送路径

| 概念 | 标识什么 | 是否有独立业务生命周期 |
|---|---|---|
| `TargetPartitionId` | 真正的物理目的地 | 不因 Profile/并发槽变化而创建新目标 |
| `TargetQueueState` | 某源 Shard 中该目标的队头摘要与持久控制 | 只保留必要控制与索引投影 |
| `TargetRuntime` | 一个 Worker 内该目标的公平份额、唤醒、并发与熔断 | 可重建，空闲可回收 |
| `ProducerChannel` | Broker 连接、认证及事务/sequence 所需的实际执行上下文 | 有界资源生命周期，不拥有额外发送权重 |

Message、Claim、Attempt 和源 Shard 沿用原来的业务概念，不另起一套状态机。严格顺序额外使用按 key 的必要 barrier，不作为默认第五种重型运行实体。

### 4.3 Target ID 的稳定定义

建议使用新的、明确区分于旧 Lane 的版本化身份：

```text
TargetPartitionId = SHA-256(
    domainSeparator
    || version
    || canonical(adapterKind)
    || canonical(authenticatedClusterIdentity)
    || canonical(brokerResourceIncarnation)
    || canonical(physicalPartition)
)
```

Kafka resource 包含 native topic UUID；Pulsar resource 包含已 pin 的 resource token、physical topic identity 及需要的 creation identity。字段长度和 canonical 编码沿用现有 Registry 机制，不能直接用 Java `toString()` 拼接。

**不包含：** Destination Profile ID/version、Capability Profile ID/version、tenant、ordering key、unordered bucket、Producer slot、连接 generation。

**也不能只包含：** topic name。不同集群同名 topic、删除重建后的同名 topic，不是同一个目标。

Profile、tenant、安全身份仍需保留在 Message/Binding/Admission 中。将 tenant 从物理目标 hash 移除，绝不意味着移除 tenant 授权或允许跨租户查询。

### 4.4 三种“唯一”的区别

```text
集群级语义：同一个物理目的地得到同一个 TargetPartitionId。
Shard 级持久化：同一 TargetPartitionId 在每个源 Shard 中最多一份目标队列投影。
Worker 级调度：同一 TargetPartitionId 在一个 Worker 中最多一个调度入口。
```

多个源 Shard 的目标队列不是新的独立目标；Worker 对它们轮转取消息。多个 Worker 不共享一个内存队列，也不靠跨 DB 原子写协调发送。

若业务以后要求“目标 partition 全局只有一个发送 Owner”，那是重新定义路由与 ownership 的另外一个架构项目，不纳入本次简化。

### 4.5 合并调度，不合并租户的控制权限

新 `TargetQueueState.sourceOrderedAdmissionState` 只表达明确授权的目标级控制，不作为任何租户都可写的公共开关。平台管理员的目标 Pause/Close 必须经现有 Control Operation 固定受影响的源 Shard 集合，各 Shard 的 marker 分别生效；不宣称跨 Shard 瞬时原子关闭。

租户只能通过已有 Route、Profile binding 或单消息操作控制自己的数据，不能因不同租户共享 Target ID 而暂停、恢复或查询其他租户的消息。Profile deprecation 继续只关闭规定范围的新 binding，不以改变共享 Target ID 的方式追溯改写旧消息。

对于同一源 Shard/target 中要求不同暂停、恢复或强保证隔离的存量 binding，本次不把这些差异用一个目标开关粗暴覆盖。无数据环境采用新控制范围；有数据环境先保留被保护的旧控制效果并排空，不能安全转换则拒绝切换。确实需要长期保留的细粒度控制，应存成小型 binding/control 记录，而不是恢复每个 binding 一份 Producer、DRR 和完整 Lane 生命周期。

同理，目标不存在、分区不可用属于 target 故障；某一凭证无效属于执行上下文故障。它们不能共用一个过大的故障开关。默认合并路径要求执行上下文兼容；不兼容情况按 §8.2、§8.5 处理，不额外承诺所有上下文都能零成本共享。

## 5. P0：先把取 head 从全扫改成有序最小值查询

### 5.1 最小风险修复，不先改身份和协议

第一步仍使用现有 Lane key，只替换候选选择算法。现有 key 已把时间放在 Lane 前缀后；`TimelineCandidate.compareTo` 和 native comparator 先比时间、再比 key 字节，可以利用每个 namespace 内的排序。[S06][S11]

对当前“一条消息变更、最多排除一个旧 generation”的调用：

```text
DUE 前缀：取第一个未被本次替换/删除的候选
ORDERED 前缀：取第一个未被本次替换/删除的候选
NATIVE 前缀：取第一个未被本次替换/删除的候选

每个前缀再与本次 included candidate 比较。
```

在索引不含陈旧业务 key 的正常状态下，每个前缀最多读取一个正常候选和一个被本次排除的旧候选，即 1～2 项，而不是 `maxPendingMessages + 1` 项。

不能一律把 limit 改成 1：如果第一项正是本次删除的旧 head，必须看到它的 successor。

阶段 A 严格保留以下比较规则：DUE 使用现有 `eligibleAt`；ORDERED 以 `deliverAt` 保持原队头顺序；NATIVE 使用现有 `candidateAt`。时间相同再按原 unsigned key 顺序比较。尤其不能为了“统一时间”把 ORDERED 改按 retry 后的 `nextEligibleAt` 排序，让后继越过受保护的 head。Target 新索引使用 deliverAt 的 Native 设计属于阶段 B/C。[S11]

### 5.2 泛化到 bounded batch 的 read-your-writes overlay

后续批量 apply 应采用明确的局部变更集：

```text
HeadDelta {
    removedKeys
    insertedEntries
}
```

求值规则：

```text
storedCandidate = 第一个不在 removedKeys / 被覆盖集合中的持久 key
insertCandidate = 本次 insertedEntries 中的最小 key
newHead = min(storedCandidate, insertCandidate)
```

伪代码：

```text
readStoredHead(prefix, exactRemovedKeys, sharedBudget)
    -> FOUND(validatedCandidate)
    -> EMPTY_CONFIRMED
    -> INCOMPLETE(reason)

stored = readStoredHead(...)
if stored is INCOMPLETE:
    return INCOMPLETE                 // 本次新增项不能掩盖尚未读完的持久前缀
head = min(stored.candidateOrNone, delta.minimumInsert(prefix))
return head exists ? FOUND(head) : EMPTY_CONFIRMED
```

`exactRemovedKeys` 来自该 turn 中已验证的 prior state，必须是完整 key；同 key 覆盖表示“排除原值，再加入新值”。不能只按宽泛 messageId 前缀过滤，也不能将非 overlay 的损坏记录当作可跳过项。每个前缀最多排除 `d` 个已声明 key 时，健康路径最多访问 `d + 1` 个应用候选；批量大小另有硬上限。阶段 A 的公共 Command API 仍按当前单消息变更工作，不同时引入批量入口。

不要假设普通 WriteBatch 中尚未提交的改动能被普通 RocksDB iterator 自动读到。本次变更必须由显式 overlay 或已选定的、可验证的 read-your-writes 机制参与计算。

### 5.3 原子性

以下必须在同一个 shard WriteBatch 中提交：

```text
Message 状态变更
+ 删除旧 ordinary/native/expiry key
+ 写入新 ordinary/native/expiry key
+ Target/Lane head 摘要变化
+ quota 与结果
+ applied Source Position
```

只能在 WriteBatch 确认成功后发布新的进程内 head。写结果不确定时，按现有 Store/Owner 规则 fence，不能把内存回滚当作已证明 DB 未提交。

### 5.4 稳定非 head 变更的进一步优化

若本次插入的 key 晚于当前 head，且没有删除/替换当前 head，无需再次 seek 队列。只更新 Message、索引、quota，不写新的 head revision，不反复重排 READY。

若删除的是非 head，也不更新 head。只有 head 的 identity/time/必要状态变化才更新 head 摘要。

这一优化必须读取与该次状态机 turn 一致的 head，不能信任来自另一 Owner、Store 或旧 batch 的缓存。

### 5.5 把完整审计移出每条消息热路径

保留首次激活/恢复审计、按预算运行的完整性审计、以及每次选中/Claim 前的严格校验。不要用“每次插入都顺便扫描全 Lane 校验所有消息”替代这些专门流程。

新算法不会保证在一次 unrelated Schedule 时发现队尾任意损坏；但被选中的 key、实际 Message 和发送 descriptor 仍必须校验，损坏不能被静默跳过并当作空队列。

### 5.6 预算必须约束读取过程

当前 discovery 在调用 `scanReadyEntries(maxMessages)` 返回 List 后，才在上层逐项累计 bytes/elapsed。仓库已经有 `ShardStore.scan(..., BoundedReadBudget)`、`visit(...)` 和共享 `BoundedReadBudget`，优先复用这些原语，补齐调用链而不新建通用存储框架。[S02][S14]

预算至少覆盖索引 key/value、候选所依赖的 Message/header、必要 binding 读取、实际耗时和返回记录数。一次 head 求值的 DUE/ORDERED/NATIVE、一次 discovery 的 tail/wrap 及其依赖读取应分别共享本次动作的预算，不能给每个子调用重新发满额 budget。现有 `get` 不自动计费，需要在读取边界接入共同预算。[S14]

读取前检查剩余时间及已知长度上限；取得 key/value 后记录实际返回字节。byte budget 阻止继续发起读取，不能声称在不知道 value 大小时能够阻止这一条底层读取；单记录必须能装入已激活的资源 envelope。候选计数、实际读回字节、超出剩余额度的尝试分别记录，不能只统计成功加入 List 的数据。

应用层每轮可停止并让出执行权，但一次底层 seek、磁盘 I/O 或 fsync 不一定能被软件时间预算硬抢占。超时预算是轮次边界和告警条件，不是硬实时保证。

RocksDB 的 iterator 支持 seek、范围上界，并具有创建时的一致性视图；长时间持有还会 pin 资源。因此采用短生命周期 iterator，每次有界读取后关闭，不把 iterator 当作横跨 60 秒窗口的永久游标。[E01]

### 5.7 三态读取结果与提交条件

现有 `visit` 在 elapsed/bytes 预算不足时直接停止，`scan` 可能返回空或部分集合。它的返回值不能单独证明前缀为空。P0 的 head 读取原语必须显式返回停止原因：[S14]

| 结果 | 成立条件 | 调用方动作 |
|---|---|---|
| `FOUND(candidate)` | 找到第一个未被 overlay 排除的候选，key/value/Message 关系全部验证，iterator status 正常 | 与本次新增候选取最小值 |
| `EMPTY_CONFIRMED` | 已到前缀上界或 EOF，期间仅跳过已声明的旧 key，iterator status 正常 | 只考虑本次新增候选；没有新增才可置空 |
| `INCOMPLETE(reason)` | seek 前、跳过旧 head 后、Message 点查前等位置耗尽预算，尚不能确定最小值 | 本次求值未完成，不提交业务 batch |
| 异常 | iterator I/O error、损坏、跨 generation/身份不一致 | 进入现有完整性/Store 错误路径，不当作 EMPTY 或普通预算让出 |

`INCOMPLETE` 是本地控制结果，不注册为客户端业务拒绝码，不写 CommandResult，不推进 applied Source Position，也不调用 Producer。一次消息变更涉及多个前缀或多个 Lane 时，任一必要分支未完成，整个 `HeadPlan` 都未完成。

阶段 A 首版在预算不足后丢弃局部 plan、关闭 iterator，再按相同源位置重新求值。为防止永远卡在第二项，激活配置必须容纳一个最大合法单消息变更的必要候选及依赖字节；elapsed 反复不足应报出明确的预算/资源问题，不能无限静默重试。若未来有界 batch 大到需要跨 turn 求值，再设计有限 continuation，不能默认扩大 limit 或让后续 source record 越过本条记录。

### 5.8 读取视图、写失败与审计调用者

同一 plan 绑定 `(OwnerIdentity, StoreIncarnation, appliedSourcePosition, mutationSequence)`。前缀遍历和 Message/binding 点查必须处于同一 Shard 单写者的一致读取区间，多个独立 iterator 自带的一致视图不等于整个 plan 自动一致。使用现有串行 turn，或显式共享 snapshot；提交前校验绑定没有变化。

WriteBatch 确认成功后，才发布新的 head/revision 和推进内存位置。写失败明确发生在提交前时，保留原 durable state；写结果不确定时按 `ShardStore` 现有规则 fence 并重开核实。禁止仅撤销进程内队列就继续应用下一条 source record。[S14]

两个 candidate 方法也被激活、关闭和 `rebuildReadyIndexes` 调用。切换为 head 查询会消除它们曾经附带的全前缀校验，实施前必须列出全部调用者，区分“求最小值”和“完整审计”。恢复/审计需要覆盖的尾部损坏由显式有界审计处理；不得仅重命名旧方法后宣称审计覆盖不变。

## 6. 新时间索引与 TargetQueueState

### 6.1 保留现有 Column Family 数量

本次不因 Target 模型再加一批 CF。新 key namespace 和版本在现有 `timeline_cf`、`meta_cf`、`id_cf` 等 CF 中分配。

以下是**逻辑 key 设计**，不是已占用的 numeric tag；实际 tag/value version 必须在 Registry 中分配，不能复用旧 Lane key 让旧 decoder 误读。

```text
普通无序候选：
[DUE_VNEXT][targetId][domainSlot][domainGeneration][eligibleAt][sourceOrderToken][messageId][generation]

Native 初次候选：
[NATIVE_VNEXT][targetId][domainSlot][domainGeneration][deliverAt][sourceOrderToken][messageId][generation]

独立过期索引：
[EXPIRY_VNEXT][expireAt][targetId][messageId][generation]

每个源 Shard 内的目标摘要：
[TARGET_STATE_VNEXT][targetId]

计费：
[TARGET_USAGE_VNEXT][targetId][accountingIncarnation]
[TENANT_TARGET_USAGE_VNEXT][tenantScope][targetId][accountingIncarnation]  // 按需启用
[SHARD_USAGE_VNEXT]
```

普通候选时间为 `max(deliverAt, retryEligibilityAt)`。Native 索引只包含符合条件的初次 opt-in 消息，按 `deliverAt` 排序，在同一执行域内使用共同的运行时 lead 计算 eligibility。基础单域路径使用 Target 的共同 policy；E2 多域的授权范围见 §7.10、§8.7。索引不复制 payload。

从 B1 起即冻结最终 domainSlot/domainGeneration 布局，C1/C2 只启用一个域，E2 实现多域选择和生命周期，不为单域再建另一套 key 格式。每个域的前缀符合 §8.6 的可共队条件，不混放独立阻塞的上下文。`accountingIncarnation` 隔离计费生命周期，不参与 TargetPartitionId；旧 incarnation 的未释放义务不能被新计数器覆盖，具体编码在 B4 冻结。

### 6.2 摘要最小字段

```text
TargetQueueState {
    targetId
    headRevision
    sourceOrderedControlVersion
    sourceOrderedAdmissionState
    accountingIncarnation
    nativeIndexLeadCapMs
    domains[0..K] {
        domainSlot, domainGeneration
        dispatchCompatibilityRef, controlScopeRef, nativePolicyScopeRef
        ordinaryHead? { key, messageId, generation, eligibleAt }
        nativeHead?   { key, messageId, generation, deliverAt }
    }
}
```

配额放单独 counter key；凭证原文不进入摘要；健康状态、当前 next-wake、DRR deficit、探活 backoff 不进入业务持久摘要。

摘要保存的是已应用状态的最小投影，不应复制完整 Prepared Publish、完整 Profile 或一套 Lane 证书。

基础活动路径的 domains 只有一个元素，ordinary/native head 只在该元素保存，不在 Target 外层重复持久化第二份；零个域只用于没有可服务工作、仅保留目标控制的状态，不能产生 READY。`dispatchCompatibilityRef` 引用 B2 固定的执行/控制兼容要求；它不随每个 Profile 版本、credential lease 或 Producer 连接重建而增长。`nativePolicyScopeRef` 固定域内共同授权范围；实时 publication、effective lead 与有效期留在受验证的 policy cache，进入 Admission 后按原契约冻结。`nativeIndexLeadCapMs` 仍是 TargetQueue 的固定上限，各域不得越过。字段的 tag、presence、digest 域尚未分配，属于 B1–B4 的协议产物。

### 6.3 新增、取消、改期与 Claim 的索引规则

| 事件 | 普通索引 | Native 索引 | Expiry | Head |
|---|---|---|---|---|
| 首次 Schedule | 添加 | 符合条件则添加 | 添加 | 必要时改变 |
| Cancel 成功 | 删除旧 key | 删除旧 key | 删除旧 key | 删除 head 才取 successor |
| Reschedule 成功 | 删旧 generation、加新 generation | 按新 generation 的授权重新建立 | 替换 | 同 batch 重算 |
| Claim 成功 | 消费本次工作对应 key | 同一 generation 的另一路也删除 | 仍按业务状态保留 | 原子推进 |
| Claim 可逆撤销 | 恢复原工作 | 仅原工作仍具备 native 资格时恢复 | 保留 | 原子恢复 |
| Native Admission 已消耗、明确未发送 | ordinary retry | 不再创建 native candidate | 保留 | 原子更新 |
| 已 Admission 且 UNKNOWN | 按原 uncertain policy 处理 | 禁止重新伪装 initial native | 保留/关闭新 Admission | 保留旧 attempt 义务 |
| terminal | 删除可逆候选 | 删除 | 按状态删除 | 推进，但不删除未决 attempt |

Claim 不等于成功发送；删除可调度索引必须伴随可恢复状态转移，不能把消息直接丢进一个纯内存发送队列。

## 7. Handoff：60 秒窗口、1 秒 tick 应如何工作

### 7.1 60 秒是提前交接额度，不是必须读进内存的窗口

新设计使用：

```text
普通资格：earliestUtcNow >= deliverAt
Native 资格：earliestUtcNow >= deliverAt - effectiveLeadMs
```

当 effective lead=60 秒时，等价于有资格考虑 `deliverAt <= earliestUtcNow + 60s` 的 native 消息。但一次只取有执行预算的 K 条，不要求把整个 60 秒窗口展开成内存列表。

1 秒是调度唤醒/兜底周期，不代表每秒必须重新扫描所有相关消息，更不代表每秒只允许执行一个 batch。

### 7.2 示例

假设当前是 12:00:00、lead=60 秒，且资源充足：

| 消息 | deliverAt | 12:00:00 的动作 |
|---|---|---|
| A | 12:00:30 | 可 Native Claim/Admission |
| B | 12:00:59 | 可 Native Claim/Admission |
| C | 12:01:00 | 边界满足，可 Native Claim/Admission |
| D | 12:01:01 | 尚未达到候选时间 |

A/B/C 完成 Claim 状态转移后，不再留在可调度的 ordinary/native 索引里。12:00:01 到来时，主要处理新达到资格的 D，以及上一轮因预算没有处理的合法剩余工作，而不是把 A/B/C 当作窗口数据重新发送。

如果第一次只能 Claim A，则 B/C 仍然在持久索引。下一轮继续取它们是正常的队列排空，不是把它们“删除窗口重叠部分”。

### 7.3 不采用“只扫 lastWindowEnd 到 newWindowEnd”作为正确性依据

反例：

```text
12:00:00 已经扫到 deliverAt=12:01:00。
12:00:02 新收到 E，deliverAt=12:00:40。
```

如果永久从 12:01:00 之后继续扫，E 会被漏掉。Reschedule 把消息改到更早时间、Claim rollback、retry 重新入队也会造成同类问题。

正确性依据是“当前最小尚未被状态机消费的 key”，不是“上次时间窗口推进到了哪里”。跨 tick cursor 只是性能提示；新增或变更 head 必须可以重新唤醒。

### 7.4 双 head 不能直接删除

ordinary 和 native 使用不同的资格条件。Handoff 被禁用、snapshot 过期或 runtime lead 变小时，一个“静态最早 native 候选”不能挡住已经 ordinary due 的消息。NDIP-1 已经专门修正过这个问题。[S10]

因此保留：

```text
一个 target 调度入口
    ordinaryHead
    nativeHead
```

它们共享配额和公平份额，不变成两个 Lane，也不变成两个 Scanner。

这里的“两路 head”以 §8.6 的可共队条件及 §7.10 的共同运行时 policy 为前提。一个 Worker target 仍可从多个源 Shard 的 head 轮转选择；存在多个不可互换执行域时需要 §8.7 的有界候选摘要，不能把“两路”理解为任何执行组合下全集群都只保存两个候选。

普通消息已经到达 `deliverAt` 时优先执行 ordinary 分支；同一 generation 只允许一个有效 current work。Native 分支成功 Claim 时同步消费它的 ordinary 索引，反之亦然。

### 7.5 合并 Lane 后必须处理“不同 Profile 的最大 lead 不同”

这是不能省略的约束。

例如 A 比 B 更早到期，但 A 最多只能提前 5 秒，B 可以提前 60 秒。直接把二者放到按 deliverAt 排序的 native 队列，看到 A 尚未可交接就停止，会漏过本轮已经可交接的 B。

**本方案选择目标级统一 native 索引上限，避免再建任意数量的 policy 子队列。**

```text
每个 TargetQueue 的 nativeIndexLeadCapMs 固定。
运行时 effectiveLeadMs 必须在 [0, nativeIndexLeadCapMs] 内。
进入该 native 索引的消息，pinned Profile 必须允许至少 nativeIndexLeadCapMs。
```

其余显式 opt-in、但最大允许 lead 更小的消息仍走 ordinary；ALLOW 表示允许，不等于必须交接。这个保守回退必须在文档和诊断中明确，不能谎称它已进入 native 调度。

对于提问中的配置，新建目标队列可采用 cap=60 秒，并只让 Profile 最大 lead 至少 60 秒的消息进入 native 索引。未来把 runtime lead 从 60 改为 30，仍无需重写每个消息 key。

不能增大 `nativeIndexLeadCapMs` 后假设所有存量 Profile 自动同意了更早交接。增大 cap 要经过显式重建/迁移或新队列格式下的控制流程；不允许直接更新一个标量越过旧消息授权。

这一设计有明确取舍：牺牲少量不兼容 Profile 的提前交接机会，换取同一目标内单一、可预测的 native 排序，不引入 N 份 policy Lane。

### 7.6 动态 policy、SHADOW、Disable

保留现有 signed snapshot、scope、generation、有效期和 Admission 冻结的语义。新身份下共同 Target policy scope 按 §7.10 定义；不能把旧 Lane/Profile scope 的签名 bytes 改个 ID 继续使用。

SHADOW 只计算、记录，不提前 Claim/Admission。Disable 停止新的 native 授权；已经进入 ownership 的请求仍按原 attempt 处理，不伪造 definitive-not-sent。普通 due 不受 native policy 可用性影响。[S10]

policy 变化只重新计算该 target 的 `nativeHead.deliverAt - effectiveLeadMs`，不全量更新窗口内的 key。

### 7.7 唤醒机制

内存中维护有界的 target 唤醒结构；每个 target 至多一个有效登记。下一次动作由这些事件触发：

```text
head 被更早的 Schedule/Reschedule 改变
当前工作 Claim/终态后出现 successor
到达 ordinary/native 的下一个资格时间
in-flight permit 释放
target backoff 到期
policy / channel / credential 状态改变
周期性安全重查
```

不能每次用版本号 push 新 heap node、任由旧节点无限累积。使用可更新 heap，或者对 stale entry 数设硬界并做有界重建。

为了避免 missed wake，head revision 更新必须在业务 WriteBatch 成功后由单写者发布；注册睡眠与检查 revision 要有明确顺序。通知可合并，不能把每个 message mutation 都变成一份无界事件对象。

### 7.8 没有预算时不要扫描窗口

目标 blocked 或没有全局/target 执行许可时，保留 head 和 next-wake，不继续遍历其 backlog。一次探活失败只延长该 target 的退避，不能不断取新消息来“测试下游好了没有”。

容量释放后的下一轮可继续排空，不必等完整 1 秒 tick。每轮仍受 record/byte/elapsed budget 和公平轮转限制，不能用 `while(due)` 独占事件循环。

### 7.9 60 秒不保证一定准时

交接路径仍有调度、materialization、Admission append/apply、Journal、ownership marker、目标写入等成本。60 秒只是预留时间；若窗口内到期量超过整个链路的处理能力，仍会晚到。[S10]

配置应由以下预算约束，而不是简单把 tick 调小：

```text
lead 应覆盖健康范围内的：
扫描/调度等待 + materialization + Admission 排队/应用
+ Journal + ownership marker + target append + 余量
```

已经到期的 ordinary 工作应获得保留服务份额；early handoff 只能使用受限份额/空闲能力，不能提前 60 秒的工作占满所有 permit，让现在到期的消息反而等待。

### 7.10 固定 cap 之外还需要共同运行时 policy

当前 `HandoffPolicyScope.digest` 包含 tenant routing scope、Destination Profile、Capability Profile、目标资源、partition、ordering mode、allowed path bits 与 artifact set。同一物理目标可以得到多个独立 scope。[S15]

只把所有 Profile 的最大 lead 统一为 60 秒仍不充分。例如 A 的 deliverAt 更早但 policy 已 DISABLED，B 的 deliverAt 稍晚且 policy 为 ENABLED；仅检查 A 后停止，会挡住已经允许提前交接的 B。

基础单域路径采用以下规则；E2 启用多个真实执行/控制域后，每个域内部继续遵循共同 policy 规则，所有域共享 TargetQueue 的固定 cap。多域不授予自动按 Profile 拆 policy 的权限：

1. 基础单域 TargetQueue 的 Native 分支使用一个共同 `nativePolicyScopeRef`，其 publication 决定共同 mode、effective lead、允许路径及 lease 有效性；多域时共同范围收在真实执行/控制域内。
2. 消息是否显式 opt-in、是否首次 attempt、是否允许固定 cap，在 source apply 建立 Native 索引时依据 pinned binding 判断。FORBID、小 cap、不满足能力组合的消息只建 ordinary 索引。
3. 同 Native 前缀内不再保留独立的 Profile 级 enable/disable 或独立 lease 作为“只阻止某个 head”的运行时开关。基础单域路径中需要此能力的绑定不进入共同 Native 索引，ordinary 回退原因必须可诊断；E2 只在已支持的独立域内表达真实隔离需要。
4. pinned Profile/Capability 的完整性仍按绑定验证；损坏不是一个可以跳过该消息的正常 policy 结果。执行上下文的其他动态门继续满足 §8.6。

共同 scope 的 canonical 输入至少明确 policy authority namespace、TargetPartitionId、允许路径集合及所需 artifact authority；`dispatchCompatibilityRef` 是否需要进入 scope，由 B3 依据实际授权边界冻结。它不通过 Profile 数量生成新的 Target ID，也不以移除 tenant hash 的方式授予跨租户控制权限。新 scope 必须有新的版本/签名域和独立可信发布，不能重新解释旧签名。

| policy 变化 | 对索引和本地候选的影响 | Admission 边界 |
|---|---|---|
| 60→30 秒，仍满足固定 cap | 更新共同 next-wake，刷新本地 Native 资格；不逐消息改 key | preparation 使用当前 publication |
| SHADOW / DISABLED / lease 过期 | 整个共同 Native 分支停止产生新的提前工作；ordinary head 继续 | 不得创建新的提前 Admission |
| policy 刷新后重新 ENABLED | 从现存 Native head 重新判断；由 policy 事件或安全重查唤醒 | 重新验证 current head/ref |
| 固定 cap 增大 | 显式重建/迁移并验证存量授权 | 不以 live scalar 更新越过 pinned 上限 |
| 已有冻结 Admission，随后 policy 更新 | 保留原 attempt、snapshot、hash 和恢复义务 | Producer 边界按现有冻结 snapshot/lease 规则验证，不用新值改写历史 |

旧 Profile-scoped 签名与新 Target scope 的共存只属于有限迁移/旧 attempt 恢复。迁移前必须逐项决定待发送消息是否进入共同 Native 索引；不能为保留旧开关而把任意数量的 policy 子队列偷偷变成新常态。

## 8. 发送调度与 Producer 复用

### 8.1 一份 Target 公平份额，不再按 Profile/bucket 放大

Worker 发送调度先在可服务 target 间按字节成本做 bounded DRR；选中 target 后，在有资格且有预算的源 Shard head 间轮转。Shard 本身仍由其 owner 进行状态变更，调度器只持有轻量候选。

同一个 target 增加 Profile、ordering key 或 Producer slot，不得获得额外 weight。增加通道只提高有界执行并发，不改变逻辑目的地的公平权。

源 apply、lease、Outcome、expiry 与发送的 work-class 隔离继续保留。它们解决状态机工作的推进问题，不再各自维护一份新的目标发送公平性权威。

### 8.2 同一个 target 并不必然只使用一个 Producer

推荐的规则：

| 情况 | 处理 |
|---|---|
| 同 target、相同认证/编码/结果能力，仅 Profile version 或 retry 参数不同 | 复用兼容通道/池，不创建新的目标调度入口 |
| 不同 tenant，但实际共用同一受控服务端写权限 | 可复用；tenant 授权与 quota 不消失 |
| 认证范围不同，无法证明等价 | 首版同 Shard/target 拒绝新增不兼容共队绑定；有界隔离执行域扩展见 §8.7 |
| Kafka 普通发送 | 可以评估在同 Worker 复用兼容 Producer；必须保留目标级 admission/buffer 隔离 |
| Kafka transactional receipt | 保留事务通道的单事务状态、stable transactional identity 与恢复域 |
| Pulsar Managed Journal/固定 sequence | 按 source Shard + target + channel slot 保留可恢复 sequence 域，不把多个旧域强行混成一个 Producer |
| 严格 ordering key | 使用必要的 key barrier，不用“每 key 一个 Producer”表达顺序 |

Kafka 官方 API 将 Producer 定义为线程安全并建议在线程间复用，但这不等于其默认实现自动满足本项目的 guarded resource、租户隔离和事务要求。[E02]

### 8.3 不新增跨 Shard 全局 sequence 服务

Pulsar sequence 的含义与 producer/topic 绑定。现有 Managed path 的 Journal 负责映射与恢复，合并 scheduling identity 不能重写已经存在的 sequence 或 producer identity。[S10][E03]

默认新通道身份至少区分：

```text
sourceShard
+ TargetPartitionId
+ 真正不兼容的执行上下文
+ 有界 channelSlot
+ channelGeneration
```

同一 source Shard/target 下的兼容 Profile 复用这些通道。不同源 Shard 的强能力通道不在本次强行合并；为此引入一个全局持久 sequence allocator 会抵消简化收益。

### 8.4 不同时放开 P1 batching 和并发关联限制

当前 guarded Pulsar 路径对 unresolved SEND、typed response、sequence 和证据关联有严格要求。此次不能在合并 Lane 的同一个改动中顺手打开 batching 或让一个原本单未决请求的 channel 发送任意多个请求。[S09]

先保持已证明的通道契约，使用有界 slot 提高并发。若需要多未决/批量协议，另行改变 P1 请求与回执的精确关联方式，再验 response loss、重连重发、部分失败、sequence 恢复。

### 8.5 共享资源的失效范围

一个 source Shard 失去 lease，应立即关闭该 Shard 新请求的权限，不得误关闭其他仍合法 Shard 的整个共享 Producer。共享通道要有明确引用计数、请求归属与 teardown 规则。

反过来，共享 Producer 真正故障时，其影响范围就是该 Producer 的所有使用者，不能仍承诺“只影响原来的一个 Lane”。为减少跨目标故障扩散，默认先在同一 target 内复用，不急于跨许多目标共享一个无限大的 buffer。

对于同一 target 下无法兼容的认证上下文，不能声称不存在额外隔离成本。第一阶段可拒绝不兼容的新绑定；已有此类数据保留旧通道直至安全排空。不能把不兼容上下文的 head 永久卡在公共队列最前面，却宣称其他绑定不受影响。

### 8.6 首版可共队条件与失败处理

首版每个 `(sourceShard, targetId)` 的默认无序前缀只容纳一种已证明可共同调度的执行类别。同类可以使用多个 Producer slot；slot 数量不会创建新的持久队列、Target ID 或发送 weight。

兼容检查至少覆盖：

| 维度 | 可以共队 | 不满足时的处理 |
|---|---|---|
| 认证与资源权限 | 任一候选可由该类别的合法通道执行；凭据轮换不改变授权语义 | 新绑定确定性拒绝；存量转换报告冲突 |
| 编码与结果能力 | 实际 codec、receipt/去重保证及 transport 能力要求兼容 | 不把强能力请求降成普通发送 |
| 事务、sequence 恢复域 | 新未 Admission 工作可按已冻结规则分配通道；旧 attempt 的通道固定 | 旧 obligation 沿旧域恢复，不换 producer/sequence |
| 控制范围 | 队列成员共享会阻止发送的控制门，或差异已被专门的候选结构表达 | 不能用公共 head 代表多个独立暂停范围 |
| 发送 permit | 目标共享预算及该类别通道的可用性可以由类别 head 表达 | 独立 tenant/channel permit 若会挡单个 head，也属于不兼容因素 |
| 消息参数 | Profile 版本、payload、retry 次数/间隔可不同；retry 时间已进入 ordinary key | 不因这些参数本身复制调度实体 |

`可共队` 比“物理目标相同”更严格，也比“Producer 客户端支持线程安全”更严格。检查结果绑定规范化的执行/控制要求，不保存凭据秘密，不把无关 Profile bytes 整体 hash 成另一种 Lane。

反例固定为合并验收用例：A 的到期时间早于 B，A 依赖失效凭证或被独立 Pause，B 使用健康上下文。首版在注册/迁移时识别该不兼容组合，不把二者写入同一个仅有单 head 的前缀；不能写入后靠逐条向后扫描找 B。拒绝需有 Registry 注册的稳定结果，并按 Source Position 消费命令，不停住整条源日志。

同类通道全部不可用时，该类别整体等待；有健康且可互换 slot 时，未 Admission 候选可以选择健康 slot。Admission 后的 producer/sequence/事务身份继续固定，不能通过重新选 slot 绕过 UNKNOWN。

同一个 Worker 下不同源 Shard 的 head 仍单独可见。Shard A 失去 owner 或其通道不可用时，可以跳过其轻量候选继续服务 Shard B；不需要扫描 Shard A 的消息尾部。

### 8.7 多个不可互换执行域的有界扩展

基础路径默认 `maxExecutionDomainsPerShardTarget = 1`；大于 1 的完整实现纳入 E2，完成前不能在配置中悄悄打开。若实际存量必须保留多个独立执行/控制域，设计必须同时引入有界候选结构，而非仅增加 Producer：

```text
TargetRuntime                         // 仍只有一份 target weight 与总预算
    sourceShard A
        domain 0: ordinaryHead / nativeHead / blockedUntil
        ... 至多 K 个 domain
    sourceShard B
        ... 至多 K 个 domain
```

此处 domain 是实际不可互换的执行/控制要求，不以 Profile ID、ordering key 或 bucket 派生。建议采用按 `(targetId, domainSlot)` 分隔的候选前缀与小型摘要，Target ID、外层公平份额和生命周期仍统一。数字 tag、domain generation 和迁移布局纳入 B 的完整 schema 冻结，由 E2 实现。

被选 target 内只查看至多 K 个 domain head，跳过被阻止的域，并公平选择可服务域；某个域失败不得降低其他域的可见性。Native 域自身仍须满足共同 policy 规则。禁用的旧域有未决 attempt 时保留槽位与费用，不能立即复用 generation；超过 K 时确定性拒绝新增，不能扩成无界 map。

扩展未完成而存量又不满足 §8.6 时，该目标迁移保持阻塞并给出冲突清单。它不阻止阶段 A，也不要求其他无冲突目标回退到完整 Lane 模型。

## 9. 严格顺序：保留必要 barrier，不保留一整套 Lane

默认 BEST_EFFORT 的 target 队列不增加 key 级状态。

启用严格模式时，Ordering Domain 的语义继续绑定 tenant、原有 routing/binding 边界和 ordering key。同域必须路由到同一源 Shard；不能因为 Target ID 去掉了 tenant/Profile 就把原来不同的域混为一个域。

需要的持久结构是：

```text
ORDERED[targetId][orderingDomain][deliverAt][sourceOrder][messageId][generation]
ORDER_STATE[targetId][orderingDomain] = executionDomainRef, orderingContractRevision,
                                      lastAdmittedOrder, unresolvedAttempt/barrier
ORDER_HEAD[targetId][domainSlot][domainGeneration][headEligibility][orderingDomain]
    // 每个 OrderingDomain 只暴露一个允许服务的 head
```

这些是启用严格功能所必需的索引，不拥有独立 target weight、不要求独立 Producer、不复制一份 target circuit。

同域最多一个 unresolved head，未知结果没有证据时不能让后继通过。不同域可以由同一个 target runtime 公平推进。

`lastAdmittedOrder` 与新增迟到拒绝规则作为完整任务 E5 设计和实现，在 B 中明确新语义、版本及旧数据处理。A–D 验证基础新路径时保留当前 strict domain、未决 head、迟到处理和 replay 语义；E5 激活后才对显式绑定新排序契约的工作使用新拒绝规则。已有 strict 数据不能被临时新增的规则追溯拒绝。

Native delivery 与严格模式的禁止组合沿用 NDIP-1；不在此改造中扩展消费端顺序保证。[S10]

## 10. 删除高频持久公平性，保留可恢复业务事实

### 10.1 持久化边界

继续 durable 的是 Message/current work、Claim、Admission、attempt/evidence、取消与关闭控制、时间索引、quota、结果与 source position。

以下默认成为进程状态：

```text
DRR deficit
active ring 顺序
last-served round
recovery first-pass 已服务集合
下一次探活/退避时间
当前 next-wake
discovered head 去重缓存
```

它们丢失可以影响下一轮先服务谁，不应改变一条已应用命令的业务结果，也不能制造 Producer 首次发送权。

### 10.2 明确调整公平性承诺

不再保证跨任意次数 crash/迁移还能精确保留 DRR credit。保证范围改为：

> 在连续 Owner/Worker 运行区间、可用容量和有界 target 数等前提下，持续可服务目标获得有界服务机会；恢复后先让每个 eligible target 获得一次机会，再允许重复服务。

这是契约调整，不是单纯将 `sync=false`。不能一边删除持久 fairness，一边保留文档里精确跨重启公平性的承诺。

### 10.3 恢复流程

从有界 TargetQueueState 集合恢复两路 head，构建进程内 ring/heap，deficit 清零或使用配置初值。未 due 的 target 不占恢复首轮的待服务集合；没有足够 byte budget 的 head 也不能卡住其他可服务目标。

恢复不加载全部延迟消息正文。head 摘要损坏/缺失则进入原有 fenced repair/restore 路径，不把“缓存可重建”当作忽略 durable 索引损坏的理由。

旧五个 scheduler projection 的 reader 只在有限升级窗口用于识别旧数据，不再被新格式 writer 更新。等旧格式不再是允许恢复点后清理，不长期维护两套 fairness writer。

### 10.4 空 poll、恢复首轮与计量口径

普通 poll、无 eligible target、预算用尽但未改变业务状态，只更新有界进程状态，不为 deficit/ring/round/cursor 单独调用 `store.write`。Claim 的持久化、回退与普通/native sibling 去重仍按原业务边界执行，删除 fairness persist 不等于删除这些边界。

恢复首轮从有限、已加载的目标摘要构造 eligible 集合：排除未来到期、被控制门阻止、无法装入本轮已认证 byte envelope 的候选。对首轮集合中每个持续可服务 target 提供一次机会；新进入的目标加入后续有界轮次，不能不断扩展首轮集合使它永不完成。精确的 membership、blocked 移除和重新加入规则及服务间隔上界在 B5 冻结。

原来使用 durable DRR generation 的指标必须改为带 Owner/Worker interval 的进程轮次或实测服务间隔，不能把新内存 round 声称为跨重启单调值。这个必要的公平性指标调整纳入 B5/C3；其他 durable SLO outbox 与业务审计在基础路径中保持原契约，整体观测模式分层由 E4 完成。

## 11. Quota、背压与资源配置收敛

### 11.1 用局部 counter 更新替代整个集合的计算与写入

每个 target/tenant-target counter 独立编码。一次 Schedule 只写受影响 target counter、必要 tenant counter 和 shard aggregate，仍与业务变更同 batch。

当前 `replace` 会对全部 entry 统一 revision 并重新排序，`aggregateQuotaUsage` 会重新求和。[S16] 新路径同时满足以下规则：

```text
QuotaDelta {
    affectedCounterKeys
    priorCounterRevisions
    perCounterChanges
    shardAggregateChange
    expectedMutationSequence
}

nextCounter.usage = checkedAdd(priorCounter.usage, localDelta)
nextCounter.revision = checkedIncrement(priorCounter.revision)
nextAggregate = checkedAdd(priorAggregate, shardAggregateChange)
```

只有变化的 counter 更新自身 revision；其他 entry 的 bytes 和 revision 保持不变。Shard aggregate 的 revision/position 单独绑定本次 mutation，不要求所有 counter revision 相等。revision 初值、溢出、accounting incarnation、retire 条件与 digest 在 B4 注册。

target usage 是既定计费维度的主视图，tenant-target usage 是相同费用的租户投影，不能把二者重复相加。Outcome reserve、retained legacy attempt 等独立账本按每个 capacity dimension 的归属计算 delta；每一笔费用必须有且只有一个 aggregate 来源。

进程内使用按完整 counter identity 的局部查询/更新，不在每条命令上复制、排序或 hash 全部 target 集合。先计算不可变的小型 `QuotaDelta`，WriteBatch 成功后再发布内存变更；失败不留下半更新 aggregate。重复 source replay/命令去重不重复扣增费用。

恢复/显式审计可以遍历完整 counter 集合重新求和，核对 durable aggregate、Message/reservation/attempt 账本及 revision 关系。发现不一致时进入原有 repair/restore 流程，不能在正常 Schedule 中默默重置 aggregate。新格式不能仍生成旧完整 map 作为高频“兼容投影”。

不要把 per-target counter 的减少/删除与 Producer pool 的物理释放混为一谈：逻辑消息终态可以释放 active quota，尚未完成的 request/zombie、retained payload、历史结果仍占各自资源。

### 11.2 同一 target 的总额度不能在合并时放大

旧多个 Lane 的资源合并应重算 target usage 和新 grant，不能为每个旧 Lane 都给一份新的 full target cap。Worker 总 request/byte pool 仍只有一份。

tenant 路由原本属于不同源 Shard 时，静态 shard grant 的总和继续受 tenant hard quota 约束。将 target 统一只改变发送共享方式，不自动提供跨 Worker 的全局瞬时限流。

### 11.3 面向运维的少量参数，内部仍做完整边界检查

建议主要暴露：

```text
每 Worker：最大 owned shards、总内存/磁盘 envelope、总物理 in-flight requests/bytes
每 target：pending 上限、in-flight requests/bytes、发送速率、权重、backoff
调度：每 turn records/bytes/elapsed、周期性安全重查上限
Handoff：目标 native 索引 cap、effective lead、early 工作预算
后台：checkpoint/GC I/O 与恢复保留空间
```

现有更细的 capacity dimension 可由这些配置与认证参数派生，集中校验。不是简单删除 FD、native memory、zombie、WAL/temp 等真实物理约束，也不是每条消息都重新构造一份完整容量证明。

### 11.4 坏目标不能拖停源日志

目标熔断、发送失败、没有 target permit：只停止该目标新的 Claim/Admission。

目标 backlog 达到已激活逻辑 grant：继续按 Source Position 消费该目标的新 Schedule，并确定性拒绝增加 usage 的请求；已有 Cancel/Outcome/terminal/GC 继续推进。

共享磁盘/RSS/FD 已触及安全边界时，仍按真实共享故障域暂停，不能为了“一个 target 一份队列”而承诺物理资源故障也只影响一个目标。[S09]

### 11.5 同一日志的控制积压问题不在此偷改

Admission、Outcome、Cancel、Time Fence 仍可能排在大量入口记录之后。发送调度简化不能解决已经形成的 source prefix 等待。

应以 shard 未应用 bytes/records、最老年龄约束入口增长，并为 system writer 保留资源；不增加第二条能越过业务日志的“高优先级状态日志”。

## 12. 时间、取消与未知结果不变

### 12.1 两种 delivery contract 继续分开

`NEREUS_MANAGED_NOT_BEFORE` 在 deliverAt 前不普通发送；`PULSAR_NATIVE_DELIVERY` 允许提前持久化并设置 Pulsar deliverAt，后续行为遵循 Pulsar 原生语义。

Pulsar 官方文档说明延迟投递适用于 Shared/Key_Shared，其他订阅会立即分发。因此“提前 60 秒只是透明搬运，不改变任何消费者时间语义”不是本方案承诺。[E03]

### 12.2 Cancel 的不可逆边界

同一 generation：

```text
仅有可逆 Claim：Cancel 可以按 Source Position 获胜。
Admission 已经生效：Cancel TOO_LATE。
HANDED_OFF：不能宣称 Pulsar 消息仍可由 Nereus 撤回。
```

target 合并不改变这一规则。提前交接可能提前结束取消窗口，SDK/Query 必须显示实际 contract 和状态。[S09][S10]

### 12.3 无法确认的发送不能回到普通待发送状态

Owner loss、response loss、逻辑超时或未知 teardown，按原 attempt 进入 UNKNOWN/UNCERTAIN 处理。保留旧 obligation；允许 possible-duplicate retry 的策略也不能把旧义务抹掉。

缓存中的“未完成”不构成未发送证据；Producer pool 复用不提供远端 exactly-once。

## 13. 其他简化：做减法，但不给热路径增加新框架

### 13.1 校验集中到四个权威边界

建议集中为：

```text
入口 decode / prepare：格式、不可变 identity、caller 允许范围。
source apply：可重放语义、状态前置条件、quota 与控制顺序。
Claim / Admission preparation：当前 Owner、Store、target/channel、时间与资源。
真正交给 Producer 前：精确 attempt、首次调用 token、仍有效的 live lease/guard。
```

内部同一次调用中的 immutable typed object 不应被反复 encode/decode/re-hash。跨队列等待、Owner/Store 变化、凭证续租等边界的重新验证必须保留。

正式入口不得接受自由拼装的 raw state 或伪 Owner；简化 wrapper 数量，不等于公开原来 package-local 的裸 WriteBatch 方法。

### 13.2 常规指标与认证审计分层

常规 scan lag、发送耗时、计数、队列长度、histogram 使用有界异步指标路径；导出失败上报 gap，不默认卡住消息状态机。

业务审计、已承诺的命令结果、发送证据继续持久化。若某项发布认证确实要求逐事件 durable SLO，可启用明确的认证模式，并单独计其成本；不能在关闭后继续宣称指标样本零丢失。

### 13.3 Compatibility 限定终止条件

旧 synthetic ledger、旧 Lane value、legacy enqueue bridge 的兼容逻辑集中于升级边界。新 writer 不创建 legacy bytes；没有历史数据的本地环境不应为了理论兼容永久携带所有旧路径。

有历史数据时必须保留它们的读取和恢复能力，直到相关 source/recovery/evidence window 结束。不能全局搜索 `legacy` 后直接删除。

### 13.4 Object Store 与 AUTO_FAST 不作为这次重写对象

Object Store 不只服务大 payload，也承担 checkpoint。默认 inline 模式可以不暴露复杂大消息 API，但不能因此删除恢复所依赖的 Object Store。

AUTO_FAST 和 Managed 的所有权、查询/取消能力不同，继续保持显式分支。无需为简化 Lane 将二者合并成一个含糊的“快速发送”状态机。[S09][S10]

### 14.1 最小内部接口形态

```java
// 建议接口形态，不是可直接编译的当前仓库代码。
interface HeadIndexUpdater {
    HeadPlanResult plan(ShardReadView view, MessageMutationDelta delta, BoundedReadBudget budget);
}

interface TargetDispatchScheduler {
    void onCommittedHeadChange(ShardId shard, TargetPartitionId target, long revision);
    DispatchCandidates poll(TrustedUtcIntervalEvidence time, DispatchBudget budget);
}

interface ProducerChannelProvider {
    ChannelAcquireResult acquire(ShardId shard, TargetPartitionId target, ExecutionRequirements requirements);
}
```

单前缀 `HeadReadResult` 使用 §5.7 的三态；`HeadPlanResult` 只有 `COMPLETE(projections, viewBinding)` 或 `INCOMPLETE(reason)`。COMPLETE 内可以包含已确认的空 head；损坏和 I/O error 仍抛出明确异常。`ChannelAcquireResult` 区分取得 lease、暂时不可用和执行要求不兼容，不能用同一个 null 混合表达。

`DispatchCandidates` 至少携带源 Shard、Target、head identity/revision 和候选分支，不具有发送权；取得的 `ChannelLease` 不替代 Publish Admission；`plan` 不提交 DB，最终由原有 shard 单写者统一提交。以上为建议接口，不是当前仓库已存在的类型。不要为这三个接口再创建一个可自由插拔的通用工作流引擎。

## 15. 迁移：不能只重新 hash 旧 Lane ID

旧 Lane 身份进入 Message、ScheduleBinding、Claim/Admission、prepared hash、Journal mapping、producer identity、evidence cursor、terminal guard、quota、checkpoint 等关系。[S01][S09][S10]

因此直接修改 `DestinationLaneId.derive` 会让旧数据“解码成功但指向了另一套身份”，比明确的版本不兼容更危险。

### 15.1 分开两种变更

**A. 无业务 schema 变化的性能修复。** 前缀取 head、减少不必要解码、扫描计量，优先用现有格式落地并回归。这一步不需要先部署新 Target 身份。

**B. Target 身份/存储模型切换。** 分配明确的新 storage/protocol version，更新 required generation set 与 decoder。旧 reader 必须拒绝不认识的新格式，而不是按旧 Lane 解释。

### 15.2 无需保留数据的本地环境

只有经过明确识别的 disposable 测试环境，才能按已有环境规则重新初始化并导入测试数据。本次文档不授权删除任何运行数据。

优先在这类环境验证新索引和 Producer 通道的完整链路，避免为了本地写代码先引入一轮无关的生产治理阻塞。

### 15.3 有持久数据的环境

建议第一版采用维护窗口内的 fenced 转换，避免在线双 writer：

```text
停止新的目标身份切换和新 Schedule 选择
    -> drain 可撤销工作、停止新 Claim/Admission
    -> 取得一致的 checkpoint + source cut
    -> 保存旧 source/evidence/channel 恢复材料
    -> 在新 Store Incarnation 中转换可安全转换的待发送状态
    -> 对已 Admission/UNCERTAIN 保留 exact legacy obligation
    -> 校验消息数、字节、quota、head、身份和 barrier
    -> 发布新 checkpoint/catalog 与版本激活
    -> 按原 source successor 继续 replay
```

转换器只把尚未进入不可逆 Admission 的调度投影重建为 Target 索引。旧 Admission/prepared bytes/hash/Journal/sequence/evidence 不被改写；它们沿原恢复域完成，之后才释放。

### 15.4 Migration collision 逐项处理

多个旧 Lane 合到同一 Target 时，要显式审查：

| 冲突 | 处理 |
|---|---|
| Profile 不同，但物理目标/执行要求兼容 | 统一 target；保留各 Message 的 ProfileRef |
| 不同 unordered bucket | 合并，无业务排序承诺转移 |
| 不同 tenant | 目标身份可统一；授权与计费仍分开 |
| 不同 credential/outcome/sequence 恢复域 | 不重写旧域；保留有限旧通道排空或拒绝本轮合并 |
| 部分旧 Lane 已 Pause/Close | 不能用任意 OR/AND 把范围扩大或重新开放；保留旧绑定的控制效果 |
| strict domain 存在 unresolved barrier | 原样保留；不能在新队列放行后继 |
| native 最大 lead 不同 | 采用目标统一 cap；不满足的未发送消息 ordinary 回退，明确报告 |
| native 最大 lead 相同，但旧 scope/mode/lease 独立 | 按 §7.10 建立新共同 scope；不具备新授权的未 Admission 消息只走 ordinary，旧 snapshot 不改签名 |
| 公共 head 后存在独立凭证/控制/permit 域 | 首版拒绝不兼容转换；只有 §8.7 扩展经过验收后才能映射到有限 domain slot |
| quota entry 原来统一 revision | 保留旧证据，初始化新 counter 各自 revision 和 aggregate revision；不要求继承为全体同步递增 |
| 新 target quota 小于现有 usage | 保留已计费工作，先阻止新增；不能删消息或把差额当 free |

若这批数据的控制范围/执行域无法安全表达，转换应停止并输出精确冲突清单，而不是生成一个“看似成功”的统一目标。

### 15.5 回滚边界

新 schema 尚未接受新数据、未发送新 attempt 前，可以回退到受保护旧 checkpoint/cut。

一旦新 schema 已产生消息状态或外部发送，不能直接恢复旧镜像继续发送，否则会重复或丢失状态。应使用能识别新格式的修复版本 roll forward，或设计明确的数据级回退转换。

旧 Lane reader 的终止条件是相关旧 source/attempt/evidence/checkpoint 保护结束，而不是“新代码已启动一次”。

## 16. 测试与验收：先证明复杂度，再跑完整链路

### 16.1 算法/存储回归

| 用例 | 必须验证 |
|---|---|
| 同 Lane 连续插入大量远期消息 | head 求值与全量 reference 模型一致；读量不随 backlog 线性增长 |
| 删除当前 head | 正确选 successor，不因 limit=1 误判空 |
| 删除非 head | 不扫描整队列，不改 head revision |
| Reschedule 到更早/更晚时间 | 旧 key 删除、新 key 生效，head 正确 |
| 同 deliverAt 多条消息 | source token/message/generation 定序与旧规则一致 |
| 同 batch 删除多个前缀项再插入 | overlay 正确，读取量受 delta 大小约束 |
| 读前预算已耗尽；删除 head 后 successor 读取预算耗尽 | 返回 INCOMPLETE；不写空 head、不提交命令结果、不推进 Source Position |
| DUE 已完成，ORDERED/NATIVE 或 Message 点查耗尽预算 | 整体 plan 未完成；不能只提交已完成分支 |
| overlay 新 key 更晚，但持久前缀未读完 | 不将新增项误当最小值 |
| 跨 turn 重试前 Owner/Store/mutationSequence 改变 | 丢弃旧 plan，重新验证读取视图 |
| iterator I/O error | fail closed，不当作前缀为空 |
| WriteBatch 失败/结果不确定 | 不推进内存 head/source ACK；恢复结果一致 |
| tail 损坏但尚未选中 | 专项审计发现；一旦被选中必须阻止发送 |

对“单条消息变更、每个前缀最多排除一个 key”的健康路径，目标是每个相关前缀最多读取 2 个应用可见候选；这是逻辑读取验收，不宣称 RocksDB 每次仅发生两个底层 I/O。

### 16.2 60 秒 / 1 秒专项矩阵

| 用例 | 必须验证 |
|---|---|
| 60 秒内所有消息第一轮已 Claim | 下一轮不再为它们产生新 Claim |
| 第一轮预算只取 K 条 | 下一轮从剩余工作继续，不跳过未处理区间 |
| 扫描后插入旧窗口内的新消息 | 新 head 事件使其可发现，不依赖窗口高水位 |
| 60→30→0 秒 lead | 不全量改消息 key；ordinary due 继续 |
| SHADOW / snapshot 过期 / Disable | 无非法提前 Admission；普通分支不被挡 |
| 不同 pinned max lead 的 Profile | 不发生 native head 遮蔽已可交接候选 |
| cap 同为 60 秒，旧 Profile A DISABLED、B ENABLED | 不直接共用旧 scope；新共同 scope 或显式 ordinary 回退，不靠逐消息跳过 A |
| 新 scope 与旧 scope 的签名/authority namespace 混用 | 新 Admission 拒绝错误授权；旧 Admission 仍绑定原 snapshot |
| 当前消息同时是 ordinary/native head | 最多一个 current work，原子消费两路 |
| Claim 超时撤销 | 正确恢复原索引，不烧掉 Admission budget |
| native 明确失败后 retry | 只走 ordinary retry |
| native response loss | 保留 UNKNOWN/Journal 恢复，不重新分配 old sequence |
| target 永久故障 | 不重复扫描整个 target backlog，其他目标有服务机会 |
| early burst + 当前 ordinary due | ordinary 不被 early 工作耗尽全部资源 |

### 16.3 Lane 合并专项

同一个物理目标使用多个 Profile、多个无序 bucket、许多 message key，必须只产生一个 Worker target 调度入口，并在各源 Shard 中各有至多一个该目标队列摘要。

Producer 数量按配置的真实通道槽位和必要恢复域增长，不能继续按 Profile 数或 key 数增长。新增 Profile 不得增加目标 weight。

不同集群同名 topic、删除重建同名 topic、不同物理 partition 必须保持不同 Target ID。认证不兼容不能被合并掉。严格顺序与 terminal guard 的旧控制语义不能被重新打开。

新增专项用例：同 target 的 A 因凭证失效/独立 Pause/独立 permit 受阻，B 可发送。首版必须在不兼容绑定入队前给出稳定拒绝或迁移冲突；扩展支持多个执行域时，B 必须从自己的有界 head 获得服务，扫描量不能随 A 的 backlog 增长。一个源 Shard 失去 lease 不能关闭另一个源 Shard 的合法通道。

### 16.4 性能测量分组

按可复现的源码候选或明确的组件测量分组。测量标签使用 M，避免与实施阶段 A–D 混淆：

```text
M0：当前 Lane + 当前全扫候选算法
M1：当前 Lane + P0 head/预算修复
M2：M1 + 独立公平性切片，或等价的 scheduler 组件测量
M3：Target 队列/通道与进程内公平性，quota 切片前后分别记录
M4：完整新路径及其真实 Broker 回归
```

M0 只在安全的小规模基线运行，避免为了证明 O(N²) 强行跑超大样本。组件测量不能当作端到端 TPS；中间组合若不是可运行的完整候选，应明确标为 component-only，不为凑对照组维护永久双调度路径。

分开增长 backlog N 与 Lane/Target 数 L：固定 L 增大 N，用来验证取 head 读量；固定 N 增大 L，用来验证 quota 计算与公平性写量。使用 1k、10k、100k 等递增 backlog，覆盖 inline payload 大小、ordinary/native 比例、正常与坏目标、单/多源 Shard。先看读写次数增长曲线，再做更大规模容量验证。P0 只证明候选查询的复杂度，不声称整个 Schedule 热路径已经 O(1)。

### 16.5 必须新增的观测项

```text
head_recompute_total
head_candidate_keys_read_total
head_message_get_total
head_recompute_elapsed
head_read_incomplete_total{reason}
head_read_actual_bytes_total
```

RocksDB iterator Next/Get 调用量、实际读 bytes、cache miss、WAL bytes、CPU 分配和 pause 都应纳入。不能只测平均 TPS，忽略 due lag 与 healthy target 的服务间隔。

基数监控优先使用聚合或受控采样，不把每条 messageId、无限 Profile/key 直接作为监控标签。

### 16.6 局部 quota 与内存公平性专项

| 用例 | 必须验证 |
|---|---|
| L 从小到大，仅修改一个 target usage | 只编码/写相关 counter 与 aggregate；未变化 entry 的 bytes/revision 不变，无全 map copy/sort |
| 同一次变更同时影响 target 与 tenant 投影 | aggregate 仅计一次；费用来源符合逐维归属 |
| 重复 apply/replay、WriteBatch 提交前失败、结果不确定 | 不重复计费；内存不领先持久状态；未知写按 Store 规则恢复 |
| counter 下溢/溢出、revision 溢出、incarnation 冲突 | 明确拒绝/完整性失败，不回绕或静默修正 |
| 新 grant 小于已有 usage | 保留费用与旧工作，拒绝新增；Cancel/Outcome 可继续 |
| 恢复重算 aggregate 与持久值不符 | 明确发现，不在新 Schedule 内静默覆盖 |
| 连续空 poll、只有未来 head、预算不足 | fairness 产生的独立 store.write 次数与字节均为 0 |
| 重启后多目标 eligible、随后有新增/blocked target | 有限恢复首轮可完成；持续可服务目标有界获机会 |
| Claim 前失败及普通/native sibling | 正确重排可逆工作，durable Claim 与去重契约不变 |
| 同一目标新增 Profile/bucket/channel slot | target weight、总额度不被复制 |

### 17.2 阶段 A：原 Lane/原协议上的 P0 修复

#### A0：固定基线、调用者清单和参考结果

**输入：** 当前审查基线及原 Lane key/comparator，不改变 Target、Profile 或 Producer 身份。

**工作：**

1. 列出 `findLaneCandidate`、`findLaneNativeCandidate`、`projectLane` 的全部调用者，区分正常 mutation、Claim/revoke、控制、激活、修复及审计。
2. 在测试侧保留按旧 comparator 全量求最小值的参考模型；用同一组 Schedule/Cancel/Reschedule/Claim/rollback 事件比较每次提交后的 Message、时间索引和两路 head。
3. 增加可归属到 head/discovery/quota/fairness 的计量接口或测试探针，避免仅凭 wall time 推断读写次数。探针不创建逐消息 durable SLO 记录。
4. 固定原 `KeyCodec`、同时间 tie-break、generation 和 SourcePosition token 样本，并记录源仓库、commit、构建/配置及数据规模。

**产物：** 调用点清单、参考测试、基线测量格式、现有测试到本次风险的映射。

**完成条件：** 小规模基线可重复，计量能区分候选读取与 Message 点查；没有为了构造 N=100k 先在旧 O(N²) 路径强行灌入大样本。

#### A1：替换普通与 Native 的全前缀候选选择

**主要路径：** `runtime/DelayShard.java`、必要的小型 head helper；复用 `store/ShardStore.java` 与 `KeyCodec.java` 的排序。

**工作：** 将“读整个前缀后取最小值”替换成“首个未被 exact overlay 排除的已验证候选 + 本次新增候选”。DUE、ORDERED、NATIVE 各自取头，再按原 comparator 合并；保留 prior/next 跨 Lane 时对两侧的原子更新。

先覆盖当前单消息变更。内部 delta 能明确表达删除/覆盖，但不新增批量 Command API，也不在本切片实现稳定 head 缓存。完整 mutation batch 内容、原 Lane ID、prepared bytes 和发送身份保持原语义。

**必测：** 空前缀、首项插入、删除唯一项、删除 head 后取 successor、删除非 head、同 key 覆盖、Reschedule 更早/更晚、同时间多项、普通/native 同消息、ORDERED retry 阻塞、Claim 撤销恢复。

**完成条件：** 每个健康单消息变更的相关前缀最多访问两个应用候选；读取量不随 Lane backlog N 线性增加；选中候选与参考结果一致。

**停止条件：** comparator 与 key 顺序不符、正常路径需要跳过未声明旧项、无法解释某个控制/Claim 调用的 overlay。必须定位原因，不能增大 limit 掩盖。

#### A2：补齐三态结果、共享预算与提交屏障

**依赖：** A1 的局部求头算法；详细规则见 §5.6–§5.8。

**工作：**

1. 复用 `BoundedReadBudget`，在 head 读取结果中区分 FOUND、EMPTY_CONFIRMED、INCOMPLETE，保留 iterator status 与独立错误路径。
2. 将记录/字节/时间计量传至候选依赖的 Message/binding get；READY tail/wrap 不重置预算。可见返回字节与预算拒绝的尝试均有计量。
3. 在进入 `store.write` 之前要求整个 HeadPlan 为 COMPLETE，且读取视图仍绑定当前 Owner/Store/mutationSequence。
4. 将预算让出映射为本地重试/调度结果；不产生客户端业务拒绝，不推进源位置。重试从最新一致视图重新计算。
5. 配置验证证明一个最大合法单消息 plan 可装入 byte envelope；记录连续 elapsed 不足的诊断，防止永远未完成却无告警。

**必测：** seek 前耗尽、删除旧 head 后耗尽、Message 点查前耗尽、DUE 成功后 NATIVE 耗尽、存在 included candidate 但 store 未读完、tail/wrap 共用额度，以及重试前 view 已变化。

**完成条件：** 所有 INCOMPLETE 用例没有 Message/head/quota/CommandResult/SourcePosition 的部分提交；错误与空队列可区分；读动作计量与探针一致。

#### A3：调用者审计、失败恢复与 P0 独立验收

**工作：** 为 A0 中需要完整审计的调用者保留显式审计入口；校验新算法不会让 `rebuildReadyIndexes` 的“重建完成”被误当成整条候选尾部已审计。以实际故障注入验证提交前失败和 native write 结果不确定两类边界。

**产物：** `DelayShardTest`、`ShardStoreTest`、`KeyCodecTest` 及 scheduler/Claim 相关测试的必要回归；准确记录新增或调整的测试名，不只列测试类名。测试-only 全扫 oracle 不进入生产热路径。

**完成条件：** §16.1 全部适用用例通过；健康路径读量满足 A1 上限；被选中损坏不能发送，尾部损坏由声明的审计发现；运行源码变化按现有 source authority 规则记录新证据。P0 可独立交付，结论只覆盖算法与正确性，不覆盖 Target 收敛或最终容量。

### 17.4 阶段 C：按组件实现并分别计量

#### C1：Target 存储投影与原子 head 更新

**依赖：** A3 + B7。主要修改 `KeyCodec`、新增 Target identity/value codec、`DelayShard` 与 READY 投影相关路径。

**工作：** 复用 A 的算法，建立新 Target DUE/NATIVE/EXPIRY/摘要；绑定共同 policy 与 compatibility ref；完成所有涉及候选的 mutation、Claim/revoke、控制及恢复映射。Native 索引资格依据 pinned cap/opt-in/初次状态判定；新 policy 改动不批量重写 key。

**完成条件：** Target hash/排序向量通过，普通/native 原子消费与 rollback 通过，损坏/旧版本拒绝正确；同 source Shard 下兼容 Profile/bucket 不增加 Target 摘要数。新 counter/fairness 装配未完成时，只报告组件完成，不激活不完整 writer。

#### C2：Worker Target 调度、共同 policy 与兼容通道

**主要路径：** `WorkerSchedulingRuntime`、`WorkerShardRuntime`、`WorkerShardFleetRuntime`、`WorkerPhysicalPublishExecutor`、activation、Handoff resolver/authority。

**工作：** Worker 按 target 选择，再轮转其 eligible source Shard；各 Shard 仍独立 Claim/Admission。按 §8.6 注册兼容执行类别和有限 slot，Owner loss 只撤销所属请求权限；Producer fault 的影响范围按实际使用者处理。

共同 policy、head change、permit release 和 backoff 到期驱动唤醒。首次发现/Claim/Admission/Producer 边界按既定语义验证；缓存以 Owner、Store、head revision 及相关 policy/control/channel generation 失效，不能仅凭 head 未变绕过 lease 到期。

**必测：** A 不兼容/B 健康的注册与迁移拒绝、单 Shard 通道故障下其他 Shard 进展、Producer slot 上限、关闭引用归属、policy mode/lease 变化、丢失/合并唤醒后的兜底重查。

**完成条件：** 同 Worker/target 只有一个外层发送入口；新增 Profile 不增加 weight；无预算/故障时不遍历 backlog；旧 Journal/sequence/事务 attempt 身份不变。

#### C3：移除高频 fairness 持久化

**主要路径：** `PersistentLaneScheduler`、`LaneScheduler`、Worker scheduler、恢复 bootstrap 及必要公平性指标。

**工作：** 把 DRR deficit/ring/round/cursor/recovery-first-pass 改成进程状态；保留 durable Message/Claim/Admission、两路 head 消费和失败重排。只在已接受的新恢复契约下停止写旧五个 projection。

此切片对公平性写量单独测量；若以原 Lane 身份构建隔离测量候选，其用途是验证该机制，不形成第二条长期产品路径。Target 索引、quota 与 Producer 不在同一测量中反复改动。

**完成条件：** 空 poll 和纯公平性推进的独立持久写为 0；有限恢复首轮可完成；连续运行时健康 target 获得 B5 规定的服务机会。Claim/Admission 的业务写不计入应删除的 fairness 写，未拿到目标 ACK 不被误当作没有服务机会。

#### C4：局部 quota counter、revision 与增量 aggregate

**主要路径：** `LaneQuotaUsageProjection` 的替代局部投影、`DelayShard.persistQuota/aggregateQuotaUsage`、counter codec、恢复/审计与相关 grant 校验。

**工作：** 将所有 quota mutation 接入 B4 的 `QuotaDelta`；只处理受影响 counter，aggregate 按维度做 checked delta；提交成功后发布内存结果。同步更新 Active/Target 投影与查询中的计费一致性检查，避免仍要求全体同 revision。

保留完整重建算法于恢复/审计，禁止在正常 mutation 上调用；正常路径不再产生旧 map bytes。retire 必须保留未决 attempt、zombie 和 retained 费用；counter identity 的槽位释放由真实保护结束决定。

**完成条件：** §16.6 quota 矩阵通过；固定每条 mutation 的受影响 counter 数，增大 L 不增加完整集合的遍历、复制、排序、编码和写入。恢复重算与增量 aggregate 一致，不重计 tenant 镜像或 legacy obligation。

#### C5：装配闭合与旧路径使用清单

**工作：** 确认正式入口只选择一个完整 writer/scheduler 组合；按新增、取消、改期、Claim、Admission、Outcome、控制、恢复列出端到端装配映射。列出剩余旧 reader、旧通道及其 source/evidence/checkpoint 保护条件。

**完成条件：** C1–C4 的接口、计量、异常与恢复规则一致；新 writer 不再生成旧 Lane/bucket、fairness map 或 quota map 的兼容副本。只保留有明确恢复义务的旧 reader，未解除保护前不删除。

**停止条件：** 存在以兼容 overload 绕过新 scope/compatibility/预算的正式入口，或者某个状态转移仍写旧 map。定位并闭合该入口，再进入完整 D 验证。

### 17.5 阶段 D：基础路径的真实链路、故障与测量

#### D1：固定源码与支持能力的真实 Broker 回归

以 C5 的实际 runtime source、构建依赖、Kafka/Pulsar client/P1 lock 和测试配置建立证据身份。先执行功能回归，再对 B2 声明支持的能力逐项运行真实路径：

| 能力 | 必须保留的真实验证 |
|---|---|
| Pulsar Managed ordinary | Admission→ownership→发送→ACK/Outcome 与 not-before |
| Pulsar Native Handoff | deliverAt、共同 policy、双 head、cap 回退、Journal 固定 sequence、HANDED_OFF |
| Kafka 普通发送 | 资源身份、Admission/结果分类、通道复用与实际并发边界 |
| Kafka transactional 等强能力 | exact transaction identity、恢复域、未知结果与旧 attempt 处理；只有声明支持才允许激活 |

能力未验证的状态须明确不可激活，不能用基础发送 smoke 代替强能力回归。原 NDIP-1 的关闭状态和历史证据保留；新架构按自己的源身份产出证据。

#### D2：UNKNOWN、多源 Shard 故障和接管

覆盖 Claim 前失败、Admission 后响应丢失、Producer ownership 后 crash、Owner loss、Store 写结果不确定、单 Shard 重开、同 target 多 Shard 交替失效及共享通道 teardown。

**完成条件：** 未知发送始终保留原 obligation；旧 sequence/producer/transaction identity 不改写；独立 Shard 不互相误 fence；ordinary 不被 Native 失效挡住；恢复不会产生普通/native sibling 的重复 current work。所有预期中断保留原始结果，不能计作普通 PASS。

#### D3：复杂度与性能测量

按 §16.4 的 M0–M4 固定源码、配置与数据集，分别改变 N、L、source Shard 数、兼容 Profile 数、payload 大小及 ordinary/native 比例。记录读取/写入次数、字节、CPU 分配与 pause、due lag、普通消息服务间隔及目标故障时的进展。

**完成条件：** A 的应用候选上限、C3 的纯 fairness 零持久写、C4 的局部 counter 成本及 C2 的目标数量约束都有直接数据。报告组件测量与端到端数据的区别，不承诺未测得的 TPS 倍数。大规模容量/SLO 或生产 rollout 是否作为本提案完成条件，必须在 B7 显式声明，不能临时追加。

### 17.6 阶段 E：完成其余全部改造任务

E1–E6 是完整方案的正式任务，优先级靠后不等于省略。依赖 B 中已冻结的契约和 C/D 的基础路径结果；有相互影响的部分按 E1→E2→E3→E4→E5→E6 顺序集成，E7 对最终组合验收。

#### E1：稳定 head 快路径、revision 缓存与事件唤醒闭环

**对应：** §3.1、§5.4、§7.7、§13.1。**依赖：** A3、B5、C1/C2。

**设计：**

1. 区分持久 `headRevision` 与 policy/control/channel 的 live generation。只有 head identity、候选时间、分支或必要投影改变时递增 headRevision；单纯 quota 变化不让 READY 反复重排。
2. 按 `(Owner, Store, sourceShard, target, prefix/domain)` 保存有上限的已验证 head 摘要。单写者在同一 mutation turn 中证明旧 head 未被删除/覆盖且新 key 更晚时，可复用该 head，免做前缀 seek。
3. 缓存的可信延续来自每次已提交 delta 的更新。不能因为当前 mutationSequence 与缓存记录不同就盲目复用，也不应把每次无关 mutation 都变成整套重验；由单写者在成功提交后更新缓存的已核验位置。
4. cache miss、Owner/Store 变化、无法证明 delta 与 head 无关时，回退到 A 的有界 head 查询。预算耗尽仍返回 INCOMPLETE，绝不回退成全前缀扫描。
5. 发送前的 live lease、time、policy、credential 和 resource 校验保留。head 未变仅能免除不可变索引关系的重复读取，不代表发送权还有效。

**唤醒时序：** 业务 batch 成功→发布 head/revision→标记 target dirty；调度器注册 `(observedRevision, nextWake)` 后再核对 revision/可用性。注册期间发生变化立即重新入队；通知可以合并为每 target 一个 dirty 标志。安全重查使用有界 rotating slice，覆盖丢失通知与窗口内晚插入。

heap 使用原位更新或受限 stale 节点加有界重建，不能每次 mutation 新增永久节点。空闲 TargetRuntime 只在无候选、等待者、物理 in-flight 和活跃资源引用时回收；持久控制与旧 attempt 保护另行保留。

**产物：** head cache/事件失效矩阵、mutation delta 与 revision 更新代码、调度注册/提交竞争时序测试、有界内存与重查测量。

**必测：** 连续插入更晚消息、删除非 head、同时间不同 key、native/ordinary 仅一路改变、policy 到期但 head 不变、注册睡眠时插入更早消息、通知丢失、Owner 接管、写结果不确定、持续更新 heap。

**完成条件：** 可证明不影响 head 的 mutation 不 seek/不写 head revision；cache miss 保持 A 的读上限；所有唤醒竞争最终可发现；缓存/heap/事件数量受配置约束。**停止条件：** 缓存会跨 Owner/Store 复用，或正确性依赖每个通知必达。

#### E2：同 Target 下多个不可互换执行域

**对应：** §4.5、§8.2–§8.7。**依赖：** B1/B2/B3/B4、C2/C4、E1。

**设计：** 在一个 `(sourceShard,targetId)` 中提供至多 K 个真实执行/控制域。域的要求由认证等价范围、结果/事务/sequence 能力及独立发送控制组成；兼容 Profile 复用同一域。K 和总通道上限由资源预算限定，不按 Profile 数自动增长。

```text
DomainSlot {
    slotId, domainGeneration
    executionRequirementsRef, controlScopeRef, nativePolicyScopeRef
    ordinaryHead, nativeHead
}

候选前缀：(kind, targetId, slotId, domainGeneration, time, sourceOrder, messageId, generation)
目标状态：单份 TargetQueueState + 至多 K 个轻量 DomainSlot 摘要
```

该结构中的 domainGeneration 防止槽位重用误接旧索引/请求。它不进入 TargetPartitionId，不创建单独 target weight、target quota 或完整 Lane activation 生命周期。必要的 domain/channel 资源仍计入 Target/Worker 的共同额度。

**状态与选择规则：**

- 新 binding 在 source apply 中解析执行域，复用兼容 slot；不存在兼容 slot 时在限额内 source-ordered 创建，超过 K 给出稳定拒绝并继续消费命令。
- 每个候选只属于一个当前域；未 Admission 的域迁移/改期在同 batch 删除旧索引、建立新索引并重算两侧 head，不重复增加 target aggregate。
- Target 被选中后，只检查至多 K 个域摘要，跳过受阻域，在可服务域间轮转；目标总 weight 与 early/ordinary 预算只扣一次。
- 各 Native 域内部继续使用一个共同 policy；若独立 scope 是真实需求，必须由 B3 明确授权到该域，不能挪用旧 Profile 签名或重新制造无界 policy Lane。
- Admission/materialization 固定 domain/channel generation 和 exact attempt 身份；UNKNOWN 沿原域恢复，不能搬到健康域重发。
- 域 Pause/Close 不关闭同 Target 的其他域。释放 slot 必须满足候选、可逆 Claim、未决 attempt、物理引用与相关恢复保护的退出条件。

**产物：** 域 codec/有限 registry、按域索引和候选摘要、兼容映射、域内轮转、Claim/Admission 校验、quota 归属及迁移映射。

**必测：** A 域凭证失效、B 域健康；A 单独 Pause；A 无 permit；A policy 过期、B scope 有效；K 满后新域拒绝但已有 Cancel/Outcome 继续；旧 generation 的异步回调；域释放后重用；同 target 多 Shard 故障。

**完成条件：** B 获得有界服务机会，选择成本随 K 而非 A 的 backlog 增长；新增兼容 Profile 不增加域数；域计费和生命周期有界。**停止条件：** 隔离需求无法用已冻结域表示、K 之外仍隐式创建对象，或会重写旧 attempt 身份。

#### E3：集中必要校验、简化 authority wrapper 与兼容入口

**对应：** §3.1、§13.1、§13.3、§14。**依赖：** C5、E1/E2。

**设计：** 将校验按入口 decode/prepare、source apply、Claim/Admission preparation、Producer 首次 ownership 四个边界分类。每条规则记录输入来自哪里、何时可能失效、失败如何返回；同一边界内传递已验证的不可变 typed object，复用 canonical bytes/hash。

跨异步队列、policy 刷新、Owner/Store 变化或凭证续租后，重新验证对应的 live 条件；不能把一次验证结果缓存成永久 authority。统一 wrapper 的目标是减少同一事实的重复构造和验证，业务门与外部权威边界仍保留。

为正式入口、package-local helper、legacy decoder/bridge 建立调用图。正式入口只接收已绑定 source/target/attempt 的参数，不新增自由拼装 raw state 的公共接口。没有恢复义务且无正式调用者的兼容 overload 可删除；有旧 source/evidence 依赖的路径集中到有限升级层，由 F2 清退。

**产物：** guard 归属矩阵、正式 API/调用图、小型 immutable context、合并后的正式入口、兼容使用清单及终止条件。只改必要模块，不借机整体搬迁 `DelayShard` 或引入可插拔工作流引擎。

**必测：** typed identity 被替换、准备后 policy/Owner/Store 改变、credential 到期、跨异步边界重用旧 token、重复首次 Producer 调用、legacy bytes 误入新 writer、裸 helper 是否可绕过正式 guard。

**完成条件：** 每项必要校验有唯一清晰归属；减少重复 encode/decode/hash 的调用量有数据；安全边界负例仍拒绝，正常错误语义不漂移。**停止条件：** 删除的 wrapper 实际持有独立 fencing 或不可逆发送边界。

#### E4：常规指标、业务证据与认证观测分层

**对应：** §3.1、§13.2、§16.5。**依赖：** B5、C3、E3。

**设计：** 先逐个审查当前 SLO outbox/hook，将数据按语义归属，而不是按类名决定能否异步：

| 数据 | 新处理方式 | 丢失/失败处理 |
|---|---|---|
| CommandResult、Admission、Outcome、attempt/ownership/Journal 恢复证据 | 按原业务状态与重放契约持久化 | 维持现有原子提交及失败边界 |
| 扫描计数、队列长度、耗时 histogram、服务间隔 | 有界进程统计与异步导出 | 导出失败/溢出报告 gap；不阻塞普通业务提交 |
| 发布认证明确要求的逐事件 SLO 样本 | 明确启用的 durable certification observation | 满足原 exact sample/retention 契约；缺失不能宣称完整认证 |

观测模式、generation、资源预算与生效 source boundary 有明确配置/控制记录；切换只影响之后的观测，不能改变已应用的业务结果或历史样本含义。默认运行模式允许异步指标 gap；认证模式通过 activation 证明其 outbox/retention budget 足够。

异步队列同时限制 records 与 bytes，导出背压不能形成无界对象。统计 dropped/failed export 与进程重启后的未知覆盖区间；未知丢失量不能记为零。证据消费者必须识别 mode/generation/coverage，不把有 gap 的窗口升级成完整 SLO 样本。

关闭认证模式后，已有 durable outbox 按原确认/保留规则排空；不能直接删除仍受保护的证据。认证模式必需的写失败保持既有持久化边界，不能提交缺证据状态却报告认证完成。

**产物：** 全部 hook 分类表、模式/控制 codec、bounded async exporter、certification adapter、样本 consumer/verifier 规则、模式切换与诊断文档。

**必测：** exporter 失联、队列满、crash 前未导出、重启覆盖 gap、模式切换途中失败、历史 outbox 未排空、业务 Outcome 证据与普通指标混淆、认证样本缺失。

**完成条件：** 普通模式不为非业务指标生成逐消息同步 outbox；业务恢复证据完整；认证模式仍满足声明的样本契约，两模式成本分别测量。**停止条件：** 某个待移除 hook 实际参与业务结果/恢复，或新 consumer 无法识别缺失覆盖。

#### E5：严格顺序的轻量 barrier 与迟到边界

**对应：** §3.3、§9。**依赖：** B1/B2/B5/B6、C1/C2、E2。

**设计：** 默认 BEST_EFFORT 无需 ordering-domain 对象。严格模式按原 tenant/routing/binding/key 边界定义 OrderingDomain，继续路由到同一 source Shard；每域保留排序索引、一个未决 head/barrier 和必要水位，不增加独立 Producer、熔断器或 Target 权重。

新排序契约显式绑定 `orderingContractRevision`。`lastAdmittedOrder` 使用与已冻结 ORDERED key 一致的全序 `(deliverAt, sourceOrderToken, messageId, generation)`，在 durable Admission 生效的同 batch 中推进，不以 poll、Claim 或一次物理 send 调用推进。

新 Schedule/Reschedule 在新契约下不得插到已不可逆 Admission 的位置之前，返回 B5 注册的稳定错误码；失败不修改原消息、费用或 barrier。重复 command/replay 先遵守已有幂等规则，不能因当前水位较新就改写历史结果。同一 head 的合法 retry/旧 attempt 恢复按原 obligation 处理，不能被“禁止迟到插入”规则错误拒绝。

同域有 UNKNOWN 或未满足解除条件的 barrier 时，后继不进入可服务 ORDER_HEAD；其他域的 head 仍可参与 Target 内公平选择。barrier 的清除来自 source-ordered 的明确状态/证据，不能靠 Producer 超时或换槽位推断未发送。

每个 OrderingDomain 的可服务 head 归属其 executionDomainRef，ORDER_HEAD 按 `max(deliverAt, retryEligibilityAt)` 排序；其余严格消息留在 ORDERED，不直接混进无序 DUE。执行域的普通候选由 DUE 首项与 ORDER_HEAD 首项按已冻结规则选择，避免为了找一个未阻塞 key 扫描全部严格域。ORDER_STATE、ORDER_HEAD、Message/Admission 与费用在同一 batch 更新；默认 BEST_EFFORT 不创建这些索引。

旧 strict 数据与 checkpoint 后尚未 apply 的旧命令继续按其已绑定契约解释。切到新契约需要 B6/F1 的显式映射或排空边界；不能从当前 Profile 值追溯推导新规则，不能改变原 Admission/hash。Native 与严格模式的禁止组合继续保留。

**产物：** OrderingDomain/ORDER_STATE/ORDER_HEAD 规则和 codec、迟到错误码与前置条件、source apply/Admission watermark 更新、迁移与旧契约 reader、严格能力文档。

**必测：** 同时间 tie-break、迟到 Schedule、更早/更晚 Reschedule、Claim 可逆撤销、Admission 后 crash、UNKNOWN 阻塞后继但其他域推进、head retry、重复 replay、旧契约切换、跨 tenant/key/Shard 边界和 Native 禁止组合。

**完成条件：** 默认路径不承担按 key 的状态；严格域只有必要索引/barrier；新水位和拒绝行为可重放且不追溯改变旧结果。**停止条件：** 无法定义旧契约切点，或以新增拒绝规则掩盖旧数据转换冲突。

#### E6：配额、背压和运行参数统一

**对应：** §4.4–§4.5、§7.8–§7.9、§11 全部、§13.4。**依赖：** C4、E1/E2/E4/E5。

**设计：** 在现有 Worker 资源图中统一派生调度与资源边界，集中配置验证，不为每条消息重新构造容量证明。运维主入口按 Worker、target、调度、Handoff、后台恢复五组组织，实际 FD、native memory、WAL/temp、zombie、retained 等维度继续校验。

配置必须能说明下列数量如何受限：

```text
S = 已拥有 source Shard 数
T_s = Shard s 的活动 Target 数
K = 每 Shard/Target 的最大执行域数

Target 持久摘要数 <= sum(T_s)
普通/Native 域 head 数 <= 2 * K * sum(T_s)
Worker 有效 wake 登记数 <= Worker distinct Target 数
Producer slot、旧通道、zombie 合计 <= 已激活的物理资源 envelope
严格 ORDER_HEAD/历史 counter incarnation <= 对应的显式活动与保留额度
```

这些是不含实际测量常数的设计关系；bytes/FD/RSS 的单项上界和最大合法消息 cost 在 B5/实现测量后填写，不填写虚构默认容量。共同读取预算能容纳一条最大合法 mutation 的完整求值；每 turn 仍受 records/bytes/elapsed 限制。

**背压与源日志：** 目标不可用或无 target permit 时停止它的新 Claim/Admission，保留 head/backoff；容量恢复立即唤醒。target 逻辑 grant 已满时，新增长型 Schedule 确定性拒绝，Cancel/Outcome/terminal/GC 继续。共享磁盘/RSS/FD 到安全边界则按真实共享故障域暂停。

入口增长同时受 source 未应用 records/bytes、最老年龄和保留空间约束。system writer 保留 append/内存等必要资源，但 Admission/Outcome/Cancel 仍按同一日志 Source Position 应用，不能声称有资源保留就能越过已排队数据；不引入第二条状态日志。

ordinary due 配置保留服务份额，early handoff 的占用有上限；native burst 不能占满所有 permit。Probe 使用有界 ownership/backoff，不以不断取新消息测试坏目标。Object Store 的 checkpoint/大 payload/retained 保护及 AUTO_FAST 的独立契约继续接入同一容量核对。

**产物：** 统一配置 schema/loader、派生边界验证、启动错误与运行诊断、source ingress/backpressure 接入、健康目标服务及控制类工作进展测试、运维参数映射。

**必测：** 单坏目标积压、quota 降到 usage 以下、系统控制与业务积压同日志、共享物理资源耗尽、permit 释放重唤醒、Native burst 与 ordinary due、K/slot/strict/retained 上限、Object Store 不可用与 AUTO_FAST 旁路约束。

**完成条件：** 所有已声明资源维度有唯一配置来源及可检查约束；无消息级容量证明重建；健康目标和必要系统工作按声明前提推进。**停止条件：** 配置合并丢掉真实费用，或用目标隔离承诺掩盖共享资源故障。

#### E7：完整任务集的最终集成与证据收束

**依赖：** A0–A3、B1–B7、C1–C5、D1–D3、E1–E6。基础路径 D 的结果不能直接代表 E 修改后的 runtime。

**工作：** 固定最终 runtime source、client/P1 lock、schema/golden corpus 与能力配置。根据 E 实际改变的路径重新执行必要的功能、真实 Broker、故障、复杂度与资源验证；复用未变化证据时必须符合当前 source authority 规则，不只比较文件名或仓库 HEAD。

核对 ordinary/native、单/多执行域、默认/严格顺序、常规/认证观测模式、单/多源 Shard 的受支持组合。禁止组合必须明确拒绝；不得因为矩阵较大就用普通发送覆盖它们。

**产物：** 最终支持/禁止组合表、29 个切片状态清单、准确绑定最终源码的证据目录、F 的迁移输入、剩余旧格式/恢复义务清单。

**完成条件：** 所有必要实现任务和适用证据有明确结果，未决正确性状态为零；F 的转换器识别 E2/E4/E5 的新状态。未测性能范围与未启动环境保持单独状态，不混入代码实现完成结论。

### 17.7 阶段 F：适用环境迁移、清退与方案收尾

#### F1：有存量数据时的受控迁移

迁移是具体环境的独立动作，不由本设计文件自动启动。实现阶段先在明确的 disposable 环境测试转换器、重放与回滚；没有需保留数据的环境时，记录该事实及适用范围，不虚构一份生产迁移 PASS。

对有存量的目标环境，依次形成以下可核验产物：

1. **只读清单与 dry-run：** 环境身份、旧 Lane→Target 映射、cap/policy/执行控制冲突、quota/旧 attempt/strict barrier、预计 legacy reader 和通道数。
2. **fenced 一致切点：** 停止新 Claim/Admission 与会改变迁移输入的写入，完成可逆工作处置，取得 checkpoint/source cut 及新 Store 身份。
3. **旧字节与义务保护：** 保存未应用旧命令、prepared/Admission/hash、Journal mapping、sequence、控制 marker、Floor/checkpoint 保护；不可逆 attempt 继续原恢复域。
4. **转换与校验：** 只转换可安全转换的调度状态；逐项验证消息/字节/费用守恒、两路 head、counter aggregate、控制和 strict barrier。旧 scope 无法获得共同新授权的未 Admission 工作明确 ordinary 回退。
5. **版本激活与 replay：** 按 B6 的 decoder/mapping 消费 source cut 后旧命令与新命令；保持原 commandId/hash，不在新 reader 中临时猜测旧 binding 的含义。
6. **环境验证与切换：** 沿现有环境授权流程执行适用的 G0/Gate C/SHADOW/bounded ENABLED，记录具体环境结果与回滚点。

出现 §15.4 冲突时保持源切点和恢复材料，报告未转换原因；不能删消息、放大权限、减少旧费用或重新分配未知 attempt 来让校验通过。

#### F2：保护解除后的旧路径清退

在旧 source、checkpoint、attempt、evidence 的允许恢复窗口结束后，按清单释放旧通道、counter incarnation 和 reader。校验新 writer 从未再生成这些旧格式，更新当前设计/Registry/ADR/Status 的描述及能力配置。

**完成条件：** 必要实现与证据按新 NDIP 关闭规则汇总；迁移和 rollout 状态按各环境单独记录。保留中的合法 legacy obligation 标明具体对象和退出条件，不通过隐瞒它们宣称迁移完成。

#### F3：权威文档、运行配置与完整任务状态收尾

## 18. 预期收益与明确不承诺

预期收益主要来自三个可验证机制：

```text
单次求 head：从访问整 Lane 的候选，变成常数/变更量级的候选访问。
调度与 quota 写：从重写整套 map/ring，变成必要的局部持久状态。
默认调度基数：从目标 × Profile/bucket/domain 等组合，收敛到实际目标及其源 Shard 投影。
```

不承诺固定倍数 TPS 提升、不承诺 60 秒 lead 足以覆盖任意 burst、不承诺单一 Producer 能承载所有负载、不承诺所有认证/强去重通道能合并，也不承诺 native 模式对所有订阅保持 not-before。

真正的简化是让每一个持久化维度都对应一种必要语义，而不是把 Lane 改名为 Target 后仍然保留相同数量的对象、证书、map、状态机和扫描。

**实施顺序按 §17 的 A–F 全任务清单：先独立完成 P0，冻结完整契约，完成基础 Target/公平性/quota 与真实链路验证，再完成其余全部改造及最终回归，最后处理适用环境迁移和清退。**
