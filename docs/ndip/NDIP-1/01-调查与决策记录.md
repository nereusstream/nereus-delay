# Pulsar Native Delivery Handoff：调查与决策记录

## 1. 目的与边界

本文为 `NDIP-1` 工作包提供源码审查上下文，供 `NDIP-1` Discussion 和 Pro 模型复核。本文：

- 记录 `main@8915d21ed325a90ec305201ca85ab8daea3803dc` 的可见事实；
- 记录 H0 实现提交 `main@7cb377ca9dd3135792237af0f027076630d5e4f3` 及其验证边界；
- 固化已经确认的产品契约和实施边界；
- 区分仍然有效的根因分析与已经被讨论淘汰的方案；
- 不修改当前权威设计，不把 Draft 内容描述成已实现能力。

## 2. 治理事实

当前主干采用持续设计演进治理：

```text
Draft -> Discussion -> Accepted -> Implemented
```

重大语义、状态机、安全边界、wire、持久化、跨仓契约、迁移方式和发布 gate 的变化必须
先提交 NDP。只有 Accepted 的 NDP 可以修改当前权威设计；只有实现和 gate 全部完成后
才能标记 Implemented。

仓库不再按项目整体编号版本维护并行设计线。低层格式仍可使用精确的 generation：

- `descriptor_schema_generation`
- `adapter_encoding_generation`
- `evidence_schema_generation`
- `store_value_generation`
- `reset_generation`

这些字段用于 mixed bytes fail-closed，不代表项目发布代际。

## 3. 当前源码事实

### 3.1 timing 模型存在，完整物理发送仍未闭环

`PulsarDestinationTimingPolicy` 当前可以验证：

```text
ordinary managed:
    actionAt == deliverAt

certified handoff:
    actionAt == deliverAt - handoffLeadMs
```

`WorkerPhysicalPublishExecutor` 也会把 `actionAt`、`deliverAt` 投影到
`DestinationPublishRequest`。但真实 Managed Pulsar transport 最终仍是 payload-only：

```java
producer.newMessage()
        .value(request.payload())
        .sendAsync();
```

它没有应用 Pulsar `deliverAt`，也没有完整应用 key、ordering key、properties、event time
和固定 sequence。因此，允许 early request 到达该 transport 会导致消息可能在
`actionAt` 后按普通消息分发。H0 现在已在 Worker、Pinned adapter 和 real transport 三层
阻断 `actionAt < deliverAt`；ordinary `actionAt == deliverAt` 仍使用现有路径，完整 Handoff
physical record 仍未实现。

### 3.2 Prepared 边界在 Worker 到 transport 之间有损

`PreparedPublishDescriptor` 已经绑定 Profile、目标资源、Lane/channel、payload、business
metadata、reserved metadata 和 timing。当前 `DestinationPublishRequest` 只保留 Lane、消息、
attempt、两个时间、payload 和一段 adapter metadata bytes。

这会使物理层无法从同一个 closed record 中验证：

- 实际目标资源和 partition；
- Destination/Capability Profile；
- reserved properties；
- event time；
- 实际 delivery contract；
- runtime policy snapshot；
- prepared target record hash；
- Attempt Journal mapping 与 sequence。

### 3.3 Attempt Journal 目前只是本地协议 seam

`PulsarAttemptJournal` 已经定义：

```text
appendOrReuse mapping
    -> durable mapping-before-send
    -> fixed sequenceId
    -> sendAfterMapped
```

但其类注释明确说明 real implementation 应是 Nereus-owned、non-compacted Pulsar topic；
当前生产 Managed destination transport 尚未接通这条 journal-before-send 链路。

### 3.4 现有 ACK 证据少一个 SEND command hash

`PulsarSendAckEvidence` 当前是固定 11 字段的 closed branch。它保存
`authenticatedResponseSha256`，但没有保存 P1 客户端实际序列化得到的
`sendCommandSha256`，也没有 `preparedRecordHash`。

source-locked P1 的 `GuardedSendSuccessEvidence` 已经同时提供：

- `sendCommandSha256`
- `authenticatedResponseCommandSha256`

因此 Delay 应消费现有 P1 证据，而不是再修改 Broker 来生成另一套证据。

### 3.5 AUTO_FAST 是独立状态机

AUTO_FAST 已有独立的：

- `NativePreparedDelivery`；
- capability snapshot；
- Producer ownership 前 definitive-not-queued；
- Producer ownership 后 `NATIVE_ENQUEUE_UNCERTAIN`；
- outcome/query/evidence resolution。

它不能被当成 Managed destination path 的一个布尔分支。当前 AUTO_FAST 还保存
`deliverAtEpochMs` 与 `brokerDeliverAtEpochMs`，并按
`targetClockAheadBoundMs` 把 Broker timestamp 向后偏移。

本轮进一步确认，真实 `PulsarClientArtifactSendTransport` 把
`NativePreparedDelivery.canonicalBytes()` 作为业务 Message payload 调用
`newMessage().value(preparedBytes).sendAsync()`；它既没有发送原始 inline payload 和 metadata，
也没有调用 Pulsar `deliverAt`。H0 现在已在 adapter 和 real transport 两层将有效 native request
fail-closed，因此 AUTO_FAST 的完整物理 record 仍不可达，物理缺口尚未闭环。原本的

### 3.6 当前 canonical 数据形状

- `CanonicalScheduleIntent.eventTimeEpochMs` 已存在；
- `PreparedPublishDescriptor` 当前未物理投影 event time；
- reserved property registry 只允许九个 `nereus.delay.*` 字段；
- 当前 `DeliveryMode` 只有 `MANAGED`；
- current protocol activation 已有 Worker capability、`ProtocolTuple` 和 source-ordered
  `ProtocolActivationState`，不应再创造一套互不关联的 Writer/Reader activation authority。

## 4. 已确认的产品决策

### 4.1 两种投递契约

#### `NEREUS_MANAGED_NOT_BEFORE`

- Nereus 持有消息直到 `deliverAt`；
- `deliverAt` 继续表示消费者 not-before；
- 普通 Pulsar Message 不设置 Pulsar `deliverAt`。

#### `PULSAR_NATIVE_DELIVERY`

- Nereus 可以在 `deliverAt` 前把消息写入 Pulsar；
- Pulsar Message 设置原生 `deliverAt`；
- 后续投递完全继承 Pulsar 原生行为。

原生契约显式接受：

- Shared、Key_Shared 使用 Pulsar delayed delivery；
- 非 strict 模式可能有 tick 级提前；
- Exclusive、Failover 可能在持久化后立即消费；
- delayed delivery 关闭时可能立即消费；
- TTL、retention、Broker clock 和配置按 Pulsar 自身语义处理。

### 4.2 原生投递策略为三态且默认拒绝

```java
public enum NativeDeliveryPolicy {
    FORBID,
    ALLOW_MANAGED_HANDOFF,
    ALLOW_AUTO_FAST_AND_MANAGED_HANDOFF
}
```

| Policy | AUTO_FAST | Managed Handoff |
|---|---:|---:|
| `FORBID` | 禁止 | 禁止 |
| `ALLOW_MANAGED_HANDOFF` | 禁止 | 允许 |
| `ALLOW_AUTO_FAST_AND_MANAGED_HANDOFF` | 允许 | 允许 |

默认必须是 `FORBID`。wire 必须显式编码；字段缺失不得解释为允许。

### 4.3 保留 source-locked P1 Resource Guard

继续依赖：

- `TopicResourceGuard`
- `GuardedMessageId`
- `GuardedSendSuccessEvidence`

它负责目标 resource incarnation、connection/producer generation、SEND command evidence、
ACK response evidence 和 definitive resource-guard rejection。它不负责消费者可见时间。

不新增：

- Visibility Guard；
- Subscription restriction；
- Dispatcher 改造；
- Protected Topic。

### 4.4 runtime policy 是有界租约式硬控制

新增签名、自包含的 `HandoffPolicySnapshot`，至少包含：

- policy scope digest；
- generation；
- `DISABLED / SHADOW / ENABLED`；
- `effectiveLeadMs`；
- `validFrom` / `validUntil`；
- issuer key generation；
- issued trusted-time evidence；
- snapshot digest；
- signature。

Candidate、Claim 读取当前 head；Admission 再验证并冻结完整 snapshot。replay 不依赖已经
被覆盖的 Oxia 旧值。

Disable 的硬边界是：停止签发新的 ENABLED snapshot，等待已签 snapshot 到期，再声明
`EFFECTIVE_DISABLED`。不声称跨 Oxia 和 source log 的瞬时全局线性化。

### 4.5 兼容策略为直接替换，但必须先证明环境可重置

`DataResetManifest` 必须覆盖：

- Command Topic 和 system topic；
- RocksDB Store；
- Checkpoint Catalog；
- Profile/Oxia 状态与 runtime policy；
- payload reservation 和测试 Object 状态；
- Pulsar Attempt Journal；
- evidence topic/cursor；
- query/dedupe 状态；
- 所有 `PUBLISHING / UNCERTAIN` obligation；
- 旧资源 incarnation；
- 参与切换的 Worker。

直接替换条件：

1. 没有需要保留的外部用户数据；
2. 没有未解决的 `PUBLISHING / UNCERTAIN`；
3. 旧内部资源已清理或换新 incarnation；
4. 所有 Worker 识别目标 schema/reset generation；
5. 启动时验证 manifest digest。

无法证明时改为一次性迁移，不建立永久双轨。

### 4.6 Ordering 第一阶段收窄

```text
DELIVERY_TIME_FIFO
+ NativeDeliveryPolicy != FORBID
= ORDERING_CAPABILITY_UNAVAILABLE
```

第一阶段原生投递只支持 `BEST_EFFORT`。Nereus 不检查 Subscription，因此不能把 Producer
发送顺序提升为 Shared、Key_Shared 或 Failover 的 consumer delivery FIFO。

### 4.7 closed wire / record

- exact nine reserved properties，不增加 `dispatch_mode` property；
- actual `DeliveryContract` 放入 descriptor，由 `prepared_hash` 绑定；不增加 `DispatchMode`；
- Pulsar key 使用 closed oneof：`NONE / UTF8 / BINARY`；
- properties 使用按 key unsigned-byte 排序且唯一的 immutable list；
- event time 进入 descriptor 和 `PulsarPreparedRecord`；
- unknown generation、unknown enum、缺失 required field 全部 fail-closed。

### 4.8 sequence 与 unknown recovery

Managed destination：

```text
Pulsar Attempt Journal mapping-before-send
    -> fixed sequenceId
    -> durable attempt ledger
    -> builder.sequenceId(sequenceId)
    -> target SEND
```

生产路径不允许“有 mapping 才设置 sequenceId，否则自动分配”。

AUTO_FAST：

```text
Producer ownership 前失败
    -> fallback Managed

Producer ownership 后 unknown
    -> NATIVE_ENQUEUE_UNCERTAIN
    -> query / evidence resolution only
    -> no automatic resend
```

### 4.9 Eligibility 行为

```text
policyLead > profileMax
    -> POLICY_OUT_OF_BOUNDS
    -> Handoff 禁止
    -> ordinary due 保持可用
```

可信时间区间跨越 candidate 或 `deliverAt`：

```text
TIME_SAMPLE_REQUIRED
    -> 新 trusted-time sample
       或 bounded monotonic backoff
```

不得返回已经位于过去的 `WaitUntil(candidateAt)`，避免 scheduler 热循环。

### 4.10 Pulsar 运维条件是显式风险，不是 capability gate

以下条件不授予 capability，也不阻塞 ordinary Managed：

- Subscription type；
- delayed delivery enabled；
- strictness / tick；
- Broker clock；
- TTL / retention。

可以提供 best-effort diagnostics 和 drift 告警，但不得把诊断结果升级为 Nereus correctness
证明。

## 5. Draft 阶段唯一代码范围：H0

### 5.1 Managed 入口阻断

Managed early request 在 Worker physical admission 前、Pinned adapter 和 real transport
三层返回：

```text
DEFINITELY_NOT_PUBLISHED
CAPABILITY_UNAVAILABLE
```

### 5.2 AUTO_FAST 入口阻断

有效 AUTO_FAST request 在 `PinnedPulsarNativeSubmissionAdapter` 调用 transport 前返回：

```text
NATIVE_DEFINITELY_NOT_QUEUED
CAPABILITY_UNAVAILABLE
LOCAL_BEFORE_PRODUCER_OWNERSHIP
```

真实 `PulsarClientArtifactSendTransport.send(PulsarNativeSendRequest)` 在 `sendFrame` 和
`producer.newMessage()` 前返回 definitive-not-persisted。不得把本地 H0 编码成 Broker guard
rejection。

### 5.3 Real transport 最后防线

Managed 与 AUTO_FAST 两个 real transport 的最后阻断都必须发生在
`producer.newMessage()` 之前。

### 5.4 no-producer-touch 证明

测试至少断言：

```text
producer.newMessage() = 0
TypedMessageBuilder created = 0
sendAsync() = 0
Managed Worker physical admission acquire = 0
physical reservation leak = 0
AUTO_FAST transport.send = 0
Outcome = definitive non-publication
```

### 5.5 文档状态

Draft NDIP 只能写：

```text
Managed Handoff 与 AUTO_FAST 物理 record 链路未闭环
H0: implemented (fail-closed)
```

H0 已在 `main@7cb377ca9dd3135792237af0f027076630d5e4f3` 合入并通过 gate；这只表示未闭环
物理入口被阻断，不表示完整 Handoff 能力已经实现。Draft 阶段不得删除当前权威设计中的
not-before 语义。

## 6. 已淘汰的旧结论

下列分析不再属于当前提案：

- 为 Handoff 新增 Broker Visibility Guard；
- 限制或探测 Subscription；
- Protected Topic；
- Dispatcher delayed-delivery 改造；
- 跨 Subscription not-before 认证；
- 永久并行协议或双读；
- 根据 `actionAt < deliverAt` 推导 `HANDED_OFF`；
- runtime policy 越界时静默 `Math.min`；
- `NativeDeliveryPolicy` 默认允许；
- 用普通 `Map` 作为 canonical properties authority；
- Managed transport 缺 journal mapping 时让 Producer 自动分配 sequence。

动态 lead、Admission 冻结、无损 physical request、真实 transport 缺口、P1 resource guard 和
Producer ownership 后 unknown 的分析仍然有效。

## 7. 已关闭的评审问题

### R1. policy、contract 与 dispatch 的唯一权威

Schedule/Message 只保存 requested `NativeDeliveryPolicy`；Managed Admission 或 AUTO_FAST
prepared 只保存 actual `DeliveryContract`。路径类型由外层 union 表达，不增加
`DispatchMode`。

### R2. lease 与 Producer ownership

Candidate、Claim、Admission 逐层验证 current policy head；Admission 冻结 full snapshot。
Managed 在 durable Journal `OWNERSHIP_STARTED` marker 前再次使用 trusted-time interval 验证
frozen lease，AUTO_FAST 在 `transport.send` 前验证。marker/transport call 是 physical point
of no return；之后的 unknown 不能因 lease 到期降为 definite。

### R3. AUTO_FAST target timestamp

删除 `brokerDeliverAtEpochMs`、`targetClockAheadBoundMs` 和 clock-shift correctness。两条 native
路径的 Pulsar timestamp 都精确等于业务 `deliverAtEpochMs`；Broker clock 是显式产品风险。

### R4. DataReset gate

```text
NDIP Accepted + read-only DataResetAssessment PASS
    -> 允许实现 H1-H6

environment signed DataResetManifest PASS
    -> 允许 activation/cutover
```

这样避免要求尚未实现的 manifest 工具先证明自身。

### R5. schema activation authority

新增一个 closed `ArtifactGenerationSet`，同时绑定 Client/System tuple、Profile、descriptor、
adapter、native prepared、Journal、record、snapshot、evidence、Store、reset 和 P1 source lock。
Worker declaration 和 source-ordered `ProtocolActivationState` 复用现有 authority，一个 marker
原子激活 tuple + set，不新增独立 heads。

### R6. Record 与 SEND command 关联

Admission 只冻结 `PulsarRecordTemplate` 和 `recordTemplateHash`。Journal 分配 mapping/sequence
后才构造 `PulsarPreparedRecord` 与 `preparedRecordHash`。record hash 与
`sendCommandSha256` 属于不同 domain，不要求数值相等；关联由唯一 source-locked
`PulsarClientArtifactRecordEncoder`、P1 actual SEND/ACK evidence 和逐字段 golden vectors证明。

另一个已关闭的实现阻塞是 scheduler：同一 Lane 保留 ordinary/native 两个内部 head 投影，
共享一份 DRR authority，避免 disabled/小 lead 的 native head 阻塞 ordinary due；不新增独立
Handoff Scanner。
