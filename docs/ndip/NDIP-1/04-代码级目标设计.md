## 2. 本轮源码审查发现的阻塞问题

### 2.1 Managed 与 AUTO_FAST 都存在真实物理缺口

Managed real transport 当前只执行：

```java
producer.newMessage()
        .value(request.payload())
        .sendAsync();
```

AUTO_FAST real transport 当前把 `NativePreparedDelivery.canonicalBytes()` 当成业务 payload：

```java
producer.newMessage()
        .value(request.preparedBytes())
        .sendAsync();
```

两条路径都没有把完整业务 record 投影到 builder，也没有调用 Pulsar `deliverAt`。因此 H0
必须同时封闭两条路径。只封 Managed 不是完整 fail-closed。

### 2.2 Admission 不能绑定最终 `preparedRecordHash`

Managed `sequenceId` 由 Attempt Journal 在 Admission 之后分配。最终 record 包含 sequence
authority，因此 Admission 阶段不可能已经拥有最终 `preparedRecordHash`。

固定的时序是：

```text
Claim
  -> Admission freezes PulsarRecordTemplate
  -> recordTemplateHash
  -> preparedPublishHash
  -> Journal allocates mapping + sequenceId
  -> PulsarPreparedRecord
  -> preparedRecordHash
  -> ownership marker
  -> target SEND
  -> SEND/ACK evidence
```

Admission 绑定 template，不绑定未来才产生的 mapping、sequence 或最终 record hash。

### 2.3 单一 Lane head 会让 native 优化阻塞 ordinary due

若把 `deliverAt - maxHandoffLeadMs` 直接当成现有 Lane 唯一 READY head，而运行时 policy 又是
DISABLED 或使用较小 lead，则该 future-native head 可能挡住同一 Lane 中更早到期的 ordinary
消息。这会破坏“native 不可用不得影响 ordinary due”。

目标实现使用同一 Lane、同一 DRR 权重下的双投影 head：

- ordinary head：按 `max(deliverAt, retryEligibilityAt)`；
- native candidate head：仅初次、显式 opt-in 的 Pulsar BEST_EFFORT 消息，按
  `deliverAt - maxHandoffLeadMs`。

这不是 Lane 拆分，也不新增独立 Handoff Scanner。两种索引在同一个 RocksDB WriteBatch 中
维护，现有 scheduler/recovery work class 同时恢复和选择二者。

## 3. 唯一产品权威

### 3.1 requested policy

`NativeDeliveryPolicy` 只表达调用方允许的路径，wire value 固定为：

| value | enum | AUTO_FAST | Managed Handoff |
|---:|---|---:|---:|
| 1 | `FORBID` | 禁止 | 禁止 |
| 2 | `ALLOW_MANAGED_HANDOFF` | 禁止 | 允许 |
| 3 | `ALLOW_AUTO_FAST_AND_MANAGED_HANDOFF` | 允许 | 允许 |

不得定义 value 0。SDK/API 未选择时，writer 必须显式写 value 1；decoder 遇到缺失或 unknown
value 必须拒绝。

### 3.2 actual contract

`DeliveryContract` 只表达一次实际发送的产品契约：

| value | enum | Pulsar `deliverAt` |
|---:|---|---|
| 1 | `NEREUS_MANAGED_NOT_BEFORE` | 必须缺失 |
| 2 | `PULSAR_NATIVE_DELIVERY` | 必须等于业务 `deliverAt` |

Schedule/Message 保存 requested policy；Managed Admission 或 AUTO_FAST prepared 保存 actual
contract。外层 union 已经表达 Managed 与 AUTO_FAST 路径，不增加 `DispatchMode`。

合法组合固定为：

| outer path | policy | contract | snapshot |
|---|---|---|---|
| Kafka Managed | `FORBID` | Managed not-before | absent |
| Pulsar ordinary Managed | 任意允许值 | Managed not-before | absent |
| Pulsar Managed Handoff | value 2 或 3 | Native delivery | full ENABLED snapshot |
| Pulsar AUTO_FAST | value 3 | Native delivery | full ENABLED snapshot |

任何其他组合都在 canonical decode 或 Producer ownership 前 fail-closed。

### 3.3 Ordering 与 retry

- `DELIVERY_TIME_FIFO + policy != FORBID` 在 Schedule ownership 前返回
  `ORDERING_CAPABILITY_UNAVAILABLE`；
- native delivery 第一阶段只允许 `BEST_EFFORT`；
- Managed Handoff 只允许 `TimelineWorkKind.INITIAL_SCHEDULE` 且 `attemptNo == 1`；
- 一旦初次 native Admission 产生 definitive-not-published，后续 retry 只走 ordinary due；
- AUTO_FAST ownership 前 fallback 创建的 Managed Schedule 仍是初次消息，可在之后重新参与
  Managed Handoff eligibility；ownership 后不得 fallback。

## 7. Scheduler、Claim 与 Admission

### 7.1 双投影，不新增 Scanner

每条初次 Schedule 在一个 WriteBatch 中维护：

1. ordinary Timeline key/ref；
2. 若 policy、Profile、capability、ordering 静态允许，则维护 native candidate index key/ref；
3. Lane READY value 同时保存 ordinary head 和 optional native head；
4. READY key 的 persistent wake 是两个 head 最早静态边界的最小值。

Cancel、Reschedule、Claim、Outcome、retry 和 recovery 必须原子更新两种投影。FIFO 永远没有
native head。retry work 永远没有 native head。

`ScheduleWorkItem` 目标字段：

```text
laneId
messageId
generation
persistentWakeAtEpochMs
effectiveEligibleAtEpochMs
candidateKind = ORDINARY | MANAGED_NATIVE
optional HandoffPolicyHeadRef/full candidate snapshot
accountedBytes
```

`sameWork`/READY identity 只比较 durable identity 与 persistent wake；process-local effective
eligibility 不得被误判为 Store divergence。Lane DRR 使用 effective eligibility，但一个 Lane
仍只有一份 weight/deficit/last-served authority。

### 7.2 resolver closed result

新增 `HandoffEligibilityResolver`：

```text
HandoffEligibilityAction:
  WAIT_UNTIL
  TIME_SAMPLE_REQUIRED
  ORDINARY_DUE
  MANAGED_NATIVE_CANDIDATE

HandoffEligibilityReason:
  FORBIDDEN
  WRONG_ADAPTER
  ORDERING_UNAVAILABLE
  NOT_INITIAL_ATTEMPT
  CAPABILITY_UNAVAILABLE
  POLICY_DISABLED
  POLICY_SHADOW
  POLICY_OUT_OF_BOUNDS
  POLICY_NOT_YET_VALID
  POLICY_EXPIRED
  ELIGIBLE
```

SHADOW 计算 candidate/metrics，但 action 只能是 `WAIT_UNTIL` 或 `ORDINARY_DUE`，不能返回
native candidate。

### 7.3 trusted-time 分区

令 trusted interval 为 `[E,L]`，candidate 为 `C`，deliver 为 `D`：

```text
L < C                       -> WAIT_UNTIL(C)
E < C <= L                  -> TIME_SAMPLE_REQUIRED
C <= E && L < D             -> MANAGED_NATIVE_CANDIDATE
E < D <= L                  -> TIME_SAMPLE_REQUIRED
D <= E                      -> ORDINARY_DUE
```

若 native policy 不可用，则只对 D 使用同样的 wait/cross/due 分区。任何返回的 wall-clock
`WaitUntil` 必须严格大于当前 trusted latest；否则使用 bounded monotonic backoff。禁止返回
past candidate 形成热循环。

### 7.4 policy refresh

`PersistentLaneScheduler.refreshDynamicEligibility(...)` 只处理已发现 Lane heads 和有界 READY
slice：

- lead 增加：candidate 可立即变 due；
- lead 减少：更新 process-local effective time；
- DISABLED：native head 被忽略，ordinary head 仍可被选；
- watcher/Oxia/trust unavailable：fail closed 到 ordinary head；
- restart：从 dual READY 全量有界恢复，再读 current heads。

watch 丢失最多损失 Handoff 优化，不得丢 ordinary due。周期性有界 refresh 是 watcher 的安全
补充，不是独立 Scanner。

### 7.5 Claim 与 Admission

Candidate、Claim 都验证 current head。Claim 保存 head ref 和实际 actionAt。Admission：

1. CAS-stable reread current head；
2. 验证 scope、signature、issuer trust、artifact set、mode、lead、ordering 和 trusted interval；
3. native 时冻结 full snapshot；ordinary 时 snapshot absent；
4. 构造 record template、template hash、descriptor 和 preparedPublishHash；
5. 将 exact Admission 写入 source log。

head 漂移、lease 跨界或 out-of-bounds 发生在 Admission 之前时，撤销 Claim 并恢复 READY；
ordinary due 仍由独立 ordinary head 保证。

## 8. runtime policy trust 与 Disable

新增 `HandoffPolicyTrustStore`，按 issuer key generation 和 source/activation position 返回历史
Ed25519 public key。生产构造器不得只接收一个可替换 raw `PublicKey`。

验证发生在：

- Candidate：current head + trusted interval；
- Claim：current head ref equality；
- Admission：CAS-stable current head + freeze；
- Managed physical ownership marker 前：验证 Admission 中 frozen snapshot 的签名、scope、
  artifact set 与 lease；不要求它仍是 current head；
- AUTO_FAST `transport.send(...)` 前：同样验证 frozen snapshot。

Disable 语义：

```text
CAS current head -> signed DISABLED snapshot
stop issuing ENABLED snapshots
retain maximum outstanding validUntil
after bound and no new ownership markers -> EFFECTIVE_DISABLED
```

已在有效 lease 内写入 durable `OWNERSHIP_STARTED` 的 exact attempt 可以在 lease 到期后完成
或解析；`validUntil` 限制新 ownership 的线性化，不把已拥有的 unknown 伪造成 definite。

## 9. Managed Attempt Journal

### 9.1 production resource

- Nereus-owned non-compacted Pulsar topic；
- partition 与 Delay Shard exact 绑定；
- fresh resource incarnation；
- retention 覆盖 checkpoint floor、所有 unresolved mapping 和 recovery horizon；
- reader/cursor 必须证明 contiguous replay；
- source-locked producer/consumer identity 写入 artifact set/manifest。

### 9.2 schema generation 2 状态机

`RecordKind` 直接替换为：

```text
MAPPED = 1
OWNERSHIP_STARTED = 2
PUBLISHED = 3
RETIRED_NOT_PUBLISHED = 4
```

状态迁移：

```text
UNMAPPED
  -> MAPPED
  -> OWNERSHIP_STARTED
     -> PUBLISHED
     -> unresolved/UNCERTAIN
     -> RETIRED_NOT_PUBLISHED only with exact definitive proof

MAPPED
  -> RETIRED_NOT_PUBLISHED before ownership
```

`Mapping` 必须绑定 producer key、sequenceId、message/generation/attempt、preparedPublishHash、
recordTemplateHash、delivery contract、source Admission position 和 artifact set digest。删除旧的
`guardedBrokerTimestampEpochMs` 字段。

### 9.3 physical ordering

```text
appendOrReuse MAPPED and await Broker ACK
  -> construct and validate PulsarPreparedRecord
  -> validate frozen lease with trusted interval
  -> if invalid: durable RETIRED_NOT_PUBLISHED, then source Outcome
  -> append OWNERSHIP_STARTED and await Broker ACK
  -> call P1 transport exactly once
  -> append PUBLISHED or retain UNCERTAIN/definitive retirement evidence
```

`OWNERSHIP_STARTED` 是 Managed physical point of no return。它之前的失败可以是 definitive；
它之后没有 exact proof 时必须 UNCERTAIN。相同 attempt replay 复用相同 mapping 和 sequence。
同一 producer 的 unresolved lower sequence 阻塞更高 sequence。

## 10. P1 record encoder、transport 与 evidence

新增 `PulsarClientArtifactRecordEncoder`，唯一负责把 validated `PulsarPreparedRecord` 投影到
P1 `TypedMessageBuilder<byte[]>`：

```text
newMessage
value(exact payload)

UTF8 key -> key(exact text)
BINARY key -> keyBytes(exact bytes)
optional ordering key

```

ordinary contract 禁止调用 `deliverAt`。AUTO_FAST 禁止再把 `NativePreparedDelivery` envelope 当成

Producer ownership 前校验 target incarnation、topic creation identity、partition、channel、
producer/connection generation、producer-name hash、sequence authority、template/record/prepared

`preparedRecordHash` 与 actual SEND command hash 的关联由以下三项共同证明：

1. source-locked deterministic encoder 是唯一 builder projection；
2. source-locked P1 `GuardedSendSuccessEvidence` 返回 actual SEND 与 authenticated response hash；
3. golden vectors/command interception 对 payload、deliverAt、sequence、key、ordering key、
   properties、event time、producer/connection identity逐字段验证。

`nereus/delay-resource-guard@0a2536484cd3932801a98dc88ff112b2df88a1c7`；H4 开始前必须重新
验证实际 source lock，并把最终 commit/distribution digest 写入 artifact set 和 receipt。

真实 Managed transport 中 `TopicResourceGuardException.definitelyNotPersisted()` 必须投影为
definitive-not-published exact proof；不得像当前代码一样降为 UNKNOWN。

## 13. Data reset 与兼容边界

### 13.1 deployment / upgrade assessment gate

G0 core 已在 `main@68fe2c292e34f0162aac9377b9f935fe598831e4` 实现，不作为 H1-H6 前置。
只有准备接触 existing/staging/production persistent environment 时才运行
`DataResetAssessment`；`DISPOSABLE_LOCAL` 和 `UNKNOWN` 不能创建真实 Assessment scope。G0 只能
由 read-only runtime adapter、closed evaluator 和本地 receipt writer 组成；唯一允许的写入是
assessment receipt，禁止 runtime Producer/Writer、cleanup、drain、migration、resource mutation、
Worker rollout 和 policy issuance。Assessment 至少列出 Command/system topic、RocksDB、
Checkpoint、Profile/Oxia、runtime policy、payload reservation/Object、Attempt Journal、
evidence/cursor、query/dedupe、当前所有 `PUBLISHING / UNCERTAIN`、resource incarnation 和可枚举
Worker 集合，并绑定 exact NDIP package digest、source baseline、scope、trusted observation time
和 evidence digests。

closed result：

```text
PASS_DIRECT_REPLACE
    -> 没有外部兼容/迁移义务
    -> 旧内部状态均可丢弃或换 incarnation
    -> 没有必须跨 generation 保留的 unknown obligation
    -> Worker 集合可枚举且可在 cutover 前整体升级
    -> RESET candidate；不能直接产生 Gate C authority

PASS_RETAIN
    -> 所有需保留状态都明确 RETAIN_COMPATIBLE
    -> RETAIN candidate；不能直接产生 Gate C authority

MIGRATION_REQUIRED
    -> 先完成有界一次性迁移设计、执行和 completion receipt
    -> 只有 MIGRATED Gate C resolution 才可继续

INCOMPLETE
    -> scope/access/identity/evidence 不完整
    -> fail-closed
```

Assessment 不要求尚未构建的 Worker 已支持未来 generation，不证明 actual zero obligation、fresh
resource 或 cutover readiness；因此它不能作为 Gate C 或 activation authority。当前没有真实
deployment 时状态固定为 `NOT_APPLICABLE_FOR_IMPLEMENTATION / PENDING_DEPLOYMENT`，不得创建
虚假 scope、PASS 或 receipt。

### 13.2 implementation / disposable / deployment closed guard

已实现的 `DeploymentSafetyGate` 提供三个不共享裸布尔 authority 的入口：

```java
Decision implementation(
        GateBStatus gateBStatus,
        ImplementationSlice requestedSlice,
        Set<ImplementationSlice> completedSlices);

Decision localDisposable(
        GateBStatus gateBStatus,
        String environmentId,
        EnvironmentClassification classification,
        Optional<DisposableEnvironmentAttestation> attestation,
        LocalOperation operation);

Decision deployment(
        GateBStatus gateBStatus,
        String environmentId,
        EnvironmentClassification classification,
        Optional<GateCAuthorization> gateCAuthorization,
        DeploymentOperation operation,
        ShadowReadiness shadowReadiness);
```

closed enums 固定为：

- `GateBStatus = PENDING / PASS`；
- `ImplementationSlice = H1 / H2 / H3 / H4 / H5 / H6`；completed set 必须是 ordered prefix；
- `EnvironmentClassification = DISPOSABLE_LOCAL / EXISTING / STAGING / PRODUCTION / UNKNOWN`；
- `LocalOperation = CREATE / RESET / DESTROY / REBUILD / INTEGRATION_TEST`；
- `DeploymentOperation = ENTER_SHADOW / ENTER_ENABLED`；
- `ShadowReadiness = NOT_STARTED / REQUIREMENTS_PASS`；
- `GateCAuthorization.Resolution = RESET / RETAIN / MIGRATED`。

`DisposableEnvironmentAttestation` 必须绑定 environmentId、executionId、isolated resource scope、
synthetic-only、exclusive resource ownership、cleanup authorization 与 non-zero evidence SHA-256；
任一缺失或 environment mismatch 都拒绝。`GateCAuthorization` 必须绑定 environmentId、persistent
classification、assessment scope digest、assessment receipt digest 与 gate receipt digest；不能为
`DISPOSABLE_LOCAL` 或 `UNKNOWN` 构造 positive authority。

Decision code 至少区分 `GATE_B_REQUIRED`、`PREDECESSOR_REQUIRED`、
`INVALID_IMPLEMENTATION_PROGRESS`、`UNKNOWN_ENVIRONMENT`、`ENVIRONMENT_NOT_DISPOSABLE`、
`DISPOSABLE_ATTESTATION_REQUIRED/INCOMPLETE`、`ATTESTATION_ENVIRONMENT_MISMATCH`、
`GATE_C_REQUIRED`、`GATE_C_SCOPE_MISMATCH` 和 `SHADOW_REQUIREMENTS_REQUIRED`。只有
`AUTHORIZED` 对应 `authorized=true`。

### 13.3 activation gate

Gate C 必须绑定 exact environment/classification/scope、Assessment receipt 和独立 gate receipt，
closed resolution 为 `RESET / RETAIN / MIGRATED`。Gate C PASS 只允许该 exact environment 进入
SHADOW。实现提供 canonical、Ed25519 签名的 `DataResetManifest`；只有 Gate C、SHADOW
requirements 与环境级 manifest 全部 PASS 才允许 ENABLED/cutover。manifest 绑定 exact
ArtifactGenerationSet、reset generation、资源列表与 incarnation、zero-obligation proof、Worker
set、trusted time、activation window 和 issuer key generation。

Manifest tooling 只在 H6 实现；它必须在实际 cutover window 重新读取环境并证明零外部数据
保留义务、零 unresolved obligation、fresh resources 和全 Worker exact set。任一条件不能证明
时停止 activation。一次性迁移必须有完成 receipt、退出条件和旧 reader 删除点。
