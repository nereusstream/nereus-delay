# Use versioned self-routing identities and a fixed hash

Nereus Delay V1 prepares every Command with self-routing `delayMessageId` and `commandId` values before network I/O. Both carry the immutable Route Incarnation and physical partition selected from a fixed cross-language routing algorithm. Later control and query calls decode that locator rather than consulting a mutable modulo mapping. The identity is opaque location metadata, not an authorization credential.

## Binary and text format

V1 uses fixed-width canonical binary:

```text
byte 0       formatVersion = 1
bytes 1..16  routeIncarnation UUID, RFC byte order
bytes 17..20 partition uint32, big endian
bytes 21..36 logical UUIDv7, RFC byte order
bytes 37..40 CRC32C of bytes 0..36, big endian
```

The public text form is unpadded Base64url with prefix `ndm1_` for Delay Message Identity and `ndc1_` for Command Identity. Decoders reject wrong prefix/version/length, non-canonical Base64url, CRC mismatch, unknown Route Incarnation, or partition outside that incarnation's fixed range. CRC detects accidental corruption only; authenticated tenant context still authorizes every operation.

Logical UUIDs follow RFC 9562 UUIDv7 and use a cryptographically secure random source. Their timestamp aids tracing but is never command order, trusted current time, TTL evidence, or uniqueness authority. Implementations must tolerate clock rollback and rely on the random field rather than inventing a cross-process sequence.

The UUID timestamp is not proof of current time or elapsed time. Once validated against Broker persistence time, it may derive the fixed Command retry or Message-identity freshness deadline; only Broker persistence time plus a signed source-ordered TIME_FENCE closes that deadline.

## Routing hash

`ROUTING_HASH_V1` is:

```text
digest = SHA-256(
    "nereus-delay-routing-v1" ||
    length-prefixed routeIncarnation bytes ||
    length-prefixed tenantRoutingScope bytes ||
    length-prefixed routingKey bytes)
partition = unsignedBigEndian64(digest[0..7]) mod partitionCount
```

`tenantRoutingScope` is an exact opaque 32-byte value generated by the control plane and permanently bound to the Route's Security Domain. It is distributed in the authenticated Route snapshot and cannot come from tenant payload, display name, or caller input.

For `DELIVERY_TIME_FIFO`, `routingKey` is the exact ordering-key bytes so one Ordering Domain remains on one shard. For unordered Schedule, it is the generated Delay Message UUID bytes. Length prefixes are unsigned 32-bit big-endian; strings are normalized and encoded as UTF-8 only where the protocol field explicitly defines text. Test vectors are normative for every SDK language.

Preparation chooses the active Route Incarnation, generates the logical UUIDs, computes the partition, constructs both IDs and canonical Command bytes, and hashes them before opening a Producer. Cancel and Reschedule validate/reuse the Delay Message locator. Signed Replay/Resolve/control System Mutations instead use a deterministic `systemMutationId + mutationHash` bound to the same exact shard subject; they do not create a Command Identity or appear in Command query.

## Topology changes

An existing Route Incarnation never changes partition count or hash version. Capacity expansion creates a new incarnation and SDK route snapshot. Old messages and all of their Client Commands/signed control mutations remain on the old route until its lifecycle safely retires. V1 does not move active messages between route partitions, and it makes no strict Ordering Domain guarantee across an explicit route-incarnation cutover.

If a stale SDK queues a first-seen Schedule after the route's immutable Broker-time acceptance cutoff, the shard durably rejects it as `ROUTE_NOT_ACTIVE`. The cutoff activation is source-ordered and cannot be retroactive to before its authenticated control request. A within-window duplicate of a Command already applied before cutoff remains an idempotent no-op rather than being revalidated under the later lifecycle state. Only the first logical Command's authoritative rejection or Definitive Not Queued result permits the caller to prepare a new Schedule on another route with new identities; an uncertain enqueue is retried unchanged.
