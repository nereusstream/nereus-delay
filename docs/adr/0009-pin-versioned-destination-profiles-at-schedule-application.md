# Pin versioned Destination Profiles at Schedule application

Nereus Delay accepts only pre-registered, versioned Destination Profiles rather than arbitrary per-message cluster, credential, or Adapter configuration. A Prepared Schedule carries the exact Profile version rather than `latest`. When that Command is authoritatively applied, the shard validates the immutable version and persists its canonical semantic destination, Broker Resource Incarnation, partition and Ordering Domain policy, and resulting Destination Lane without live target I/O. Existing Delayed Messages remain bound to that semantic version; changing a Profile affects new Schedules unless an explicit migration operation is designed and executed.

## Consequences

- A Schedule supplies `destinationProfileId` plus only the logical topic or partition choices explicitly permitted by that Profile. Cluster endpoints, authentication material, and arbitrary Adapter settings are never accepted from Command payloads.
-Current target routing is either an allowed explicit partition or `TARGET_PARTITION_HASH`: `SHA-256("nereus-delay-target-partition" || lp32(profileId) || u64be(profileVersion) || lp32(profileSelectedRoutingBytes))`, with the first unsigned 64 bits modulo the immutable target partition-count snapshot. The Profile fixes whether ordering key, message key, or Delay-Message-ID bytes are selected; empty is an explicit zero length. The Worker passes the resulting physical partition explicitly and never re-enters a client library's default partitioner.
- Profile semantic configuration stores the verifiable Kafka topic UUID or protected Pulsar incarnation/creation identity plus an immutable credential authorization-scope/policy digest, never the current secret reference or generation. A separately CAS-versioned private Credential Binding holds the service-owned reference. Equivalent rotation is transparent only after the platform verifier proves the new credential has the same immutable principal/resource/operation scope; changing that scope, cluster, topic resource incarnation, routing, or ordering semantics creates a new Profile version.
- Publication carries this identity to the Broker boundary: Kafka uses a v13+ pinned-topic-ID Produce channel that never substitutes current name metadata, and Pulsar Producers carry the expected token for `PULSAR_RESOURCE_GUARD` to check before every SEND is persisted. An activation-time lookup alone is insufficient.
- Each applied message persists `destinationProfileId`, `destinationProfileVersion`, `canonicalDestinationKey`, Broker Resource Incarnation, and `destinationLaneId`, so replay, retry, and long-delay publication do not depend on mutable control-plane lookup for semantic routing.
- Dynamic topics are allowed only under an explicit namespace or allowlist policy and hard tenant/shard Lane limits. Creating a new Lane is an authoritative admission decision; exceeding the limit yields `DESTINATION_LANE_LIMIT_EXCEEDED`.
- Destination Profile and Lane cardinality are bounded control-plane resources. Schedules cannot create a Producer, circuit breaker, Ready entry, or metric identity per message.
- Moving pending messages to a different semantic destination is not an ordinary Profile update or Reschedule. It requires an explicit, auditable migration design with new admission, ordering, idempotency, and rollback rules.
