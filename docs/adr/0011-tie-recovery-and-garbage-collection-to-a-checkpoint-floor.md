# Tie recovery and garbage collection to a checkpoint floor

Nereus Delay V1 publishes immutable per-shard Recovery Checkpoints through an authoritative Oxia checkpoint catalog and maintains an explicit Recovery Set with a monotonic Recovery Floor. Recovery may use only cataloged checkpoints at or above that floor; it never discovers arbitrary uploaded objects. Payload, terminal-state, and checkpoint garbage collection is permitted only after a Checkpoint Safety Barrier proves that every still-selectable recovery image is new enough not to require the retired resource.

## Checkpoint publication

- The shard event loop assigns every durable state batch a monotonic `shardMutationSequence` inside one Recovery Lineage. `checkpointId` and `recoveryLineageId` are nonzero random 16-byte identities fixed before I/O; a response-loss retry reuses the exact checkpoint identity, while only lineage genesis allocates the latter. A checkpoint manifest records lineage ID/generation, exact parent ID/manifest hash, restored-from checkpoint, complete database/shard identity, store format, included mutation sequence, applied Shard Log Position, owner epoch, source Store Incarnation, typed evidence cursors, and file identities/lengths/checksums. Immediately after successful local RocksDB checkpoint creation it also fixes one canonical `TrustedUtcIntervalEvidenceV1 createdAt`; upload/retry never resamples it, and checkpoint-age evidence is reconstructed from that field. `CHECKPOINT_MANIFEST_JSON_V1` is exact UTF-8 RFC 8785 JCS: 64-bit values/lengths/positions are unsigned decimal strings, file entries are strictly sorted by normalized UTF-8 name bytes, and duplicate keys, floats, non-canonical bytes, or unsorted/duplicate files are rejected. The source Store Incarnation is audit input only; each restore installs a fresh local Store token.
- `EvidenceCursorV1` is a closed tagged union. Kafka receipt cursors bind Lane/incarnation, exact topic UUID/partition/generation, contiguous `nextOffsetExclusive`, observed LSO, and guarded Broker-time anchor. Pulsar Attempt Journal cursors bind Lane/incarnation, resource token/creation identity/partition/generation, inclusive `(ledgerId, entryId, batchIndex, batchSize)`, and guarded Broker-time anchor. Arrays are strictly sorted by `(kind, Lane ID, Lane Incarnation, resource incarnation, physical partition, evidence generation)`; generation is part of the key, so protected old/new generations may coexist. Dominance is legal only for an identical full key and uses the type-specific contiguous position. Missing/incomparable cursors or retained-range gaps fail recovery.
- The current Owner creates a RocksDB checkpoint in a temporary local directory and builds a checksummed draft inventory. After winning `PENDING_UPLOAD`, it uploads immutable files under a generation-specific prefix, captures and verifies every exact object version/etag, then builds/uploads the final closed JCS manifest containing those identities. A draft cannot be finalized before object versions exist and is never catalog-visible. Files and final manifest remain non-authoritative until catalog publication.
- Immediately before publication, the Worker revalidates source assignment, shard identity, owner epoch, local database incarnation, and the exact base catalog version. Oxia CAS publishes the new catalog entry and monotonic latest generation, binding the exact manifest object version, byte length, and SHA-256 of its canonical bytes.
- A lost or failed CAS response is resolved by reloading the catalog and accepting only an exact replacement. Conflicting publication is retried from fresh authoritative state; stale Owners cannot publish.
- Before upload, Oxia holds the exact persistent `CheckpointUploadIntentV1(PENDING_UPLOAD)` bound to checkpoint/lineage/parent, token, Owner Lease/session, source Store, base catalog, Object Store Profile, creation evidence and upload deadline. Publication atomically changes it to `PUBLISHED` and catalogs the exact manifest; orphan cleanup must win the mutually exclusive `PENDING_UPLOAD -> REAPING` CAS. Deadline alone is not deletion authority while that Owner Lease/session remains current. After REAPING, cleanup waits for the certified old-Owner local guard and provider-request quiescence horizon, verifies no active Recovery Pin or published entry, exact-version deletes the unique prefix, and performs a final empty-prefix sweep so a late provider-owned PUT cannot recreate an orphan.

## Recovery and fallback

- Recovery loads the catalog and exact ancestry-bound Floor, pins one candidate in Oxia, tries the newest valid descendant first, and may fall back only to another verified descendant of that Floor. It verifies parent hashes, manifest/files, database/shard identity, store format, and required Shard Log/evidence replay positions before opening the database.
- The recovered database replays from the Adapter-defined successor of `appliedShardLogPosition`; Pulsar may seek the containing entry and skip already-applied batch members. If the source's earliest retained position is later, or no cataloged checkpoint verifies, the shard fails closed.
- The catalog defines a configurable bounded fallback count/age. The source-retention margin is computed from the Recovery Floor's Source Position, not merely from the newest checkpoint.
- All Command-affecting post-checkpoint mutations replay from the complete Shard Log. A valid replayed Admission first reconstructs the same `PUBLISHING`; if no live first-send gate survives, recovery appends the exact initial `UNKNOWN/OWNER_FENCED/RECOVERY_FIRST_SEND_UNCERTAIN/UNCERTAIN_HOLD` Outcome at a later Shard Log position. It never invents success or makes Admission apply depend on local token survival.

## Garbage-collection barrier

- Terminal transitions, payload references, reservations, and other externally backed state use `RESOURCE_RETIRE_INTENT_V1`, record their lineage-bound mutation sequence, and persist a reconstructible GC tombstone.
- A resource becomes checkpoint-safe only when the exact Recovery Floor checkpoint is an ancestry-proven descendant that includes the retirement mutation. A free scalar comparison from another branch is invalid.
- Payload deletion additionally waits for result/terminal retention, DLQ and replay requirements, and any active read or publish attempt. Exact guarded deletion is idempotent and its progress is durable.
- Old checkpoint objects are deleted only after an Oxia CAS advances the Recovery Floor and their protections/pins are released. Recovery never falls back below or outside the Floor ancestry, even if a later checkpoint is corrupt; inability to verify an allowed descendant is fail-closed.
- Local temporary directories and unrooted uploads have separate orphan reclamation and cannot influence recovery selection.
