# Make destination guarantees explicit capability Profiles

Nereus Delay V1 defines destination guarantees through a versioned Delivery Capability Profile pinned in each Destination Binding. Every Adapter must support `AT_LEAST_ONCE`; stronger Profiles are opt-in and valid only while all declared Broker, topic, producer, receipt, retention, and consumer prerequisites are continuously verified. Schedule application validates the exact immutable Profile version without live target I/O; a missing or drifted runtime prerequisite removes the Lane's READY entry and changes runtime readiness to `BLOCKED`, not the source-ordered `ADMIN_PAUSED` gate. The service never silently downgrades a bound message or describes local `ownerEpoch` as remote fencing.

Destination, Delivery Capability, Object Store and Evidence Verifier Profiles use the Protocol Registry's closed `ProfileSemanticEnvelopeV1`. `ProfileRefV1` includes kind, ID, version and a domain-separated hash of the canonical body; an Oxia serialization or display JSON cannot define equality. Destination/capability Adapter kinds must match. Runtime health, endpoint discovery and the current secret reference/generation remain outside the semantic hash; Destination/Object Store bodies bind only the immutable credential authorization scope and binding protocol. Any target identity, authorization scope, partition, timing, outcome, retention or conformance change requires a new Profile version.

## Common Adapter contract

- `fencePreviousOwner(binding, OwnerIdentity)` establishes only the remote exclusion that the selected Profile can actually prove.
- Every capability, including baseline, binds the actual Broker request to the Profile's Broker Resource Incarnation. Kafka uses `PINNED_TOPIC_ID_V1` Produce/Fetch v13+ with no name fallback. Pulsar uses an all-Broker-attested `PULSAR_RESOURCE_GUARD_V1` pre-persistence SEND check. An activation probe alone is not sufficient.
- `publish(attempt)` and `resolveUncertain` return a closed product, not a conflated enum. `sideEffect` is exactly `PUBLISHED`, `NOT_PUBLISHED`, or `UNKNOWN`; `disposition` is `NONE`, `MESSAGE_RETRIABLE`, `MESSAGE_PERMANENT`, `LANE_UNAVAILABLE`, `OWNER_FENCED`, or `ADAPTER_BUG`.
- `PUBLISHED` requires `NONE`. Only `NOT_PUBLISHED` may authorize ordinary retry or permanent message failure. `UNKNOWN` remains an `UNCERTAIN` attempt even when the same response also opens a Lane circuit or triggers an Owner/Adapter safety action.
- `resolveUncertain(attempt, evidenceCursor)` records its evidence cursor. A Profile without sufficient evidence must return `UNKNOWN`.
- `AT_LEAST_ONCE` has no remote outcome oracle. Recovery retries an `UNKNOWN` attempt with the same `delayMessageId + generation` and may create a destination duplicate. Consumers are expected to deduplicate on that logical key when duplicates matter.
- A profile capability mismatch removes READY and marks only its Destination Lane `BLOCKED(CAPABILITY_UNAVAILABLE)`; it does not change the Lane's administrative gate, pause Command application, or affect unrelated Lanes.

## Kafka transactional-receipt Profile

`KAFKA_TRANSACTIONAL_RECEIPT` is permitted only when the business topic and a Nereus-owned receipt topic are in the same Kafka cluster and finalized `transaction.version >= 2`; transaction V1 caps ProduceRequest at v11 and cannot carry topic UUIDs. A Route fixes `K` exclusive receipt-Lane slots per shard and creates `routePartitionCount * K` receipt partitions. Creating a strong Lane persistently allocates `(receiptLaneSlot, receiptSlotGeneration)`; the receipt partition is `shardPartition * K + receiptLaneSlot`. Each Lane has a bounded fixed pool of transactional channels identified by `(deploymentId, targetClusterId, routeIncarnation, shardPartition, receiptLaneSlot, receiptSlotGeneration, destinationLaneId, laneIncarnation, channelSlot)`; every admitted attempt persists its channel slot before send. A transaction contains the target record and one receipt keyed by `delayMessageId + generation`, with separately pinned target and receipt UUIDs; the receipt value binds exact Publish Attempt, Prepared Publish hash, target partition, and channel. A new Owner initializes the channels needed by that Lane before it publishes, which fences the previous producer identity and completes or aborts its unfinished transactions.

Receipt state is consumed with `isolation.level=read_committed` from that Lane's exclusive receipt partition. Recovery first fences every channel in the Lane, then captures/advances its receipt LSO only from a pinned Fetch v13+ response block that carries the exact receipt topic UUID and `lastStableOffset`; name-only ListOffsets is forbidden. Any exact hash/attempt receipt for the Generation proves `PUBLISHED`; absence is proof of `NOT_PUBLISHED` for one exact attempt only after this fence-and-LSO barrier. A receipt key with a different Prepared Publish hash is an integrity failure. The shard checkpoints every Lane receipt cursor, and receipt retention must cover every permitted Recovery Checkpoint plus replay margin; a retention gap is a recovery failure, not evidence of absence. Transactions may batch only bounded compatible records from one Destination Lane. An open transaction can hold back only that Lane's receipt LSO.

A receipt slot is released only after the old Lane has no active/retained evidence, all channels are fenced/closed, receipt and dedupe retention has elapsed, and the Checkpoint Safety Barrier covers retirement. Reallocation checked-increments `receiptSlotGeneration`; old receipts or transactional IDs can never be interpreted as evidence for the new Lane.

This Profile proves committed outcome and prevents a retry of an already committed attempt. It is not advertised as end-to-end exactly once unless every business consumer uses `read_committed`; read-uncommitted consumers can observe aborted transactional records. Target and receipt topics must satisfy the deployment's transactional durability policy.

## Pulsar Broker-dedup Profile

`PULSAR_BROKER_DEDUP` is permitted only for a persistent physical topic partition with Broker deduplication enabled, a certified dedup-state inactivity horizon, a continuously proven retained-producer cardinality strictly below `brokerDeduplicationMaxNumberOfProducers` with safety margin, a Nereus-owned persistent non-compacted Pulsar Attempt Journal, and guarded resource tokens for both target and journal. Nereus opens a stable producer identity for `(deploymentId, targetClusterId, routeIncarnation, shardPartition, destinationLaneId, laneIncarnation, physicalTopicPartition)` and allocates a strictly increasing sequence ID for each durable Publish Admission. Client/network retransmissions of that exact admitted attempt reuse its sequence, attempt identity, Prepared Publish hash, and bytes; every retransmitted SEND still passes the actual Topic token guard. A later Admission for the same Message Generation gets the next sequence only after the lower attempt is proven published or durably retired as not published. An unresolved lower sequence blocks later sends through that Lane's producer identity, never through another Lane. V1 disables client batching for this capability so one Broker send and sequence identity carry exactly one Publish Attempt.

Before target send, the Adapter durably appends a canonical `MAPPED(sequenceId, delayMessageId, generation, publishAttemptId, preparedPublishHash, producer/Lane identity)` record and persists its acknowledged journal position. The current shard Owner holds `ExclusiveWithFencing` on its Nereus-owned physical journal partition, which fences old mapping writers without touching the shared business topic. Lost mapping ACK causes only exact mapping retry; target send is forbidden. A definitively un-published attempt remains in a retirement-pending admitted state until a durable `RETIRED_NOT_PUBLISHED` record is acknowledged; only then may it move to retry/terminal state and a later Admission allocate the next sequence.

On takeover, the Adapter pre-subscribe guards every Journal reader connection generation, replays from its typed batch-aware contiguous cursor, reconnects that exact Lane/physical-partition producer, and compares the Broker-reported last published sequence ID with reconstructed mappings. A value at or above a non-retired mapped sequence proves `PUBLISHED`; a lower value proves `NOT_PUBLISHED` only if the Profile proves both inactivity retention and producer-snapshot cardinality preservation from the mapping's guarded Broker-time anchor. Broker high water above journal mapping, mapping conflict, evidence-retention gap, cap pressure/omitted producer, or an expired horizon is `PULSAR_EVIDENCE_DIVERGENCE` and fail-closed. The generic partitioned-producer maximum is not sufficient evidence for one physical partition. Without the journal and cap proof, Broker dedup is only a baseline duplicate-suppression optimization.

Pulsar `ExclusiveWithFencing` is topic-wide and therefore is not used on ordinary shared business topics. A future producer-scoped fencing extension may strengthen this Profile, but it does not change the V1 baseline.

## Operational consequences

- Destination Profile registration performs a capability probe and records immutable capability version, evidence topic/partition policy, transaction or producer-identity scheme, and required retention horizon.
- Runtime probes detect configuration drift. Loss of deduplication, receipt readability, transaction authorization, or sufficient evidence retention opens the Lane circuit and alerts operators.
- Metrics and APIs report the bound capability and whether an `UNCERTAIN` outcome is resolvable; they do not collapse `UNKNOWN` into failure.
