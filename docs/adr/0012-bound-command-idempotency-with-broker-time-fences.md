# Bound Command idempotency with Broker-time fences

Nereus Delay V1 gives every Prepared Command a fixed `retryUntil` and guarantees idempotent application for every physical record durably appended within that Command Retry Window before the partition closes it. Every record whose Broker persistence time is later than its window, or whose deadline was already closed by an earlier source-ordered time fence, is rejected at that Source Position as `COMMAND_RETRY_WINDOW_EXPIRED`, whether or not compact dedupe still exists. The outcome cannot depend on GC timing, Broker timestamp rollback cannot reopen a closed window, and an old Command cannot become a new operation after reclamation. An existing first logical result is never overwritten. Deduplication garbage collection requires a persisted closed-time watermark through `retryUntil` and a Checkpoint Safety Barrier; a wall-clock TTL alone is insufficient.

## Authoritative ingress time

- Kafka Command Topics require `message.timestamp.type=LogAppendTime`. Pulsar Command Topics require broker entry metadata with `AppendBrokerTimestampMetadataInterceptor` and exposure of that metadata to the Ingress Consumer.
- Route activation fails closed if the Adapter cannot obtain an authoritative Broker persistence timestamp. Client `createdAt`, UUID time, and message publish time are not substitutes.
- The Ingress Adapter adds `brokerPersistedAt` to the server-side application context. A Command appended at or before `retryUntil` remains valid even if outage, replay, or backlog delays its application beyond the window.
- UUIDv7 remains the required ID encoding because it embeds a Unix-millisecond creation field and random identity, but its timestamp is used for format, skew, and first-seen age validation—not for Command ordering or as the sole deduplication clock.
- For every **Client Command**, `retryUntil = checkedAdd(uuidV7Time, commandRetryWindow)` and Broker persistence time must not exceed it. For a first-seen identity with Broker persistence time `bp`, checked integer arithmetic must prove `checkedSub(bp, maximumPreparationAge) <= uuidV7Time <= checkedAdd(bp, maximumUuidFutureSkew)`; overflow/underflow or a value outside the interval is a stable validation rejection. A caller cannot refresh an old Command Identity by supplying a later retry deadline. Signed System Mutations use deterministic 32-byte IDs and a separately bounded signed `mutationRetryUntil`; they do not pretend that ID bytes contain UUID time.
- Every signed System Mutation proves `bp <= mutationRetryUntil <= checkedAdd(bp, maximumSystemMutationRetryWindow)`. Its dedupe/audit survives until that deadline is source-closed, the fence is applied, a descendant Recovery Floor contains the mutation, and `systemMutationAuditMinimum` has elapsed. Both configuration fields are mandatory and cross-validated with source/Broker retention and the non-borrowable system-writer reserve.
- Ordinary records use their Broker persistence timestamp for their own retry/timing validation but do not advance another Command's reclamation watermark. A dedicated system fence writer emits a canonical signed `TIME_FENCE(route, partition, closeThrough, keyVersion, proofTime, proofId)` only after `proofTime.earliest >= closeThrough + configured safety margin`. `proofId` is the Protocol Registry domain-separated hash of exact shard, boundary, key version and canonical `TrustedUtcIntervalEvidenceV1`, never a random token; outer signing-key version must match the fence key version. The Route retains immutable public verification-key versions; tenant topic-write authority alone cannot forge a fence.
- Applying a valid fence monotonically advances `closedIngressDeadlineThrough = max(previous, closeThrough)` in the same WriteBatch. Before the applicable Command/System-Mutation dedupe lookup, a later record with its signed retry deadline at or below `closedIngressDeadlineThrough` is position-level expired even if its own Broker timestamp regressed. The same source-ordered watermark logically turns each still-reserved payload whose reservation deadline is at or below the boundary into `RESERVATION_EXPIRED`; its bounded expiry scanner only materializes this closed overlay and cannot race a later Commit. A bad signature or scope is position-level `UNAUTHORIZED_SYSTEM_MUTATION` and cannot advance the watermark.
- A first Schedule for a previously absent Delay Message Identity applies the same UUID/Broker-time age rule and computes `messageIdentityReuseUntil = uuidV7Time + maximumPreparationAge` with checked arithmetic. An existing active or retained entity authorizes later Cancel, Reschedule, and replay regardless of ID age.

## Retention and reclamation

- The command-dedupe namespace in `dedupe_cf` retains `commandId`, `commandHash`, the stable minimal authoritative outcome, first Source Position, `retryUntil`, and a reclaim sequence. Full diagnostic results in a separate result namespace of the same CF may have a shorter query retention, but duplicate application can still return the original stable outcome while the compact dedupe record exists.
- A dedupe record is reclaimable only when: persisted `closedIngressDeadlineThrough >= retryUntil`; Source Position has advanced through the fence that formed that closure; the Recovery Floor includes the dedupe/application mutation; and the configured minimum idempotency retention has elapsed.
- When full terminal/entity history is reclaimed, `id_cf/MESSAGE` becomes a compact `RETIRED_IDENTITY(messageIdentityReuseUntil, retirementMutationSequence)` tombstone in the same WriteBatch. It is reclaimable only after `closedIngressDeadlineThrough >= messageIdentityReuseUntil`, source progress through that fence, a Recovery Floor that includes retirement, and minimum identity retention. Before deletion, reuse is `DELAY_MESSAGE_ID_CONFLICT`; after deletion, the already-closed freshness deadline makes reuse `DELAY_MESSAGE_ID_EXPIRED`, even if a later Broker timestamp regresses.
- Time fences are authenticated periodic ordered no-op records. If the writer, checkpoints, or source progress stall, dedupe/reservation GC stops. Ordinary Command application continues only while the shard's dedicated fence-evidence budget can retain the worst-case durable dedupe/result/quarantine evidence for the next record.
- The Owner may bounded-fetch and strictly decode the exact next Shard Log record to distinguish a signed fence from a business record, but before applying/consuming/acknowledging a business record it checks `remainingFenceEvidenceBytes >= worstCaseNextRecordEvidenceBytes + fenceStopSafetyMarginBytes` and the equivalent record-count bound. If false, it stops **before applying** that exact Source Position, leaves it unacknowledged, enters runtime state `FENCE_STALLED_CAPACITY`, and publishes `source_partition_paused{reason="time-fence-capacity"}`. It never consumes a business record for which it cannot durably record the deterministic result.
- The reserve and high watermark provide enough space to persist the stop/audit state and every already-read bounded batch prefix. A fence appended *after* the blocked business record cannot be reached by skipping Source Position and therefore cannot by itself resume the shard. The only no-expansion exception is when the exact next record is itself an authenticated `TIME_FENCE` and the dedicated fence reserve can apply it; otherwise an operator must first activate a larger certified evidence envelope or migrate the shard to a Worker with one, then replay the same successor in order through the fence. Guarded GC, a complete counter/invariant audit, and the same-position recheck precede normal resume. No destination condition can trigger this reason.
- A full result queried after its retention but while compact evidence remains returns `RESULT_EXPIRED` with the stable status/outcome code. A bare unknown ID is still `UNKNOWN`; expiration is not proof that a Command existed.
- A Delay Message ID uses the same time-bearing, route-bound identity discipline. The compact tombstone bridges terminal reclamation to the source-ordered closure of first-seen freshness, so first-seen age validation never has a resurrection gap; commands targeting an existing long-lived message remain valid because the active entity record proves its identity.

## Configuration invariant

The Command Retry Window, `maximumSystemMutationRetryWindow`, `systemMutationAuditMinimum`, `maximumPreparationAge`, `maximumUuidFutureSkew`, trusted-clock skew budget, time-fence interval, Command Topic retention, maximum outage/replay duration, checkpoint SLA, result retention, dedicated fence-evidence bytes/records, worst-case next-record evidence charge and stop margin are validated together with checked arithmetic. No configured retention may make an on-time queued record unrecoverable or allow its identity evidence to disappear before all admissible duplicates are ordered and checkpoint-safe.
