# Use reserve, upload, and commit for large payloads

Nereus Delay does not accept an arbitrary pre-uploaded object reference in a normal Schedule Command. Payloads above the inline threshold use a reserve-upload-attest-commit protocol: a `PREPARE_LARGE_SCHEDULE` Command durably reserves message identity, destination capacity, an opaque service-owned object location, and an upload deadline; the client uploads immutable bytes; an authenticated service API verifies the exact object and issues a deterministic signed `PayloadCommitProof`; then a `COMMIT_LARGE_SCHEDULE` Command atomically converts the reservation into `SCHEDULED` without live Object Store I/O. This makes every valid upload traceable to durable shard state, prevents a fabricated Commit from poisoning source progress, and gives orphan reclamation a safe owner.

## Protocol

- Applying `PREPARE_LARGE_SCHEDULE` validates the immutable destination and Object Store semantics plus quota, persists a `PAYLOAD_RESERVED` record whose durable binding pins the exact `PayloadProofTrustSetRef` and exact `OBJECT_STORE ProfileRef`, and returns a durable `PayloadReservationReceipt`. Registry field 15 carries that Object Store Profile; the receipt and typed Commit proof must equal the complete ref. It does not create an active timeline entry or claim that a Delayed Message is scheduled.
- An authenticated API can issue or reissue a short-lived opaque `PayloadUploadHandle` only while that reservation is valid. The handle fixes tenant, shard, `delayMessageId`, payload identity, object-store Profile, object key, expected length/SHA-256, upload deadline, and authorization scope. It is sensitive capability material and never enters the Command result, RocksDB, checkpoint, log, or ordinary receipt. Callers cannot supply arbitrary buckets, keys, endpoints, or credentials. Each service-owned Object Store Adapter instance acquires a bounded `OBJECT_STORE_ADAPTER` `CredentialUseLease` by resolving the immutable reference and using one Head-compare/protection transaction; it does not read Oxia for each provider call. Immediately before provider ownership, the Adapter validates the local lease kind/holder/generation/digest/expiry and loaded immutable-reference fingerprint, and reaches provider ownership inside the configured local-age bound. Lease/fingerprint/provider unavailability returns the closed retryable handle outcome without blocking source application.
- Upload is idempotent and immutable: the Adapter uses conditional `ifAbsent` creation with an expected checksum. Retrying an existing exact object succeeds after HEAD verification; different bytes at the same payload identity are `PAYLOAD_OBJECT_CONFLICT`.
- After upload, authenticated `attestPayloadUpload` reads the current reservation and verifies the service-owned immutable object by exact key/version/etag, length, SHA-256, and metadata. It returns a canonical, non-secret `PayloadCommitProof` whose fields bind reservation, tenant/route/shard/message, Object Store Profile ID/version/semantic hash, exact object key/version/etag, length/checksum, pinned trust-set version, proof-key version, and `notAfter=reservationExpiry`. The Protocol Registry's domain-separated `proofId` preimage covers fields 1–8 and 10–16, excluding only signing-key field 9 and the proof ID/signature fields themselves; the signature digest covers fields 1–17. An authorized re-signing therefore preserves semantic proof identity.
- The immutable trust set distinguishes historical verification keys from keys authorized to issue a first-seen Commit. `PAYLOAD_PROOF_TRUST_SET_ACTIVATE` and `PAYLOAD_PROOF_ISSUANCE_CLOSE` are signed source-ordered shard controls. A reservation pins the set active at its Prepare position; the set must keep its old signer authorized through the reservation TTL or pre-authorize a successor that can re-attest the same object/proofId. Closing an issuer prevents a later first-seen Commit under that key but never removes the public bytes required to replay an earlier accepted Commit. An activated trust set whose verifier bytes are unavailable is a deployment invariant failure, not a business rejection.
- A deterministic Ed25519 signature makes reissue under the same key version byte-identical. Private signing keys never enter Commands, RocksDB, checkpoints, or receipts.
- A transient provider failure, Credential Binding drift, or not-yet-visible object makes attestation retryable before a Commit exists; it cannot block the Command partition. Applying `COMMIT_LARGE_SCHEDULE` performs only canonical proof/signature/scope, reservation-state, exact identity, quota, and Broker-time deadline checks. It never contacts Object Store. The durable Prepare—not the later Commit body encoding or current adapter configuration—chooses both trust-set and Object Store authority. A typed proof must match the full pinned Profile ref; the legacy compatibility proof can only match its semantic hash. This check also precedes an already-committed retry fast path. A forged or mismatched proof is a stable rejection. The durable WriteBatch creates timeline/id state, stores the payload descriptor, consumes the reservation, records the Command result, and advances Source Position.
- Handle and attestation APIs first authorize the tenant and read through the reservation receipt's Query Barrier; a queued-but-not-applied Prepare cannot issue object authority. They return closed typed outcomes, never exception text as protocol. Handle outcomes are `ISSUED | RESERVATION_EXPIRED | RESERVATION_ABANDONED | RESERVATION_CLOSED | NOT_FOUND_OR_NOT_AUTHORIZED | SHARD_TRANSITIONING | SHARD_UNAVAILABLE | INTEGRITY_ERROR | OBJECT_STORE_UNAVAILABLE_RETRYABLE`. Attestation outcomes are `ATTESTED | OBJECT_NOT_READY_RETRYABLE | OBJECT_STORE_UNAVAILABLE_RETRYABLE | OBJECT_IDENTITY_CONFLICT | RESERVATION_EXPIRED | RESERVATION_ABANDONED | RESERVATION_CLOSED | NOT_FOUND_OR_NOT_AUTHORIZED | SHARD_TRANSITIONING | SHARD_UNAVAILABLE | INTEGRITY_ERROR`.
- Prepare and Commit are separate Prepared Commands with separate stable Command identities. An uncertain enqueue retries the exact corresponding Command. Cancel may abandon an uncommitted reservation; Nereus Delay does not infer a Commit after reservation expiry.
- Source Position decides Cancel/expiry/Commit/Lane-close races. Reservation expiry is the logical overlay established when a signed `TIME_FENCE` advances `closedIngressDeadlineThrough` through `reservationExpiry`; a bounded expiry cursor only materializes that already-frozen state and counters. Every Commit/query/handle path consults the overlay, so source lag or a crash midway through materialization cannot reopen the reservation. After one Commit succeeds, the local committed projection retains the Registry descriptor's ReservationId and accepted `proofId`; only a different Command that reproduces that exact ProofId/object identity and verifies under the retained historical public key is `APPLIED(ALREADY_COMMITTED)` without double accounting. Issuance close blocks a new first-seen proof but does not invalidate this historical verification. A different pinned Profile identity or invalid signature is a stable proof rejection, while a different object identity, length, checksum, or ProofId is `PAYLOAD_COMMIT_CONFLICT`. A Commit after prior abandon or closing fence returns that exact terminal reservation outcome. A source-ordered `CloseDestinationLane` freezes each uncommitted reservation as `PAYLOAD_RESERVATION_ABANDONED(LANE_CLOSED_BEFORE_COMMIT)`, invalidates upload/attestation authority, and makes every later Commit return stable `PAYLOAD_RESERVATION_CLOSED`; uploaded bytes follow the ordinary checkpoint/fence-guarded object-GC path.

## Lifecycle and safety

- The payload-reference namespace in `id_cf` tracks reservation, committed reference, terminal eligibility, exact object identity, and guarded-deletion progress. Reservations count against tenant, Lane, shard, and disk/object-byte quotas.
- Explicitly abandoned/closed reservations remain durable because an already-issued or in-flight upload handle may still create the object. They become externally reclaimable only after `closedIngressDeadlineThrough >= uploadDeadline`, an ancestry-proven Recovery Floor covers the terminal mutation, the handle credential/request quiescence horizon has elapsed, and exact multipart sessions have been aborted. GC performs a final version-aware HEAD/delete after that horizon and logs delete confirmation; a prior `HEAD not found` is not completion while an old PUT can still arrive. Later records cannot reopen the deadline with a regressed Broker timestamp. Thus a Commit persisted before its deadline and before the closing fence, but applied after source lag, cannot lose its object, and a Cancel followed by late PUT cannot create an ownerless object.
- A committed Payload Object remains immutable through Schedule, Reschedule, retry, `UNCERTAIN`, DLQ, and any replay window. It is deleted only after terminal/result retention and a checkpoint-reference safety barrier prove that no recoverable state can require it.
- Inline payloads keep the one-Command Schedule path. Threshold choice is benchmark-driven, but the semantic split and maximum sizes are explicit.
- Command hashes include the stable payload descriptor and canonical `PayloadCommitProof`, never presigned URLs, credentials, transient upload sessions, or physical retry metadata.
