# Isolate Destination Lanes from Command application

Nereus Delay V1 guarantees that a failed Destination Lane cannot stop Command application or indefinitely starve a healthy Lane. Command ingestion and durable state application are independent of destination publishing; source application pauses only for shard ownership, durability, corruption, disk-safety, or recovery-correctness failures. Destination backlog is handled through persistent Lane state and Schedule Admission Control, not by pausing the Command Topic partition.

## Persistent Lane scheduling

- `DestinationLaneId` is the versioned canonical hash of tenant Security Domain, Adapter type, authenticated destination cluster/resource incarnation, exact physical topic/partition, Destination Profile version, capability profile, and full Ordering Domain or configured unordered bucket. The tuple and golden vectors are identical to the main key contract; no shorter alias may be used for channel identity. A Lane is the publish quota, concurrency, retry, circuit-breaker, fairness, due-lag, and failure-metric unit inside a shard; it is not an ownership or checkpoint unit.
- A Lane persists two orthogonal axes. The source-ordered `admissionGate` is `OPEN`, `ADMIN_PAUSED`, `ORDERING_BROKEN`, `CLOSED`, or `RETIRED`; runtime `runtimeReadiness` is `RECOVERING_EVIDENCE`, `READY`, or `BLOCKED`. A first Schedule allocates its Lane Incarnation/grants, initializes source-ordered `laneControlVersion=1`, and writes `OPEN + RECOVERING_EVIDENCE` without destination I/O. A Lane-scoped activator establishes/fences its channel and catches up evidence before `READY`; only `OPEN + READY` may scan, Claim, or admit. Runtime/index churn uses a separate `laneVersion` and never changes the Lane control CAS.
- `READY` is backed by a persisted `ReadyCertificateV1` bound to exact `OwnerIdentity`, Store Incarnation, Lane Incarnation, Adapter channel generation, evidence barrier/cursors, Broker-resource attestation/config generation, a Head-compared/protection-CASed `DESTINATION_CHANNEL` Credential Use Lease, and Trusted-UTC expiry no later than that lease. Mandatory `readyCertificateTtl` and `readyCertificateRenewalLead` satisfy `0 < lead < ttl <= every bound prerequisite validity interval`. Claim, Admission preparation, and first Producer call revalidate the live certificate/lease; the first physical call validates the loaded credential fingerprint locally and reaches library ownership inside the configured local age bound, with no per-message Oxia read. Admission apply/replay instead validates the embedded certificate as historical decision evidence and never lets later runtime generations rewrite an on-time log record. Owner/store/channel/evidence/attestation/credential change, resolved fingerprint drift, or impending expiry first atomically deletes the READY key, increments `laneVersion`, and moves readiness to `RECOVERING_EVIDENCE` or `BLOCKED`; only then may the old channel be closed. A stale in-memory activator or Claim cannot recreate READY or prepare a new Admission with an older generation.
- Runtime capability drift changes only runtimeReadiness. Owner/store change returns it to `RECOVERING_EVIDENCE` but never clears a source-ordered pause/break/close. `PauseDestinationLane` removes the READY entry and revokes reversible Claims; `ResumeDestinationLane` changes only `ADMIN_PAUSED -> OPEN` and cannot clear capability `BLOCKED` or reopen `ORDERING_BROKEN/CLOSED`.
- `timeline_cf` uses the exact versioned DUE/ORDERED/READY layouts in ADR-0025; all message keys are Lane-first and include Generation. The server derives `sourceOrderToken` from Source Position. `id_cf` retains the exact Lane and timeline key for Cancel and Reschedule.
- The Lane-state namespace in `meta_cf` persists the exact Registry `ActiveLaneStateV1`: both axes, `laneControlVersion`, per-Lane charge, earliest-action/eligibility, circuit/failure, weight, runtime `laneVersion`, optional exact current-ready-key state, optional exact `ReadyCertificateV1`, and retirement progress. Exactly the `OPEN + READY` Lanes with a valid certificate and schedulable work have one physical `timeline_cf/READY` key; all others have none. Each relevant update—including certificate invalidation, Pause, Resume, Break, and Close—atomically deletes the old key and optionally puts the replacement. The five closed per-shard scheduler values persist ring/cursor/deficit/round/last-served state; the bounded Worker outer ring is reconstructed rather than falsely persisted across independent shard DBs. Versioning rejects old keys seen by concurrent snapshots; unexplained stale/missing/gate-inconsistent keys fence scheduling and trigger deterministic rebuild.
- `timeline_cf/EXPIRY` is independent of READY. Every active Generation that can lose future Admission at `expireAt` has one versioned expiry key even while the Lane is paused, broken, blocked, recovering evidence, in circuit backoff, or waiting for a later retry. A bounded Trusted-Time scanner prepares `EXPIRE_GENERATION_V1`; Source Position orders it against Cancel, Reschedule, and Admission.
- A bounded weighted deficit round-robin algorithm limits every Lane visit by messages, bytes, and time. Given an `ACTIVE_FOR_COMMANDS` shard, available global capacity, and a bounded number of `READY` Lanes, every continuously ready healthy Lane is visited within one complete scheduler round; byte service follows its configured quantum as deficit accumulates.
- Publish permits and byte permits are acquired before claim. Only immediately dispatchable bounded records move to `inflight_cf`; all other due records remain durable in `SCHEDULED` or `RETRY_WAIT`. No destination outage creates an unbounded in-memory queue.
- Adapter submission, client-library buffers, metadata waits, and callback execution preserve the same Lane boundary. A shared Producer/transport is allowed only with proven per-Lane reserve and no cross-Lane head blocking; otherwise the Adapter uses bounded Lane-scoped channels.

## Capacity and backpressure

- Lane, tenant, shard, and Worker limits account for all non-terminal records. A Lane at its hard pending limit still has its Commands consumed; new Schedules are durably `REJECTED(HARD_QUOTA_EXCEEDED)`, while Cancel, permitted Reschedule, and other Lanes continue.
- V1 Reschedule changes scheduling fields but not destination or payload capacity. A future operation that moves or enlarges a message must pass fresh destination admission.
- Schedule admission stops before the disk hard watermark and reserves storage for Cancel, Reschedule, command results, terminal transitions, GC, checkpoint metadata, and compaction.
- Destination outage, retry backlog, open circuits, target throttling, and exhausted Lane executor permits are forbidden source-pause reasons. Source application pauses only when the complete shard can no longer commit state safely and recoverably.
- Source Position order remains strict: a later Command cannot overtake earlier records. This decision isolates destination publish failure, not ingress traffic floods; tenant command-rate controls and route/partition policy address ingress contention.

An irreversible Break/Close is not erased by runtime retirement. After the source-ordered gate reaches `CLOSED` and all retirement preconditions hold, the same registered `meta_cf/LANE[destinationLaneId]` key atomically replaces the active Lane value with exact `LaneTerminalGuardV1(finalGate=RETIRED)`; there is no extra CF tag/namespace. The guard retains the final control version, last terminal source position, incarnation, Profile/canonical Lane identity and retire intent until the Route/Profile and every retained Prepared Command/Recovery Set reference are gone. The same old tuple can never recreate as `OPEN`; continued traffic uses a new Profile/Ordering Domain and therefore a different Lane ID.
