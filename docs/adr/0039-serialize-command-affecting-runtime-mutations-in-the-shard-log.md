# Serialize command-affecting runtime mutations in the Shard Log

Nereus Delay treats each physical Command Topic partition as the complete ordered **Shard Log** for one Delay Shard. The partition contains both tenant `CLIENT_COMMAND` records and authenticated service-only `SYSTEM_MUTATION` records. It is still one Broker log—not an additional Nereus log—but checkpoint plus replay is complete only because every post-checkpoint mutation that can change a later Command result, quota decision, query result, or external-deletion obligation is represented in this same Source Position order.

## Complete-log rule

A callback, timer, evidence reader, GC worker, or scheduler may calculate and prepare a mutation, but it cannot directly make that mutation authoritative if the mutation can affect a later Command. It must enqueue an immutable, canonical, signed System Mutation with a stable `systemMutationId + mutationHash`, retry the exact bytes on an uncertain enqueue, and let the shard consumer apply it in Source Position order. At minimum logs:

- `APPLY_SHARD_CONTROL`, binding an exact authenticated Control Operation target to a source-ordered Profile/quota/admission/Lane boundary;
- `REPLAY_DEAD_LETTER` and `RESOLVE_UNCERTAIN`, binding privileged operator actions to exact message/attempt preconditions;
- `TIME_FENCE`, advancing an authenticated Route/partition deadline closure;
- `PUBLISH_ADMISSION`, containing the exact Claim precondition, current Ready Certificate digest, channel/resource identity, full reproducible `PreparedPublishDescriptor`, its canonical hash, and reserve charge;
- `PUBLISH_OUTCOME`, including the exact attempt, typed side-effect evidence, disposition, Trusted-UTC observation, closed retry decision, and charge transfer;
- `EXPIRE_GENERATION`, carrying the Trusted UTC interval evidence that proves expiration;
- `EVIDENCE_RESOLUTION`, for Kafka receipt or Pulsar Attempt Journal reconciliation not already represented by a privileged Resolve mutation;
- `RESOURCE_RETIRE_INTENT` and `RESOURCE_DELETE_CONFIRMED`, binding every externally deleted payload/checkpoint/export dependency to a replayable tombstone and GC task.
- `CLAIM_RESULT`, the sole authority for a proven permanent pre-send materialization/serialization/size/payload result that moves a Claim to `DEAD_LETTER`;
- `DLQ_EXPORT_RESULT`, serializing each numbered physical DLQ export attempt outcome plus evidence-based resolution, retries, retained charge, and completion state.

Purely reversible or derivable runtime work—Claim creation/revocation, transient materialization backoff, partial scratch, cache state, circuit probes, Ready-index rebuild, executor permits, metrics, and bounded scheduling cursors—does not require a System Mutation. A transient pre-send failure restores the same semantic timeline key/work kind/authority/candidate/digest with a checked-incremented runtime revision/instance digest and never consumes a Publish Admission count or creates message `RETRY_WAIT`. The semantic digest excludes that local revision so recovery cannot invalidate an already persisted Admission merely by requeueing. Once a proven permanent Claim result terminalizes the Generation it is no longer reversible scratch and must use `CLAIM_RESULT`. Source-ordered Close materialization is derivable from its marker and frozen cursor inputs, so it need not emit one record per materialized message. Likewise, a signed TIME_FENCE atomically establishes the effective expiration overlay for every reservation deadline it closes; the reservation-expiry cursor merely materializes that already ordered outcome and is safe to replay without per-reservation mutations.

## Publish Admission

Claim remains reversible. To seek Publish Admission, the current Owner freezes an exact Claim precondition, Ready Certificate, Trusted-UTC decision interval, Prepared Publish descriptor, and reserve request, then prepares and enqueues `PUBLISH_ADMISSION`; a tenant Producer cannot forge it. When that record is consumed, the shard validates those immutable facts and Broker persistence time, then compares only source-ordered Message/Lane/attempt/quota preconditions. Ephemeral lease, Store, token, apply-time wall clock, or current channel state never changes the replay result of a valid, on-time record.

If the full worst-case vector does not fit, the deterministic System Mutation result is `ADMISSION_CAPACITY_GATED`: the same WriteBatch revokes the reversible Claim, restores the prior timeline eligibility with bounded backoff, records the mutation result, and advances `appliedShardLogPosition`. It allocates no attempt/attempt number, writes no `PUBLISHING`, and invokes no Producer. A later logged outcome/retirement can release capacity and the scheduler may then prepare a new exact Admission mutation. This gate is not a Schedule rejection and never stops source progress.

Only a successful Admission atomically charges the reserve and writes `PUBLISHING`, the Publish Attempt ledger's immutable Admission prefix plus exact obligation ref, and `appliedShardLogPosition`; later ledger fields advance only through registered Outcome/evidence/retirement mutations.

Only after that WAL sync may a Producer be invoked. A matching still-live Owner may send only when it also holds the exact live Owner/Store/Claim/token/certificate/monotonic-time gate for that System Mutation. A replay, owner/store change, or loss of that gate must not issue a first send, but it still reconstructs the same durable `PUBLISHING`; recovery then appends the one initial `PUBLISH_OUTCOME(UNKNOWN, OWNER_FENCED, RECOVERY_FIRST_SEND_UNCERTAIN, UNCERTAIN_HOLD)` at a later Shard Log position and uses capability evidence or the pinned baseline policy. Any later verified result is an Evidence Resolution, not a second initial Outcome. Thus Admission replay is state-deterministic without silently repeating an already-issued old-Owner request, while a crash between Admission and the original call remains conservatively uncertain.

An Admission record ordered after a Cancel, Close, Break, expiration, or stale Generation is an idempotent `STALE_SYSTEM_MUTATION` with no side effect. If it is ordered before the Command, the durable `PUBLISHING` state makes that Command `TOO_LATE`. Physical Source Position, not enqueue-call timing, is the authority.

## Outcome, time, quota, and GC

Destination callbacks and evidence readers append exact Outcome/Resolution records. Until the corresponding record is applied, the authoritative Generation remains in its prior admitted/uncertain state. `RETRY_WAIT` is produced only when every earlier admitted attempt is definitively not published and retired; otherwise the logged result retains `UNCERTAIN`.

The DLQ outbox is durable before any export call, but its callback is not authority. The terminal record fixes attempt 1; every physical callback/timeout has one `(dlqExportId, physicalAttemptNo)`-bound `DLQ_EXPORT_RESULT`, and later proof has an evidence-ID-bound resolution. A logged policy decision is the only authority to increment the checked attempt number, while every attempt reuses the deterministic export envelope/ID. These records move the outbox through `PENDING/UNCERTAIN/PUBLISHED/FAILED_PERMANENT`; Nereus Delay has no unregistered manual-abandon transition. Payload/export protections release only after a qualifying logged result is covered by a descendant Recovery Floor.

Trusted-time expiration is a logged mutation. Its body proves `earliestUtcNow >= expireAt`; replay validates the same immutable evidence instead of rerunning a timer. Runtime terminal transitions and their charge transfers therefore appear before or after a later Schedule/Cancel/Replay in the same durable order, eliminating quota and state-result divergence after local-disk loss.

Before deleting an external object, the shard applies a floor-protected `RESOURCE_RETIRE_INTENT` that contains the exact identity/version and reconstructible GC task. After exact delete/HEAD resolution it logs `RESOURCE_DELETE_CONFIRMED`; a permitted restore either sees the live reference or replays the durable retirement/deletion obligation. Completion tombstones are retained until a later Recovery Floor covers them.

## Authentication and replay

Each Route Incarnation pins a System Mutation schema set and verification-key version. System writers use a service-only Broker ACL and the exact Protocol Registry preimages: mutation hash binds framing/log/envelope/body versions, mutation type, exact shard subject, retry deadline and canonical body; signature additionally binds frame magic/kind, mutation ID/hash, typed author and signing-key version. Owner-authored runtime mutations additionally bind exact OwnerIdentity/lease-fencing digest; control mutations bind one immutable Oxia Control Operation and its enumerated target; `TIME_FENCE` binds the Route fence-writer identity/key set. The Worker validates Broker route binding, activated version tuple, historical accepted-writer generation, hash, signature and body-specific equalities before applying. It does not reject a legitimate old-Owner Admission merely because a new Owner now applies it; current lease state gates only a new physical call. Writer keys/generations and audit history remain protected through mutation retry and Recovery-Floor replay. Nereus Delay assumes accepted service writers are non-Byzantine; compromise of a service signing key is a disaster/security boundary, not a guarantee provided by Owner Epoch. Invalid system records are bounded position-level rejections and never acquire mutation authority.

For `APPLY_SHARD_CONTROL`, the signature domain additionally binds Control Operation ID/request hash, target index, semantic version/hash and expected prior control version. `ControlRef` does not embed its own expected mutation ID/hash because that would make the canonical hash self-referential; those two field names/numbers are reserved. After the complete body is hashed, the Oxia operation enumerates the resulting exact expected mutation ID/hash for every target. An exact duplicate is a no-op; changed bytes, an unlisted target, cross-shard reuse or a marker not yet registered in Oxia is `UNAUTHORIZED_SYSTEM_MUTATION` and has no control effect.

`systemMutationId` is a deterministic 32-byte SHA-256 identity over mutation type, the Registry's type-specific logical operation identity, exact shard subject and version-bound mutation hash; it is not UUIDv7. A control identity binds operation ID + target index + control/mutation kind, so multi-stage quota markers on one shard use distinct enumerated targets; Evidence Resolution binds attempt + evidence ID, while one attempt has exactly one initial Outcome. Retire also binds resource-state version. Its signed `mutationRetryUntil` is bounded against Broker persistence time by mandatory `maximumSystemMutationRetryWindow`. `dedupe_cf/SYSTEM_MUTATION` stores the complete activated version tuple plus ID/hash/type/author/scope/first Source Position/deadline/stable result. Same tuple/ID/hash is a no-op; different tuple/hash under one exact type-specific logical identity is an integrity violation. Dedupe is reclaimed only after TIME_FENCE closes the deadline, source passes that fence, a descendant Recovery Floor contains the apply, and mandatory `systemMutationAuditMinimum` has elapsed.

Replay/Resolve/control outcomes are queried through their Control Operation receipts; runtime mutations are internal evidence and never masquerade as Command receipts or `CommandQueryResult`.

`appliedShardLogPosition` advances for both record kinds. Broker ACK/commit remains a restart hint after the same RocksDB WriteBatch is durable. Checkpoint manifests carry this position and recovery replays the Adapter-defined successor through the typed Activation Barrier. Duplicate System Mutation IDs with the same hash are no-ops; a different hash is an integrity violation.

This design increases Shard Log traffic and adds one Broker round trip before each Publish Admission. Those costs are benchmarked and capacity-limited, but weakening the log would make acknowledged Command results unrecoverable.
