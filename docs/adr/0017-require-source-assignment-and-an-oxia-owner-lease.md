# Require Source Assignment and an Oxia Owner Lease

Nereus Delay V1 permits shard mutation and publication only while one Worker holds both the ingress Broker's Source Assignment and an Oxia-session-bound Owner Lease for the same Delay Shard. The lease is a single-holder ephemeral record; its `ownerEpoch` is allocated from an Oxia monotonic sequence and may contain gaps. A new assignee cannot preempt a live lease. This prevents overlapping new Publish Admissions, while already-admitted destination requests remain subject to the `UNCERTAIN` boundary.

## Acquisition and activation

1. The ingress coordinator assigns the physical Command Topic partition and the Worker disables automatic source-position commits.
2. The Worker enters `ACQUIRING`, allocates a fresh monotonic Owner Epoch, and creates the canonical ephemeral lease with `expected-not-exists`. The value contains shard identity, Worker and process-run IDs, epoch, random fencing-token digest, source-assignment identity, lifecycle, and Oxia session identity.
3. A lost create or update response is resolved by reading the canonical record. Only an exact identity match is success; a different live holder causes the assignee to wait without opening or publishing the shard.
4. The holder enters `RESTORING`, selects or creates one local store incarnation, verifies shard/database identity, restores when necessary, opens RocksDB, and seeks the source using the Adapter-defined successor of `appliedShardLogPosition` (including Pulsar containing-entry replay).
5. After lease acquisition it captures a typed Activation Barrier from the source and catches up using that Adapter's exact reached predicate: Kafka uses an exclusive read-committed LSO cursor from a pinned topic-ID Fetch response; Pulsar uses an inclusive batch-aware last MessageId obtained only through the same still-valid `PULSAR_SUBSCRIBE_RESOURCE_GUARD_V1`-certified consumer connection generation and binds the exact resource/partition attestation into the barrier. A name-only MessageId response is insufficient. It then reconstructs every Lane as `RECOVERING_EVIDENCE` and requeues reversible state.
6. The Worker revalidates Source Assignment, lease session/epoch/token, database incarnation, shard invariants, and source continuity, then conditionally marks the same lease `ACTIVE_FOR_COMMANDS`. Command application and query can resume.
7. Each Lane independently fences/initializes its stronger capability and replays its evidence barrier. Only a Lane with `admissionGate=OPEN && runtimeReadiness=READY` may scan, Claim, or grant Publish Admission; a failed target/evidence dependency cannot block Command application or another Lane.

The shard lifecycle is `UNASSIGNED -> ACQUIRING -> RESTORING -> CATCHING_UP -> ACTIVE_FOR_COMMANDS -> DRAINING -> UNASSIGNED`, with `any nonterminal -> FENCED -> UNASSIGNED|ACQUIRING` and `any nonterminal -> FAILED`. `FENCED` has zero mutation/publication authority and is a retryable placement transition. `FAILED` is reserved for proven source gaps, store/catalog integrity failures, or nonrecoverable protocol invariants; exact cause/repair operation is durable and it cannot auto-reactivate. Query maps a bounded desired transition through UNASSIGNED/ACQUIRING/RESTORING/CATCHING_UP/DRAINING/FENCED to `SHARD_TRANSITIONING`; FAILED, no recovery candidate, authoritative ambiguity, or an ownership deadline breach maps to `SHARD_UNAVAILABLE`. Command application is disabled until shard activation; destination publication additionally requires the Lane's source-ordered Admission Gate to be `OPEN` and its runtime readiness to be `READY`. Catching up to one captured typed source barrier is sufficient even if newer Commands continue to arrive; a Kafka exclusive cursor is never compared as though it were an applied record position.

## Lease guard and loss

- Oxia ephemeral records disappear when their client session closes or expires. The Worker additionally maintains a monotonic local guard based on the last confirmed session activity. Mandatory configuration proves `0 < localLeaseGuardDeadline + localLeaseGuardSafetyMargin < oxiaSessionTimeout`, so the local gate closes before Oxia can expose the canonical lease as absent. On ambiguity, timeout, JVM pause beyond the guard, session change, or Source Assignment loss, it closes the shard event gate before any further command WriteBatch, Claim, Publish Admission, callback mutation, or checkpoint publication.
- Every shard event and asynchronous callback carries shard ID, Store Incarnation, Owner Epoch, fencing-token digest, Generation, Publish Attempt, and Admission revision. Owner/Store/token/Generation/attempt mismatch is audit-only. A retained prior `UNKNOWN` attempt from the same Owner/Store may record its exact ledger outcome after the aggregate runtime revision changes, but only after revalidating the current Generation.
- The new Owner waits until the canonical lease is absent before acquiring a higher epoch. The old Owner therefore stops admitting before the server can expose an expired lease as free. Correctness does not depend on lease-loss notifications arriving promptly.
- Oxia unavailability fails closed for ownership but does not manufacture a destination failure. Recovery or publishing resumes only after a new exact lease is established.

## Revocation and handoff

On planned Source Assignment revocation, the Worker immediately enters `DRAINING`, stops source fetch, due Claim, and new Publish Admission, revokes `CLAIMED` records, and waits a bounded interval for already-admitted callbacks while the lease remains valid. It durably flushes RocksDB and may publish a final checkpoint, commits only source positions already present in the same durable database, closes the DB, and releases the lease. Checkpoint success is an RTO optimization, never a handoff correctness requirement.

If the drain deadline, process, or network fails, the Worker abandons the handoff and lets session expiry fence it. Prior `PUBLISHING` records are recovered as `UNCERTAIN`. A late callback after local fencing cannot update authoritative state.

## Source-position rule

The RocksDB `appliedShardLogPosition = EMPTY | KAFKA_POSITION | PULSAR_BATCH_POSITION`, advanced atomically with every Client Command or System Mutation result, is authoritative. Restore starts at the Adapter-defined successor: Kafka seeks the next offset; Pulsar seeks the containing entry and skips already-applied batch members; EMPTY starts from the Route's certified origin. Kafka group offsets and Pulsar subscription acknowledgements are restart hints only and are advanced strictly after the corresponding WriteBatch is durable. A Broker position ahead of the DB is never trusted as application proof. Missing retained source data causes `SOURCE_GAP` and fail-closed recovery.
